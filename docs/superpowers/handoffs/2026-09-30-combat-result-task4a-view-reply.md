## 1. 인수 확인

Task 4A의 최소 결과 타입(`CombatResult`, `CombatProcessingKind`)과 실제 조회 등록(`IBufferQuery.CombatResultReadSink`)을 받았다. View 인수 가이드의 확인 항목과 대조한 결과는 다음과 같다.

| 확인 | 결과 |
|---|---|
| 결과 없음과 수락·거절 구분 | `TryGetLatest` false = 결과 없음, 수락 여부는 `Accepted` |
| 순번·종류·명령 번호(진행이면 0)·수락·사유 | 모두 있음. 생성자가 조합을 검사 |
| 값 타입 불변·Unity 참조 없음 | 맞음(`ProjectL.Core.Contracts`, sealed, get-only) |
| 전투 전 조회·같은 저장소 | 전투 전에도 조회 가능하고 결과 없음. 상태 Buffer와 같은 인스턴스 |

View는 이것으로 Phase 4(Flow의 자동 진행 등록·확인, `CombatLifeCycle` 바인딩)를 진행한다. 명령·미리보기·진행 Job 세 개는 §3 제안 멤버가 실제 구현될 때까지 미연결로 둔다. 제안 이름으로 먼저 연결하지 않는다.

## 2. 입력 없음 처리 — "실행 시점까지 입력 유지"로 간다 (인계 §5-1 답변)

View는 Job의 처리 여부(bool)를 Flow에 전달하지 않는다. 대신 **Flow가 등록한 조건이 Job 실행 시점까지 유지되도록 보장**하고, Flow의 번호 정지 검사는 그대로 둔다. 판단은 Flow의 확인 조건 한 곳에만 둔다.

| 처리 | Flow 등록 조건 | 실행까지 유지되는 이유 | Core가 정상 false를 돌려주면 |
|---|---|---|---|
| 명령 | `PlayerInput` + 연출 완료 + 미처리 명령 있음 | View는 Core가 처리한 번호를 확인한 뒤에만 명령을 지운다. 전체 비우기는 전투 진입·이탈에서만 한다 | 일어나면 안 되는 상황이다. 처리 번호가 오르지 않으므로 Flow가 멈추고 한 번 보고한다 |
| 자동 진행 | `Automatic` + 연출 완료 | 국면은 Core 처리로만 바뀐다. Runner는 Job을 하나씩 실행하고, Flow는 Runner가 비었을 때만 한 번에 하나 등록한다 | 일어나면 안 되는 상황이다. 결과 누락으로 Flow가 멈춘다 |
| 미리보기 | 요청 번호 > 응답 번호 | 유지를 보장하지 않는다. View가 요청을 바꾸거나 비울 수 있다 | 정상이다. Flow는 요청이 바뀌거나 사라졌으면 기다리지 않는다(현재 동작 그대로) |

- Job은 제안된 bool 반환을 받아도 판단하지 않고 완료(`IsCompleted = true`)로 끝낸다. 성공·실패 판단은 Flow의 확인 조건이 한다.
- 이탈 때 "새 등록 중단 → 기존 Job 종료 확인 → 입력 비우기" 순서는 F2 합의로 완성된다. 그전까지 이탈 경로는 미완성이며, 실행 중 이 구간에 들어오는 경로도 없다.

### 2.1 이 방식의 전제 — Core 확인 부탁

위 방식은 다음이 지켜질 때만 성립한다. 인계 §3·§4의 내용과 같다고 이해했는데, 맞는지 확인을 부탁한다.

1. **처리 호출 한 번은 최종 결과를 많아야 하나 게시한다.** 명령 호출은 그 명령 하나의 결과, 자동 진행 호출은 한 단위의 결과 하나다. 한 호출 안에서 여러 명령을 처리하거나 결과를 연달아 게시하지 않는다.
   - 이유: 최신 결과 슬롯이 하나라서 View가 확인하기 전에 앞 결과가 덮인다. Flow도 등록 하나에 결과 하나만 확인한다.
2. **한 처리 안의 여러 사건(이동 → 피해 → 사망, 여러 유닛 동시 피해 등)은 결과 하나에 담는다.** 후속 F3 ④의 사건 목록 자리다. 차례로 재생할지 동시에 재생할지는 View가 연출에서 정한다.
3. 자동 진행 "한 단위"의 크기는 Core가 정한다. 다만 위 1을 지킬 수 있는 크기여야 한다.

## 3. 확인 요청

### 3.1 결과 순번이 두 곳에 있다

같은 사실이 두 곳에서 읽힌다.

| 위치 | View의 쓰임 |
|---|---|
| `ICombatStateBufferReadSink.LatestResultSequence` | 연출 대기(`PresentedResultSequence ≥ LatestResultSequence`), 전투 View의 변경 신호 |
| `CombatResult.Sequence`(`TryGetLatest`) | 자동 진행 확인: 등록 때 기록한 S보다 뒤의 결과인가 |

요청:

1. 결과를 게시할 때 **두 값을 한 번에 같은 값으로 바꾼다는 것을 계약으로 적어 달라.** View는 결과가 있을 때 두 값이 다르면 "대응 불일치"로 보고 Flow를 멈추게 구현하려 한다.
2. **결과가 없을 때 `LatestResultSequence`의 의미를 알려 달라.** 인계 §4에 따르면 카운터는 `EndBattle`에서 되감지 않고, 마지막 결과 정리는 F2에서 정한다. 그러면 "결과 없음"이면서 `LatestResultSequence > 0`인 상태가 생길 수 있다. 이 상태가 정상인지, 생긴다면 어느 시점인지 알아야 View가 연출 대기와 변경 신호를 잘못 판단하지 않는다.
3. 둘 중 하나를 권위로 두고 다른 쪽을 없애는 편이 낫다고 보면 그 방향을 알려 달라. View는 어느 쪽이든 맞춘다.

### 3.2 자동 진행의 거절이 정상 진행 중에도 나오는가

View 설계(K4·K8)는 **자동 진행 결과가 거절이면 Flow를 멈추고 다시 등록하지 않는다.** 같은 `Automatic` 국면에서 같은 진행을 다시 부르면 같은 거절이 끝없이 반복되기 때문이다. 사용자 명령의 거절(다음 입력을 받는다)과는 다르게 다룬다.

그런데 Core 테스트의 자동 진행 거절 예시가 `Timeline.NoActiveUnit`이다. 활성 유닛이 없는 상황은 정상 진행 중에도 생길 수 있어 보인다. 이 경우 View가 전투 전체를 멈추게 된다.

질문:

1. 자동 진행이 거절 결과를 게시하는 경우는 **규칙상 비정상(버그·데이터 오류)뿐인가?**
2. 활성 유닛 없음처럼 정상 진행 중 생길 수 있는 상황이라면, Core가 거절 대신 **수락 결과 + 국면 전환**(다음 라운드, `Finished` 등)으로 게시할 수 있는가?
3. 정상적인 자동 진행 거절이 꼭 필요하다면, 거절 뒤 **국면이 반드시 `Automatic` 밖으로 바뀌는가?** 같은 `Automatic`에 머물면 View는 다시 등록할 근거가 없다.

View 제안: **자동 진행 거절 = 비정상**으로 두고, 정상 진행에서 생기는 상황은 수락 + 국면 전환으로 표현한다. 답이 이와 다르면 View 설계 K4·K8을 다시 연다. 그전까지 Phase 4는 현재 설계대로 "거절이면 정지"로 구현한다.
