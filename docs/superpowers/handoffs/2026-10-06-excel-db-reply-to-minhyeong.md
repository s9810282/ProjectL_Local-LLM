# Excel DB(DT) 가이드 회신 — Core 연결 관점

작성 2026-10-06 · 보낸 쪽 Core(천명) · 받는 쪽 민형님 · 상태: **전달됨(2026-10-06), 회신 대기**

대상 문서: 「DT 폴더 구조와 Core / View SO 사용 가이드」(2026-10-06), 브랜치 `origin/feature/JMH/Shader` `3a79c81e`

이미 정해진 것(이 문서에서 다시 묻지 않음):

- develop의 기존 SO 테이블 14개는 새 Excel DB로 대체한다.
- 빠진 데이터(재화·로드아웃·필드·구조물·회복·상점 등)는 오늘~내일 중 추가한다.
- 병합은 Shader 브랜치를 먼저 받은 뒤 Core(천명)가 합친다.

## 1 가이드에서 확인한 것

폴더 구조, Core/View의 뜻(작성 방식의 구분이고 둘 다 SO), 임포터 동작, 에셋 위치, 조회 계약(Get/TryGet/GetAll·예외·키 검사), Factory 조립, 새 테이블 추가 절차는 Core가 쓰기에 충분히 명확합니다. 삭제한 Core 시스템과 테스트 범위를 숨기지 않고 적어 주셔서 병합 준비에 도움이 됐습니다.

아래는 Core가 새 DB를 실제로 읽으려면 답이 필요한 부분입니다.

## 2 숫자 코드의 의미와 검증 (답 필요)

가이드 §2에 "엑셀 숫자 코드·플래그를 그대로 저장하며 Enum 변환을 하지 않는다"고 되어 있습니다. Core 규칙은 의미 있는 값(역할, 조준 방식, 스테이지 종류 등)으로 판정하므로, 코드 → 의미 대응표가 필요합니다.

의미를 알려 주셔야 하는 컬럼:

| 테이블 | 컬럼 | Core에서 대응하는 개념 |
|---|---|---|
| Character | `RoleType`, `PositionType` | 유닛 역할(메인·서브·적·본부 등), 소유 자격, 분류 |
| Character | `MoveMethod`, `AttackMethod` → Method | 이동·공격 방식 |
| Character | `State`(문자열) | 특성 목록으로 보임. 구분자와 항목 형식 |
| Method | `Type`, `ChoiceRange`, `Splash`, `SplashValue` | 조준 방식(칸·방향·전체), 범위 모양, 스플래시 비율 |
| Stage | `RoleType` | 스테이지 종류(전투·상점·이벤트)인지 맵 역할(일반·보스)인지, 둘 다인지 |
| Chapter | `StageList`(문자열) | 스테이지 키 목록으로 보임. 구분자 |

요청:

1. 위 코드표를 문서(또는 DT `Enum/` 폴더의 Enum)로 확정해 주세요. 값이 시트에서 바뀌면 Core 판정이 바뀌므로 한 곳에서 관리해야 합니다.
2. **변환·검증 위치 제안:** 행 클래스는 지금처럼 원본 그대로 두고, Core 쪽에 "행 → Core 입력값" 변환을 두어 코드 해석과 범위 검사(음수 HP, 없는 키 참조 등)를 DB 조립 시점에 한 번 하겠습니다. 행 클래스에 의미나 검증을 넣지 않는 방향이 괜찮은지 확인 부탁드립니다.

참고로 값 형식이 다른 곳이 하나 있습니다. `Character_Delay`는 float인데 Core의 딜레이는 정수입니다. 소수가 실제로 쓰이는지 알려 주세요.

## 3 빠진 데이터의 작성 방식 (답 필요)

가이드 §5에 따르면 Excel 테이블 SO는 재임포트 때 Excel 값으로 덮어써지고, §11의 인스펙터 작성 SO는 Excel과 별개로 유지됩니다. 그래서 빠진 데이터를 어느 쪽에 둘지에 따라 Core가 읽는 경로가 달라집니다.

- Excel 시트로 추가: Excel이 원본이고 SO 수동 수정은 사라짐.
- 인스펙터 작성 SO로 추가: Excel과 무관하게 유지.

항목별로 어느 쪽인지, 인스펙터 쪽이라면 **임시인지(나중에 Excel로 옮김) 영구인지** 알려 주세요.

추가 일정이 오늘~내일이라, 시트 설계에 바로 쓰시도록 **Core가 현재 실제로 읽는 값**을 정리했습니다. 이름은 Core 개념명이고 컬럼명은 자유입니다.

| 영역 | Core가 읽는 값 |
|---|---|
| 스테이지 경제 | 전투 시작 골드, 수동 드로우 비용 |
| Run 시작 재화 | 새 Run 시작 때 지급할 재화(현재 어디에도 없음. 상점·회복 결제용) |
| 플레이어 로드아웃 | 메인 캐릭터 키, 시작 서브 캐릭터(키·수량), 시작 손패 수 |
| 적 로드아웃 | 후보 유닛(키·가중치), 등장 수, 시드 |
| 유닛 로스터 | 전투에 불러올 유닛 키 목록 |
| 필드 | 열 수, 행 수, 대기 칸 수, 플레이어·적 배치 깊이 |
| 구조물 | 크기(가로·세로), 최대 HP, 공격 가능 여부, 공격력 |
| 회복 선택지 | 선택지 ID, 비용, 회복 방식(고정·비율), 회복량 |
| 상점 | 상점 스테이지별 후보(유닛 키·가격) |
| 아티팩트 | ID, 초기 보유 수, 차지 칸 모양, 효과 |
| 설정값 | 중장갑 피해 감소율·초기 방향, 아티팩트 보드 초기 크기 |
| 유닛(Character에 없는 것) | 크기(가로·세로), 분류, 소유 자격, 조준 방식·대상 방식, 포격 범위 종류·크기, 관통 수, 특성(종류별 수치) |
| 전투 스테이지 구성 | 필드, 로스터, 적 로드아웃, 경제, 밤 길이, 타임라인 시드, 적 초기 배치(키·칸·방향), 구조물 배치, 본부, 메인 캐릭터 시작 칸·방향, 철로(칸·첫 작동·반복 간격), 지형·장애물·오브젝트 배치(칸·종류·공개 대상) |

**§11 이름 관련 요청:** 전투 스테이지 구성(유닛·배치)은 Core가 판정에 쓰는 규칙 데이터입니다. 기존 팀 규칙에서 "View 데이터"는 표현용이고 Core가 읽지 않는 데이터를 뜻합니다. 그래서 같은 InGameGroup 안이라도 `View`라는 이름이면 헷갈립니다. 이 데이터는 InGameGroup에 두고 Core가 읽는다는 점을 가이드에 명시해 주시고, 가능하면 폴더 이름을 `Authoring`이나 `Inspector`처럼 작성 방식이 드러나는 이름으로 바꾸는 것을 제안합니다.

## 4 맵 그래프 생성 입력 (답 필요)

삭제된 `StageGeneratorSystem` 안에 Core의 챕터 그래프 생성 알고리즘이 있었습니다. 병합 때 Core가 이 알고리즘을 다시 살려 Chapter 테이블에 연결하겠습니다. 챕터 완료 기록(`MapProgressBuffer`)도 Chapter 키 기준으로 다시 연결합니다. 이 방향에 이견이 있으면 알려 주세요.

현재 알고리즘이 쓰는 입력과 Excel 대응:

| 알고리즘 입력 | 설명 | Excel |
|---|---|---|
| 깊이 | 시작 노드부터 보스까지 층 수 | `Chapter_Length`로 보임 |
| 최대 폭 | 층마다 노드 수를 1~최대 폭에서 무작위로 정함 | `Chpater_StageWidth`로 보임 |
| 일반 스테이지 후보 | 중간 층 노드에 무작위로 배정 | `Chapter_StageList`로 보임 |
| 보스 스테이지 | 마지막 층 한 개 | `Chapter_End`? |
| 시드, 매 Run 시드 변경 여부 | 그래프 재현용 | 없음 |
| 연결 방식, 가중치, 추가 연결 확률 | 층 사이 연결 규칙 | 없음 |

질문:

1. `Chapter_Start`, `Chapter_Point`, `Chapter_PointStage`, `Chapter_End`, `Chapter_BattleStage`, `Chatper_EventStage`의 의미를 알려 주세요. 특히 기획 의도가 "시작 → 중간 고정 지점 → 끝" 구조라면 현재 알고리즘(시작 노드 → 무작위 층 → 보스)과 모양이 다르니, 생성 규칙을 함께 맞춰야 합니다.
2. 전투·이벤트 스테이지 "수"를 정하는 값이 있다면, 노드 종류 배분 규칙(층별 비율 등)도 알려 주세요.
3. 시드와 연결 규칙 값은 Excel에 추가할까요, 아니면 Core 상수로 둘까요?

## 5 키만 있고 테이블이 없는 참조

아래 컬럼은 다른 테이블의 키로 보이지만 해당 테이블이 없습니다. 이번 추가 범위에 들어가는지, Core가 지금은 무시해도 되는지 알려 주세요.

- `Character_WeaponUpgradeEffect`, `Item_Effect`, `Object_Effect`, `Terrain_Effect`, `Obstacle_HitEffect`·`DestroyEffect` → Effect
- `Character_UnlockTrigger`, `Item_Trigger` → Trigger

## 6 구조 규칙 확인

1. **Excel 행과 기존 규칙 P1·P2.** 기존 DB 규칙은 "순수 Data에 Unity 타입 금지(P1), 입력 SO와 순수 Data 분리 후 `GetData()`로 매번 새로 생성(P2)"이었습니다. Excel 행은 `using UnityEngine`·`[SerializeField]`를 쓰고 테이블 목록 객체를 그대로 반환합니다. 임포터 방식상 자연스러운 선택으로 보이는데, 팀 규칙으로 "Excel 행은 입력 표현이고 P1·P2의 예외"라고 명시해 주시면 됩니다. Core는 위 §2의 변환을 거쳐 순수 값만 쓰겠습니다.
2. **GUID 변경.** `InGameGroup.cs` 스크립트와 `InGameGroup.asset`의 GUID가 바뀌었습니다. 의도한 변경인지 알려 주세요. 기존 GUID를 참조하는 씬·프리팹·테스트가 있으면 병합 때 깨집니다.
3. **Enum 위치 중복.** `Stage/Enum/StageType`·`StageMapRole`은 develop의 `Data/Common/StageType`·`StageMapRole`과 값이 같고 위치만 다릅니다. 병합 뒤 한 곳만 남기겠습니다. 남길 위치에 의견이 있으면 알려 주세요.
4. **Delay 형식.** §2 참고(float와 int).
