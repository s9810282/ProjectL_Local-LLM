## 1. 담당 분리 확정 — 요청 §2 답변

**View가 전투 Plan·Job을 담당하고, 병합 과정에서 양쪽 테스트를 조정하는 것을 사용자가 허용했다.**

| 영역 | 담당 |
|---|---|
| CombatLifeCycle, CombatFlow의 등록 판단·확인·정지와 View 입력 수명 | View / Flow 작업자 |
| CombatPlan, 준비·명령·미리보기·자동 진행 Job 네 개, Job 몸통의 서비스 호출 연결 | View / Flow 작업자 |
| 해당 전투 JobType 확장 | View / Flow 작업자. 공용 변경은 Framework 담당자에게 공유 |
| 처리 서비스, 준비 입력 조립, 규칙 계산, Buffer 상태 반영과 결과 기록 | Core 작업자 |
| 상태·결과 읽기 계약 | Core가 정의하고 View와 합의 |
| 공용 Runner, 실행 예외 뒤 Runtime 중단, 전환 실행 경계 | Framework 담당자. 종료 수명은 Core·View와 협의 |

이는 **작업 담당 분리**다. Plan·Job 코드는 기존 Systems 실행 계층에 두며, View 표현 코드에 전투 규칙이나 게임 상태 쓰기를 옮기지 않는다. 한 번의 처리에 필요한 계산·검증·상태 반영·결과 기록은 Core 처리 서비스의 동기 호출 안에서 끝낸다.

Core는 앞으로 전투 Plan·Job을 별도로 확장하거나 중복 구현하지 않는다. 기존 Core 이전 계획의 Global Constraints와 Task 8에 적힌 전투 Plan·Job 담당은 이 결정으로 변경한다. Task 4의 완료 이력은 유지한다. **2026-09-30 후속 정리:** [Core 이전 계획](../plans/2026-09-29-character-buffer-effect-migration-plan.md)에 담당 변경과 G2, F3 선행 Task 4A, 종료·조회·통합 검증을 반영했다. 구현이나 병합 완료를 뜻하지 않는다. 이 답변은 Stage 등 다른 구간의 모든 Plan·Job 담당을 일괄 변경하는 결정은 아니다.

## 2. 병합과 Start 인계 — 요청 §3 답변

**View 쪽 구조로 통합하고, Core의 기존 준비 동작을 연결한다.** View 쪽에서 병합하면서 아래 양쪽 테스트를 조정할 수 있다.

1. View의 CombatPlan과 `CombatPrepareJob`, `CombatCommandJob`, `CombatPreviewJob`, `CombatAdvanceJob` 구성을 유지한다.
2. `CombatPrepareJob.Execute()`의 미연결 예외를 기존 `_service.CoreGroup.Combat.PrepareBattle()` 호출로 교체한다. 기존 완료 가드를 유지하고, 정상 반환 뒤에만 `IsCompleted = true`로 바꾼다. 예외가 발생하면 완료나 성공 결과를 만들어 내지 않는다.
3. 기존 Core의 `CombatJob`은 새 준비 Job으로 대체한다. 두 Start Job을 병존시키지 않는다. View가 이름 변경하면서 유지한 기존 `.meta` GUID를 보존한다.
4. `CharacterBattlePreparationTests`의 직접 `CombatJob` 참조를 새 Job으로 옮긴다. 실제 Register → Runner → 준비 서비스 경로와 검증 의도는 유지한다.
5. 일반 `JobSystemTests`의 Lobby 표본은 유지할 수 있다. 병합 후 사용하지 않는 준비용 가짜 구현은 사용처를 확인하고 제거한다. 새 CoreGroup 멤버 때문에 필요한 가짜 구현까지 무조건 지우지는 않는다.
6. **View의 CombatPlanTests도 함께 갱신한다.** 현재 Start의 미연결 예외를 기대하는 케이스는 준비 호출·완료 검증으로 바꾼다. 미연결 예외 전파를 검사하는 Runner 케이스는 그 검증 목적을 보존하되, 이미 연결한 Start가 미연결이라고 가정하지 않도록 조정한다.
7. 병합 후 관련 Core·Framework EditMode 테스트를 함께 실행하고 결과와 남은 실패를 공유한다. 준비 성공, 실패 시 미반영, 완료 Job 재실행 방지 검증을 약화하지 않는다.

Core 쪽 실제 준비 API는 `IInGameCoreSystemGroupService.Combat` → `ICombatProcessingService.PrepareBattle()`이며, 서비스 파일은 다음과 같다.

`Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/CoreSystem/CombatSystem/CombatProcessingService.cs`

이 서비스와 테스트용 준비 경로는 구현됐지만 **생산 준비 입력(G7)은 미연결**이다. Job 호출 연결만으로 실제 전투 진입이 완성되는 것은 아니다.

## 3. 게임 규칙 확정

| 항목 | 사용자 확인 내용 | 반영 위치 |
|---|---|---|
| 서브의 다음 전투 진입 HP — G2 해소 | 이전 전투의 피해·사망·전투 한정 버프를 초기화하고, 정의상의 최대 HP에 해당 보유 카드의 영혼 증가분을 포함한 최대 HP로 시작한다. 보유 카드와 영혼 수는 유지한다. 기본 최대 HP 10, 영혼 2개라면 이전에 죽었어도 다음 전투는 12/12다. | Core 진입·정리 계산과 회귀 테스트 |
| 메인의 전투 간 상태 | 현재 HP와 지속 수치를 유지한다. 서브의 최대 HP 복원 규칙을 메인에 적용하지 않는다. | Core CharacterBuffer 및 진입 계산 |
| 전투 중 자발적 포기·로비 복귀 | 패배 경로로 처리한다. View가 Buffer를 비우고 장면만 바꾸어 패배 처리를 우회하지 않도록 연결한다. | Core 패배 처리와 View/Framework 전환 경계 |
| 타임라인 예고 | 기본 표시 목표는 10칸이며 기획에 따라 조절할 수 있어야 한다. 순서는 Core가 계산하고, 표시 개수의 설정·요청 방법은 API에서 정한다. | Core 예고 조회 계약과 View 표시 |

**게임 튕김은 자발적 포기와 구분한다.** 사용자는 해당 스테이지를 진행하지 않은 상태로 복구하는 방향을 제시했지만, HP·영혼·보상까지 포함한 복구 범위와 저장 시점은 확정하지 않았다. 이번 답변은 크래시 복구나 디스크 저장 기능을 추가하라는 지시가 아니다.

자발적 포기의 패배 판정은 확정됐으나, 이 결정만으로 새로운 보상·패널티·전체 로스터 초기화 규칙을 추가하지 않는다. 구체적인 패배 결과 반영과 종료 호출 순서는 기존 규칙 및 아래 F2 계약으로 연결한다.

## 4. 처리 API·번호·국면 — 요청 §5.1~5.2 답변

현재 실제 API는 준비뿐이다. 명령·미리보기·자동 진행의 정확한 멤버 이름과 반환형은 Core가 후속 계약으로 제공한다. View는 예상 이름의 Core 인터페이스를 별도로 만들지 않는다.

계약 정리의 기준은 다음과 같다. 아래는 후속 구현 기준이며, 현재 구현 완료를 뜻하지 않는다.

- 명령 한 번은 처리되지 않은 명령 하나를 읽고, 수락 또는 게임 규칙상 거절 결과와 처리 번호를 기록한다. bool을 사용한다면 입력 처리 여부와 게임 행동 수락 여부를 구분한다.
- 명령이 없는 경우의 정상 반환과 Flow의 처리 확인 조건은 함께 맞춘다. 번호가 오르지 않았다는 이유로 정지하는 현재 Flow와 모순되는 호출 계약을 만들지 않는다.
- 미리보기는 게임 상태를 반영하지 않고 요청 번호에 대응하는 미리보기 결과만 기록한다. 상태 변경 결과 순번과 구분한다.
- 자동 진행 한 번의 처리 범위, 수락·거절 의미와 국면 변경을 명확히 하고, 상태와 결과를 같은 호출에서 일관되게 기록한다.
- 번호는 전투 종료·재진입만으로 되돌리지 않는 기존 인벤토리 및 View Buffer 수명과 맞춘다. 입력 번호는 명령·미리보기 사이에서 건너뛸 수 있으므로 모든 번호가 매 처리마다 정확히 1씩 증가한다고 가정하지 않는다. 결과 순번과 입력 번호는 별개다.
- Core는 View 입력을 삭제하거나 연출 확인 값을 쓰지 않는다. View가 처리 번호를 보고 입력을 정리한다.
- 준비 이후 배치 단계와 전투 개시, 적 선공·기믹 처리의 `CombatFlowPhase` 대응은 실제 명령 이전과 함께 명시한다. 현재 준비가 `PlayerInput`을 설치한다는 사실만으로 전체 국면 전환이 구현됐다고 보지 않는다.

## 5. 가장 먼저 제공할 결과 읽기 계약 — 요청 §5.3 / F3

**Core의 우선 인계 항목은 Flow 진행에 필요한 최소 결과 읽기 타입과 조회 방식이다.** 전체 전투 계산이나 모든 연출 데이터 완성을 기다려 한꺼번에 넘기지 않는다.

| 제공 단계 | 내용 | 완료를 판단하는 기준 |
|---|---|---|
| 1. 최소 읽기 계약 | 결과 순번, 명령 번호, 처리 종류, 수락/거절, 이유와 결과 유무 조회 | 실제 타입·파일·네임스페이스·어셈블리 공유. View는 가짜 구현으로 Flow를 검증 가능 |
| 2. 생산 조회 등록 | 실제 저장소에 연결된 읽기 서비스와 조회 경로 | Export/서비스 키 또는 그룹 속성으로 실제 인스턴스를 조회 가능. 전투 전 바인딩에서 결과 없음 상태도 표현 |
| 3. 처리별 발행 | 명령·자동 진행의 실제 결과 및 미리보기 발행 | 상태와 결과의 일관된 기록, 순번·처리 번호 갱신 검증 |
| 4. 연출 상세 확장 | 이동·피해·사망·영혼·기믹 등 해당 처리에서 발생하는 순서 있는 사건과 미리보기 내용 | 각 계산 이전 시 실제 값으로 검증하고 View에 변경 사항 전달 |

**Task 4A 후속 제공:** `CombatResult` / `CombatProcessingKind`와 실제 `ICombatResultReadSink.TryGetLatest(out CombatResult)` 및 기존 CombatStateBuffer 조회 등록이 구현됐다. 정확한 위치·조회 방식·검증 근거는 [Task 4A 인계 문서](2026-09-30-combat-result-task4a-handoff.md)를 따른다. 위 단계 1·2의 Core 제공은 완료됐으며, 단계 3·4의 실제 결과 게시와 View 생산 연결은 아직 미구현이다. 빈 실제 저장소의 등록과 실제 결과 소비 완료를 구분한다.

결과 저장은 기존 CombatStateBuffer와 그 수명을 우선 검토한다. 결과만을 위해 별도 Buffer를 늘리는 것으로 확정하지 않는다. 최신 결과는 View 확인 뒤에도 Flow가 읽을 수 있어야 하며, 미확인 결과를 잃지 않아야 한다. 최신 기록과 사건 목록의 교체·정리 및 전투 경계 보존 정책은 실제 조회 계약에 명시한다. 모든 사건을 보관하는 무제한 목록을 기본 전제로 삼지 않는다.

## 6. 상태·지형·표시 값 — 요청 §5.4~5.6 답변

- 턴·승패·밤·기믹 런타임·필드 효과 등 실제 전투 상태는 Core 이전 범위에서 읽기 값을 제공한다. 이미 구현된 구조물·레일·배치 깊이 등은 기존 Buffer 조회를 사용한다.
- 준비 인덱스·리비전은 옛 Snapshot 필드를 그대로 복제하지 않고, View가 필요한 판단을 확인해 최소 계약을 정한다. View에서는 해당 값의 사용 사례를 함께 알려 주면 된다.
- **막힌 칸은 입력 출처 확인이 필요하다.** 현재 Core 기준 FieldData에는 해당 필드가 없다. 기존 생성 규칙이나 DB 저작 출처를 확인한 뒤 범위를 정하며, 임의의 지형 데이터나 새 게임 규칙을 만들지 않는다.
- 수동 드로우의 가능 여부·실패 이유·비용은 Core 규칙 계산에서 제공한다. 남은 장수 등의 표시 계산은 요청 문서의 기존 분담을 따른다.
- 타임라인 예고는 기본 10칸을 목표로 하되 개수 조절을 지원한다. 정확한 설정 위치와 조회 시그니처는 후속 계약으로 제공한다.

## 7. 종료·이탈과 실제 진입 — 요청 §5.7~5.8 답변

**F2에서 확정된 게임 규칙은 자발적 포기·로비 복귀를 패배로 처리한다는 점이다.** 다음 기술 항목은 아직 Core·View·Framework 간 연결이 필요하다.

- 새 입력·새 Job 등록 중단, 이미 등록된 Job 종료 확인, 패배/최종 결과 기록, 결과 표시·확인, EndBattle, 장면 전환의 구체적인 순서와 호출자.
- 마지막 결과와 연출에 필요한 값을 정리가 먼저 없애지 않도록 하는 수명 보장.
- 정리를 별도 Job으로 할 필요가 있는지와, 필요할 때 전환 요청자가 완료를 확인하는 방법.
- 치명적 실행 예외를 정상 패배나 정상 이탈로 위장하지 않는 Framework F1 처리.

G7의 실제 준비 입력 연결 시점은 아직 약속하지 않는다. Core가 준비 입력 공급과 기존 준비 서비스 연결을 검증한 뒤 제공 상태를 알린다. 추가 Core 작업자에게 G7을 분담하는 방안은 논의됐지만, 이 문서로 작업자가 배정되거나 구현이 시작된 것은 아니다.

실제 전투 진입 활성화는 G7뿐 아니라 해당 경로에 필요한 처리 기능·Framework 실행 경계·DB 효과 연결의 준비 상태도 함께 확인한다. 특히 아티팩트 생산 연동은 기존 G9 확인을 유지한다.

View는 본 답변을 담당·병합 합의에 반영한다. Core 이전 계획의 담당 문구와 G2 상태는 위 후속 정리에 반영했다. Task 4A는 [별도 인계](2026-09-30-combat-result-task4a-handoff.md)로 최소 F3 타입과 실제 조회 등록을 제공했고, 다음 Core 구현은 Task 5다. 이후 처리 기능별 Job 연결과 실제 결과 발행·보존을 검증한다. 이 문서는 새 Runner, View의 규칙 계산, Core의 View 입력 수정, 저장·복구 기능 추가를 요청하지 않는다.
