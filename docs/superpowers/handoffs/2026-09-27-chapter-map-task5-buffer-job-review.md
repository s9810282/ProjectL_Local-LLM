## Write and failure trace

All rows require fresh Buffer reads for the command and prevalidation before their first write. These are proposed application orders, not currently wired call paths.

| Command | Inputs and prevalidation | Ordered effect | Failure or callback boundary |
|---|---|---|---|
| Initial chapter entry | Map exists via `MapProgressReadSink.GetMap`; graph is nonempty via `StageProgressReadSink.GetStages`; chapter is uncleared; reject a different active unfinished chapter. Complete `Generate` first. | `CurrentProgressWriteSink.SelectMap(chapterKey)` once. Same-key call retains `CurrentStage`; do not use it as a reset. | `SelectMap` checks a positive key before mutation and has no callback. Missing map or graph must fail before it. |
| Accepted node click | Copy graph/clear flags and derive `fromNodeId` from `CurrentStage.NodeId`, or use the start sentinel before first entry. Check current/graph/chapter agreement, uncleared adjacent next-depth target, target stage key and DB stage readiness, a nonblank temporary stage label, and still-active chapter. | Call the approved stage dispatch; only after confirmed successful entry call `CurrentProgressWriteSink.SelectStage(nodeId, stageKey, stageName)`. | Current `StageServiceManager.Enter(stageKey)` performs a DB lookup, selects a type handler, and calls it; the handlers only validate data. These may throw before the Buffer write. A future asynchronous handler or callback cannot be treated as completed by a void return. The current path is not playable entry and is blocked until the owner defines a success/commit boundary. `SelectStage` checks map/node/key/name before mutation but does not validate node membership itself. |
| Ordinary stage victory | Selected `CurrentStage` node/key match the Buffer graph, chapter is active and uncleared, node is uncleared, and the stage outcome is verified as victory by its owner. | `StageProgressWriteSink.SetClear(chapterKey, nodeId, true)` once. | `SetClear` checks map/node registration before replacing the record and has no callback. Its read-only `GetStages` view wraps mutable list contents; copy the command values immediately before evaluation. |
| Defeat | Same selected-stage and terminal-outcome checks. | No progression Buffer write; invoke attempt-end flow once. | `EndAttempt` is an effect flag, not a stored Buffer field. The stage/attempt owner must suppress a repeated dispatch; no current Job or Buffer receipt does this. |
| Boss victory | Same victory checks; boss fact must come from authoritative stage content, and the boss node must have no successors. Prevalidate both registered stage node (`GetStages`) and map (`GetMap`) before any write. | `StageProgressWriteSink.SetClear(chapterKey, nodeId, true)`, then `MapProgressWriteSink.SetClear(chapterKey, true)`. | A missing map would throw in the second setter after the stage write if it were not prevalidated. The current setters do no user callback between writes. With both records validated and no intervening mutation on the single-threaded path, there is no identified ordinary second-setter validation failure. This is not an atomicity guarantee: owner review is needed if callbacks, concurrency, persistence, or different failure behavior is introduced. |

`CurrentProgressBuffer.SelectStage` requires a nonblank `stageName`, but `StageProgressData`, `StageRootData`, `StageBaseData`, and `StageViewPropData` currently have no name field. `StageUI` reads `CurrentStage.StageName`, and no map screen implementation is present in the inspected View/UI source. For the current increment, a stable temporary label such as `Stage {stageKey}` can satisfy `SelectStage`; users will see that label in `StageUI`. Real display copy can be supplied later without changing progression rules. Do not add Buffer metadata for names until an actual screen requires it.

The active branch's `StageProgressData` has no boss field, but the separate `feature/Yonggeun/DB_SO` work described in the 2026-09-26 DB-SO merge notice already adds `StageType` and `MapRole` to this existing Buffer record and has `StageGeneratorSystem` copy them from DB stage content (commit `39b634f`). That commit is not in the active branch's history as of this review. Once integrated, the coordinator can use the selected non-start node's Buffer `MapRole` as the caller-supplied `isBossStage` fact. The final graph position alone must not assert a boss victory. Check merge compatibility and the resulting Buffer API before Task 6/7 implementation; do not request a second boss-classification extension.

## Related state and Jobs

`RunProgressionService` is a separate stateful `RunProgressState`/`StageMapSession` path. It already coordinates combat entry, stage completion, checkpoint versus live health, shop, recovery, wallet, deck, and Artifact activation with specific validation and prepared writes. Do not call it from the Buffer-backed chapter coordinator or silently transfer its Run ID/revision/receipt model. Its `TryActivateStage` prepares a result and validates map/stage before Artifact lease activation and mutation; `TryCompleteStage` validates the active stage and terminal combat outcome. `RunShopService` and `RunRecoveryService` plan and validate wallet/deck/health changes before applying them. No current Systems chapter command touches these owners, so no generic cross-owner transaction is justified by this review. A later combined command must trace its actual write order before enablement. Task 4's `StageArtifactLifecycleService` retains an uncertain lease and blocks activation/disposal while cleanup is pending; stage transfer must preserve that ownership block.

Initial `SelectMap` and a validated map click need no Job by default. Stage dispatch may require a Stage/LifeCycle Plan once its real handler and completion signal exist. Combat outcome, attempt-end, and result presentation may require ordered Jobs when attached to the real flow; Task 7 must decide from the concrete handler sequence. `JobRegisterSystem` binds InGame services in `PostBindService`, installs Plan delegates in `Initialize`, and enqueues their results. `StagePlan`, `CombatPlan`, and their Jobs are scaffolding. `JobRunnerSystem.Tick` calls `Execute()` again on a later Tick while `IsCompleted` is false; after completion it drops the current Job. A Job must mark completion after a successful coordinator effect, or carry a one-shot applied flag if it waits for later work. A failed or uncertain application must not report completion or blindly replay a preceding write. Runner `Clear()` is not an undo mechanism.

## Owner decisions and Task 6/7 gate

- **Stage entry:** The Stage flow owner must define when `Enter` has really succeeded, and whether a handler can call back, defer, or fail after a visible side effect. Until then, do not enable the production node-click write. `SelectStage` remains after successful dispatch.
- **Stage names and visible metadata:** Use a stable nonblank placeholder such as `Stage {stageKey}` for now. The View owner can later identify real display copy and confirm whether a map screen needs names for every node. Extend an existing Buffer only for a demonstrated display gap.
- **Boss classification:** Integrate and verify the DB-SO branch's existing B1 `StageProgressData.MapRole` change before deriving `isBossStage`; it is not yet in this branch. The coordinator reads the selected non-start node's role from Buffer. No second classification field is proposed.
- **Boss dual write:** The Buffer owner should confirm the single-threaded prevalidation contract and absence of callbacks or concurrent mutation across `Stage.SetClear` and `Map.SetClear`. If either setter can fail after the other commits under real execution, use an owner-approved narrow coordinated operation before enabling boss victory. No expected-revision Run protocol is needed.
- **Attempt end and Jobs:** The Stage/LifeCycle owner must define the terminal outcome and one-shot attempt-end handoff. Task 7 must verify incomplete Job replay cannot repeat accepted effects.
- **Bootstrap:** `StageLifeCycle` and `CombatLifeCycle` enter/exit hooks and their Jobs are TODO scaffolding. No full runtime bootstrap or playable chapter path was observed. Composition or managed tests alone do not close this gate.
