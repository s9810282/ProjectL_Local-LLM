## 1. 한 줄 요약

Task 4에서 전투 준비 서비스와 구조물·레일·기믹 정보가 생겨 요청 일부가 풀렸다. 사용자 지시로 K2를 유지해 충돌을 해결하고 준비 Job을 연결했다. **답변으로 K2와 병합 방식이 확정됐다**(천명님 계획의 담당 문구는 Core 쪽에서 정리 예정). 다음 구현에 필요한 것은 여전히 **결과 기록 읽기 타입(§5.3)**이며, Core가 가장 먼저 넘기기로 했다.

## 2. 소유 경계 — 확인 요청 (가장 먼저)

### 2.1 무엇이 어긋났나

| 문서 | 적힌 내용 |
|---|---|
| View 설계 결정 K2([전투 진행 골격 설계](../specs/2026-09-30-combat-flow-skeleton-design.md) §9) | `CombatLifeCycle`·`CombatFlow`·`CombatPlan`·전투 Job 전부(`Start` 포함)와 `JobType` 값은 **View 작업**이 만든다. Core는 **처리 서비스만** 제공한다 |
| 천명님 [이전 계획](../plans/2026-09-29-character-buffer-effect-migration-plan.md) Global Constraints(`1a51234c`에서 추가) | "Core-side ownership includes CombatPlan, command-processing Jobs" |

View 쪽 요청 문서가 전달되기 전에 두 계획이 각자 진행돼 생긴 어긋남으로 보인다. **View 작업은 K2를 유지하려 한다.** 이유는 다음과 같다.

- 전투 Flow는 Buffer 설계 D6에서 View 작업(스테이지 내부 담당)이 맡기로 했다.
- Flow는 **연출 확인(`PresentedResultSequence`)**을 보고 다음 처리를 등록한다. 연출 대기와 진행 등록이 한 곳에 있어야 진행의 주인이 하나가 된다. Plan·Job만 떼어 Core에 두면 "무엇을 언제 등록하나(View)"와 "무엇으로 구성하나(Core)"가 두 계획으로 갈린다.
- Job은 서비스 호출 한 줄이다. 규칙·계산·Buffer 쓰기는 모두 Core 서비스 안에 있으므로 Core의 책임은 줄지 않는다.

### 2.2 제안하는 분담

| 영역 | 담당 |
|---|---|
| `CombatLifeCycle`, `CombatFlow`(등록 판단·확인·정지) | View |
| `CombatPlan`, 전투 Job 네 개(준비·명령·미리보기·진행), Job 몸통의 서비스 호출 한 줄 | View |
| `JobType` 값(`ProcessCommand = 3`, `ProcessPreview = 4`, `AdvanceCombat = 5`, 이미 추가) | View(Framework 담당자에게 공유) |
| 처리 서비스(`ICombatProcessingService` 등), 규칙 계산, Buffer 게시, 결과 기록 | **Core** |
| 결과·상태 읽기 인터페이스의 모양 | Core가 정의하고 View와 합의 |

요청: 천명님 계획의 위 문장을 이 분담에 맞게 고쳐 주시거나, 다른 의견이 있으면 알려 달라. 합의되면 View 문서에 기록한다.

> **답변(Core 답변 §1):** 위 분담 그대로 확정. Core는 전투 Plan·Job을 따로 확장하거나 중복 구현하지 않는다. 공용 Runner·예외 뒤 Runtime 중단·전환 실행 경계는 Framework 담당자 몫으로 명시했다. 천명님 계획의 담당 문구는 아직 고쳐지지 않았다. View 설계 K2·K12에 기록했다.

## 5. 남은 요청

아래 모양은 View가 필요로 하는 것을 설명하는 제안이다. 이름·타입·위치는 Core 구조에 맞게 정하면 된다.

### 5.1 처리 서비스 세 개 (R6)

준비와 같은 방식으로 `CoreGroup.Combat`(`ICombatProcessingService`)에 더하는 것을 예상한다. Job은 각각 **한 번의 동기 호출**만 한다.

| 처리 | 호출 뒤 Buffer에 남아야 하는 것 |
|---|---|
| 명령 | `HandledCommandNumber`보다 큰 첫 명령 하나를 `CombatViewBuffer`에서 읽어 처리. 수락이든 거절이든 결과 기록 하나 + 결과 순번 증가 + 처리 번호 = 그 명령 번호 |
| 미리보기 | 현재 미리보기 요청을 읽어 계산. 미리보기 결과 + `AnsweredPreviewNumber` = 요청 번호. 게임 상태와 결과 순번은 바꾸지 않음 |
| 진행 | 적 턴·타임라인·기믹 한 걸음. 결과 기록 하나(명령 번호 0) + 결과 순번 증가 + 국면 갱신 |

순번이 "증가"한다는 것은 이전보다 커진다는 뜻이다. 입력 번호는 명령과 미리보기가 한 카운터를 나눠 써서 건너뛸 수 있고(Core 답변 §4), View Flow는 `≥`·`>`로만 비교하므로 정확히 1씩 오른다고 가정하지 않는다.

확인할 것: 멤버 이름, 반환값의 뜻(명령 처리 여부 bool이라면 게임 규칙 수락과 구분), 읽을 명령이 없을 때의 동작.

View Flow는 처리 뒤 번호가 오르지 않으면 "처리되지 않았다"로 보고 **멈춘다**(같은 처리를 다시 등록하지 않는다). 그래서 위 번호 갱신은 호출 한 번 안에서 끝나야 한다.

### 5.2 번호와 국면 (R1~R4)

- 세 번호는 1부터 계속 커지고 **전투가 바뀌어도 되돌리지 않는다.** `CombatViewBuffer`의 번호 카운터와 연출 확인 값도 되돌리지 않기 때문이다. Task 2 인벤토리의 "sequence counters survive battle cleanup"과 같은 뜻으로 이해하고 있다.
- 국면 `CombatFlowPhase`(`None`·`PlayerInput`·`Automatic`·`Finished`)는 처리 결과와 같은 호출에서 갱신된다. 배치 단계도 `PlayerInput`으로 본다. 전투 진입 직후 적 선공, 기믹 발동이 모두 `Automatic`에 들어가는지 확인해 달라.

### 5.3 결과 기록 읽기 — 타입을 먼저 (R5·R11·F3)

**View가 지금 막혀 있는 곳이다.** View Flow는 자동 진행을 등록하려면 그 결과가 수락인지 알아야 한다(순번 증가만으로는 거절을 구분할 수 없다). 천명님 계획의 "결과·상태 읽기 인터페이스를 먼저 정해 View와 공유한다"는 방향과 같다. **구현 전이라도 타입(인터페이스와 값 타입)만 먼저 받으면** View는 가짜 구현으로 Flow와 화면 작업을 진행할 수 있다.

한 결과 기록 안에 필요한 것:

| 항목 | 쓰는 곳 |
|---|---|
| 결과 순번, 명령 번호(진행이면 0), 처리 종류(명령/진행) | Flow 확인, View가 결과와 명령을 짝지음 |
| 수락/거절, 거절 이유 | Flow는 자동 진행 거절이면 멈춤. View는 거절 알림 |
| 일어난 일 목록(순서대로): 이동, 공격, 피격·피해(전후 값), 사망, 반격, 영혼 생성·획득, 밤 종료·회수, 승리/패배, 특성·기믹 발동 | 연출 재료. 옛 `StageSessionHost`가 결과에서 만들던 사건이 기준이다 |

미리보기 결과(R11, 최신 하나): 요청 번호 + 이동 범위, 이동 예상(도착·비용), 공격 범위, 공격 예상(영향 칸·예상 피해·관통 감쇠), 배치 가능 여부.

보존 수명:

- Tick 순서가 Runner → View → Flow라서 **View가 결과를 확인·정리한 뒤에 Flow가 같은 결과를 읽는다.** 최신 결과 기록은 View 확인 뒤에도 다음 결과로 바뀔 때까지 읽을 수 있어야 한다.
- 연출이 한 프레임에 끝나지 않으므로 View가 확인하지 않은 결과는 지우지 않는 편이 좋다. 목록 정리 정책을 알려 달라.

제안 위치: 새 Buffer를 늘리지 않고 `CombatStateBuffer` 안에 두되, 상태와 결과는 소비자·수명이 달라 **읽기 인터페이스를 따로** 두는 것(가칭 `ICombatResultReadSink`). View는 이 이름을 먼저 선언하지 않고 기다린다.

### 5.4 전투 공통 상태의 나머지 (R7)

`CombatStateData`에 더해 주었으면 하는 것(구조물·레일·기믹 정의·배치 깊이는 이미 있다):

- 배치/전투 단계, 준비 인덱스, 메인 배치 잠금
- 현재 턴: 활성 유닛, 리비전, 완료 턴 수
- 승패: 결과와 이유
- 밤: 경과와 남은 양
- 기믹 런타임 상태(다음 발동 시점 등), 필드 효과(가시밭·영혼), 아티팩트 발동

### 5.5 필드 지형 (R8)

막힌 칸. View는 InGame DB를 읽지 않으므로(P6) 전투 준비 때 Core가 담아 줘야 한다.

### 5.6 규칙 판단이 필요한 표시 값 (R9·R10)

- 수동 드로우: 가능 여부, 실패 이유, 비용. 남은 장수는 View가 순서 길이 − 커서로 계산한다.
- 타임라인 예고: 앞으로 N칸의 순서. 순서 계산은 규칙이라 View가 흉내 내지 않도록 Core가 계산한 값을 내 달라.

### 5.7 전투 종료와 이탈 수명 (F2)

- 마지막 결과 표시·확인과 `EndBattle` 중 무엇이 먼저이며 누가 부르는가
- 정상 종료와 중도 이탈에서 결과 반영·정리의 차이
- 정리에 별도 Job이 필요한가. 필요하면 View의 전환 요청 경계가 그 완료를 어떻게 확인하는가

Framework 쪽(예외 뒤 재Tick 중단, 전환 요청 소유자)은 [Framework 공유 문서](2026-09-30-combat-flow-framework-share.md)에서 민형님과 협의한다.

### 5.8 준비 입력의 운영 연결 (G7)

`PrepareBattle`은 지금 테스트용 입력 소스가 있어야 동작한다. 운영 입력이 연결되는 시점을 알려 주면 View는 그 뒤에 실제 전투 진입 경로(부트스트랩·씬)를 켠다.

## 6. 요청하지 않는 것

- Core가 `CombatViewBuffer`를 고치거나 입력을 지우는 것. 입력 정리는 View가 처리 번호를 보고 한다.
- View가 계산할 수 있는 값: 손패 목록(`Area == Hand` + 슬롯), 칸 점유(`OccupiedCells`), 남은 드로우 수, 메인 ID(`OwnershipRole == Main`), 하이라이트 같은 표시 상태.
- 연출 완료를 Core 규칙이 기다리는 것. 기다림은 View Flow가 맡는다.
- 새 Runner·실행 프레임워크.
