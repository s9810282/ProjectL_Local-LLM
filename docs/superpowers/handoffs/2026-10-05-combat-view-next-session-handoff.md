## 2. 시작할 때 유지할 상태

- 기본 View 0~E2·A2/B3와 문서 Phase F는 완료한 범위다. Boot·전투 진입·배치/공격·경로 이동·Return·시간 기반 이동·결과 소비를 다시 구현하지 않는다.
- F1과 정상 F2 기반은 사용자 검증 확인을 인수했다. 일반 승리 → 결과 확인 → EndBattle → StageSelect 호출자도 연결돼 있다. 구체 증거와 한계는 공동 인계 §2를 그대로 따른다.
- 사용자는 완료한 기존 검증을 남은 작업으로 다시 나열하지 말라고 했다. 후속 코드 변경에는 영향받는 회귀를 확인하되, 과거 완료 항목을 일괄 재요청하지 않는다. 빌드·관리 코드 실행·Unity 실행은 구분해 기록한다.
- 개발 fixture Live 성공은 운영 DB 전투 성공이 아니다. `useDevBattle=false`만 켜는 것으로 운영 진입이 완성되지 않는다. 운영 호출자는 유효한 로스터·챕터·대상을 기존 CombatEntry API에 전달해야 한다.
- 문서 인계 완료는 6B 전체, 운영 준비 소스, 재화 분리, 포기·보류한 결과 화면의 완료를 뜻하지 않는다.

## 4. 직전 구조 평가에서 남긴 보완 후보

평가는 정적 코드 검토다. 프레임 저하·GC 수치·목표 규모에서의 병목을 측정했다고 해석하지 않는다. 코드가 길다는 이유만으로 SRP 위반이라고 판정하거나 범용 프레임워크를 추가하지 않는다.

| 후보 / 기존 기준 | 확인된 구조·비용 | 계획을 세울 때의 방향 |
|---|---|---|
| 경로 입력 비용 / X4 | CombatSceneDisplay.TryMapPointer의 PointerEventData 생성·LINQ Any, CombatPathInput.ShowDraft → MovementDraft.Snapshot의 반복 경로 복사 | 입력 데이터 재사용·직접 순회, 같은 초안의 불변 Snapshot 재사용을 우선 검토. 행위자·연결 수명·초안 변경과 포인터 유효성은 구분해 보존 |
| 사건별 전체 갱신 / X4 | SceneDisplay의 사건 처리마다 표시 목록 탐색·RenderFacts 전체 순회 | 대표/최대 규모에서 비용을 확인한 뒤 필요하면 변경 개체 중심 갱신. Core 사건 순서·중간 상태·최종 동기화 유지 |
| ViewSystem 책임 집중 / X1 | 씬 수명·결과 후처리와 입력별 분배·개발 패널·Completion 연결이 한 클래스에 모임 | 연결과 후처리 순서는 유지. 새 입력 확장 시 내부 입력 분배 객체로 이동할 범위를 검토. 별도 전역 서비스는 만들지 않음 |
| Interaction 변경 범위 / X1 | 배치 Drag·공격 조준·선택/모드·명령 대기가 같은 클래스에 있음 | 배치/공격이 독립적으로 확장될 때 분리. 시작/턴 종료 대기와 재생 상태의 소유자를 중복 생성하지 않음 |
| 표시·연출 경계 / X1·X3 | SceneDisplay가 Presenter 연결 외에 좌표/UI 검사·이동 시간·사건별 표시 상태를 담당. ICombatBattleDisplay는 여러 역할을 합친 계약 | 새 비이동 연출을 붙이기 전에 사건 연출의 분리 범위 검토. 소비자에는 기존 좁은 인터페이스를 우선 전달 |

추천 검토 순서는 경로 입력 반복 비용 → 새 연출 전 SceneDisplay 경계 → 입력 확장 시 ViewSystem/Interaction 분리다. 모두를 한 번에 리팩터링하는 계획은 아니다. 문서의 입력 경로 LINQ·반복 할당 억제 원칙이 현재 코드에서 모두 충족된 것으로 표시하지 않는다.

관련 코드는 `Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/ViewSystem/Combat/`와 `ViewSystem/StageInput/MovementDraft.cs`에서 확인한다. `MovementPath`의 불변 복사는 Core 계약이므로 View 최적화를 위해 Core 계약을 약화시키지 않는다.

## 5. 세션 간 수정 경계

| 영역 | 진행 원칙 |
|---|---|
| View 내부·표시·입력·연출과 해당 테스트 | 새 View 세션의 주 작업 범위. 먼저 변경 파일·기대 동작·회귀 범위를 계획에 명시 |
| CombatFlow·Plan·Job·CombatLifeCycle·ExitSequence·Manager | 골격 소유. View에서 흐름/목적지 정책을 재정의하지 않고 필요한 계약 변경을 골격 측에 인계 |
| Core 생산 코드·Buffer 저장 구조 | 별도 담당. 새 API의 실제 서명·조회 경로·수명을 인수한 뒤 소비자만 연결 |
| GameBootstrap·Factory·공용 입력 계약·씬/DB 에셋 | 교차 변경 가능 파일. 변경 전 다른 세션의 작업 파일과 대조하고 한 세션에서만 편집 |
| FieldCamera·Architecture | 다른 작업자 영역. 이번 View 작업에서 변경하지 않음 |
| View 계획·설계·현재 UML | 실제 View 변경에 맞춰 갱신. 골격 원본·Core 요청 변경은 담당 세션과 범위를 맞춤 |

같은 체크아웃을 여는 두 세션의 로컬 변경은 즉시 공유된다. 동시에 같은 파일을 편집하지 않는다. 다른 작업이 진행 중이면 작업 트리와 예정 파일을 먼저 확인하고, 분리가 필요한 경우에만 별도 작업 공간을 사용한다. 세션마다 Runtime·Runner·오류 경계를 새로 만들지 않는다.

커밋·push·외부 메시지 전달은 사용자가 한다. 새 세션 첫 응답은 현재 차이와 진행 가능한 범위 확인이며, 이 인계만으로 구조 변경이나 Core 대기 기능 전체 구현을 승인받은 것으로 해석하지 않는다. 사용자가 구체 작업을 지시하면 그 범위에서 진행한다.

```text
전투 View 후속 작업은 이 세션에서 진행할 거야.

기본 View와 골격 7·View F는 완료된 범위이므로 다시 구현하거나 기존 완료 검증을 미완료로 되돌리지 마.
포기 API·T1/G7·재화 분리는 Core 실제 구현 인수 대기이고, 패배·최종 승리 목적지는 보류야.
우선 Core 없이 가능한 View 보완 후보를 X1·X3·X4에 맞춰 검토해서 작은 Phase 단위의 설계·구현 계획을 세워줘.
각 Phase의 수정 파일·유지할 계약·기대 효과·변경에 필요한 검증을 적고, Core/골격 변경이 필요한 부분은 분리해줘.
커밋·push는 하지 마.
```

Core 구현이 먼저 도착했다면 시작 문구의 보완 계획 대신 인수할 커밋과 대상 작업을 지정한다. 그 경우에도 세 Core 요청을 한 묶음으로 완료 가정하지 않고 실제로 제공된 계약부터 연결한다.

## 7. 작업 결과를 이쪽에 인계할 때

작업 기준 HEAD, 수정 파일·공개 계약 영향, 완료한 Phase, 실제 검증과 미확인 사항, 남은 의존성을 요약한다. 사용자가 커밋했다면 커밋 ID도 함께 전달한다. View 계획 §7에 실행 결과를 남기고 구조가 바뀌었으면 설계·UML을 맞춘다. 골격 정책·Core 규칙이 바뀌지 않았다면 그 원본 문서를 복제해 갱신하지 않는다.
