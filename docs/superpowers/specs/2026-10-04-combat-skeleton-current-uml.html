두 Tick은 역할이 다릅니다

Manager → LifeCycleBase.Tick → OnTick은 활성 Flow를 실행합니다. CombatLifeCycle의 명시적 ISystemTick은 비활성 상태에서도 진입 결과만 확인합니다.

요청 객체가 결과를 연결합니다

LifeCycle과 Job이 같은 요청을 참조합니다. Job은 결과를 쓰고 LifeCycle은 활성화 단계를 변경합니다. 호출자는 읽기 전용 핸들을 보관합니다.

UML / CLASS

Plan · Job · Core

Plan은 Job을 구성하고, Runner는 IJobService.Execute만 실행합니다.

100%
─▷ 상속┄▷ 인터페이스 구현◆ 수명 소유─→ 사용·호출┄→ 의존·반환 (도표별 문맥)

Job의 공통 부모 클래스는 없습니다

네 Job은 각각 IJobService를 구현한 struct입니다. CombatPlan이 반환하는 목록 타입은 List<IJobService>입니다.

Priority가 진행 절차를 정하지 않습니다

현재 Combat Job은 전부 Priority 0입니다. 먼저 할 작업은 Flow/LifeCycle의 등록 조건이 결정하며, Runner는 이미 등록된 작업을 실행합니다.

정상 반환과 행동 수락은 다릅니다

세 처리 API가 false를 반환해도 Job은 완료합니다. 서비스 예외는 전파하고 미완료로 남깁니다. 명시적 진입의 정상 거절도 결과를 남기고 Job을 완료합니다.

UML / SEQUENCE

진입 시퀀스

진입 요청 → Core 수락 → Job 완료 → 씬 활성화 → 최초 표시·입력 순서입니다.

100%
─▷ 상속┄▷ 인터페이스 구현◆ 수명 소유─→ 사용·호출┄→ 의존·반환 (도표별 문맥)

HasBattle만으로 활성화하지 않습니다

이번 요청의 Accepted, Job 완료, Runner Idle, Current 대상 일치를 확인합니다. 보존된 CombatResult나 결과 순번은 진입 성공 신호가 아닙니다.

이 다이어그램은 정상 수락 경로 중심입니다

거절·취소는 씬 전환 없이 종료합니다. 이미 수락된 요청의 활성화가 실패해도 Core 재준비·자동 재시도·임의 reset은 하지 않습니다.

UML / SEQUENCE

프레임 시퀀스

Runner가 실행하고, View가 결과를 소비한 뒤, Flow가 다음 처리를 판단합니다.

100%
─▷ 상속┄▷ 인터페이스 구현◆ 수명 소유─→ 사용·호출┄→ 의존·반환 (도표별 문맥)

등록과 실행은 별도 단계입니다

LifeCycle은 Global 뒤에 Tick하므로 Flow가 등록한 Job은 보통 다음 Runtime Tick의 Global Runner에서 실행됩니다.

한 Tick에서 조건을 다시 읽습니다

View가 같은 Tick 앞쪽에서 오류를 보고할 수 있습니다. Flow도 공유 F1을 읽어 뒤쪽의 새 등록을 막습니다. 새 오류 상태를 복제하지 않습니다.

UML / STATE

요청 상태 전이

이 상태는 진입 요청의 수명이며 Core의 PlayerInput·Automatic·Finished 국면과 다릅니다.

100%
─▷ 상속┄▷ 인터페이스 구현◆ 수명 소유─→ 사용·호출┄→ 의존·반환 (도표별 문맥)

취소 가능한 구간은 실행 전입니다

공개 API가 반환한 Queued 요청만 취소할 수 있습니다. 다른 대상으로 바꾸려면 취소 Job이 배출된 뒤 새 요청을 만듭니다.

정상 거절은 전역 오류가 아닙니다

거절 결과는 요청 핸들에 남고 런타임은 계속 Tick할 수 있습니다. 반대로 Faulted 이후에는 기존 F1 정책을 따릅니다.

Flow.Tick의 실제 판단 순서

코드 시점 요약입니다. 설계 정책의 원본은 골격 설계 §4.1입니다.

  1. 공유 F1 오류, Flow Stop, Runner Busy면 반환합니다.
  2. 대기 중인 처리가 있으면 번호·결과를 확인합니다. 불일치는 한 번 기록하고 Flow를 멈춥니다.
  3. 전투가 없거나 RecordInputOnly면 반환합니다.
  4. PlayerInput에서 연출 확인이 끝났고 명령이 있으면 Command를 등록합니다.
  5. 같은 국면에서 새 미리보기가 있으면 Preview를 등록합니다. 일반 연출 대기 중에도 가능합니다.
  6. 연출 확인이 끝나지 않았으면 반환합니다.
  7. Automatic이면 Advance를 등록합니다. PlayerInput 대기·Finished·None이면 등록하지 않습니다.

수명과 후속 범위

  • 진입 수락 / Job 완료 / 씬 활성화 / 최초 그리기는 서로 다른 시점입니다.
  • RecordInputOnly도 실제 EnterBattle로 준비합니다. 활성화 뒤 처리 Job 등록만 차단하며 View Tick과 입력 기록은 유지합니다.
  • F1: 예외 Job은 미완료로 보존됩니다. Bootstrap이 다음 Runtime Tick을 중단하며 Flow도 같은 오류 상태를 읽습니다.
  • F2 후속: 현재 OnExit는 Flow.Stop → 입력 Clear → 요청 Close입니다. 진행 중 Job을 기다리거나 EndBattle을 호출하는 안전한 이탈 경계는 아직 연결하지 않았습니다.
  • 운영 DB 후속: 기본 source의 T1/G7 조립은 별도입니다. 개발 fixture 동작을 운영 전투 준비 성공으로 보지 않습니다.
