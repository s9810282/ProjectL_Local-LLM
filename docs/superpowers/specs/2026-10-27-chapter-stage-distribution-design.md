# 챕터 스테이지 분포 — 최소 개수 보장과 SO 가중치 설계

날짜: 2026-10-27
상태: 설계 초안. 사용자 선택은 §1에 기록하며, 세부 구현 제안과 구분한다. 코드·SO·씬 변경 없음.
추가(2026-11-03): §13 층 최소 폭·종류별 출현 시작 깊이 설계. Q-MS1~Q-MS6 모두 A로 결정(사용자). Task는 [계획 §12](../plans/2026-10-27-chapter-stage-distribution-plan.md), 코드 변경 없음.
범위: 챕터 그래프의 스테이지 배정, 기획 입력 SO, DB → Core 변환, 관련 검증. Task 계획은 이 설계 검토 뒤 별도로 작성한다.

## 1. 요구와 결정

사용자가 요청한 내용:

- 기획자가 SO에서 특수 스테이지의 출현 가중치를 조정할 수 있게 한다.
- 챕터당 상점과 회복 스테이지가 각각 최소 한 번은 등장해야 한다.
- 제시한 두 방식 중 **최소 개수 보장 + 나머지 노드는 종류별 가중치 추첨**을 선택했다.

보장 단위는 **생성된 챕터 맵 전체의 노드 수**다. 모든 노드는 시작점에서 도달 가능해야 하지만, 플레이어가 고르는 모든 경로에 상점과 회복이 하나씩 있다는 뜻은 아니다. 서로 다른 분기에 배치될 수 있다. 모든 경로에서의 방문 보장, 연속 등장 제한, 출현 깊이·간격 지정은 이번 범위 밖이다.

아래는 요구를 구체화하기 위한 작성자 제안이며, 사용자가 각각 별도로 확정한 정책은 아니다:

- 일반 상점과 강화를 별도 종류로 취급한다. 강화 노드로 일반 상점 최소 개수를 채우지 않는다.
- 기획자가 종류별 상대 가중치와 최소 개수를 조정한다. 운영 맵에서는 일반 상점·회복 최소 개수가 각각 1 이상이어야 한다.
- 일반 전투·강화의 최소 개수 기본값은 0이다. 추가 보장이 필요하면 SO에서 올릴 수 있다.
- 배치할 자리가 부족한 설정은 생성 전에 오류로 거절한다. 맵 크기를 몰래 늘리거나 보장을 줄이지 않는다.
- 기존 시드의 과거 맵 모양을 그대로 보존하지 않는다. 새 알고리즘 안에서의 재현성과 종류 비중 변경 시 길 구조 보존을 보장한다.

## 3. 검토한 방식

| 방식 | 효과와 비용 | 판단 |
|---|---|---|
| 개별 StageRoot에 가중치만 추가 | 변경은 작지만 상점·회복이 0개일 수 있고 전투 후보 수가 전체 비율에 영향을 준다 | 요구를 충족하지 못함 |
| 최소 개수 확보 후 나머지 종류를 가중치 추첨 | 반드시 필요한 노드를 확보하면서 맵별 변화를 유지한다. 종류 안에서는 키를 균등 추첨한다 | **사용자 선택** |
| 모든 종류의 개수·비율을 먼저 할당 | 맵마다 분포가 더 일정하지만 작은 맵의 반올림·잔여량 정책이 필요하다 | 이번에는 선택하지 않음 |

가중치는 맵 전체의 정확한 최종 비율이 아니다. 최소 배치가 먼저 들어가므로 **최소 배치 후 남은 자리의 확률**이다.

## 4. 기획자가 편집하는 SO

기존 `StageMapDataSO`에 `스테이지 출현 설정` 영역을 추가한다. 별도 Database Table, 서비스, Bootstrap은 만들지 않는다. 일반 전투·일반 상점·회복·강화 네 항목을 고정으로 표시하며 각 항목은 `weight`와 `minimumCount`를 가진다. 중복 종류 행을 만들 수 있는 자유 목록 UI는 필요하지 않다.

| 항목 | 가중치 예시 | 최소 개수 기본 제안 | 의미 |
|---|---:|---:|---|
| 일반 전투 | 70 | 0 | 보스가 아닌 전투 |
| 일반 상점 | 10 | 1 | ShopStageDetail만 해당 |
| 회복 | 10 | 1 | 현재 EventStageDetail |
| 강화 | 10 | 0 | EnhancementStageDetail |

70:10:10:10은 사용법 설명용 시작 제안이며 확정된 밸런스가 아니다. 실제 운영 에셋에 적용할 값은 구현 시 기획 확인 사항으로 남긴다. 최소 개수 기본 제안은 위와 같고, 상점·회복의 운영 하한 1은 사용자 요구를 따른다.

- 정수 가중치 범위는 `0..10000`, 최소 개수는 0 이상. 상점·회복의 운영 하한은 1이다.
- 합계 100을 요구하지 않는다. 7:1:1:1과 70:10:10:10은 같은 확률이다.
- `weight = 0`: 남은 자리 추첨에서 제외한다. `minimumCount > 0`이면 최소 개수는 여전히 배치된다. 예: 상점 0/1은 상점 정확히 1개다.
- `weight = 0`, `minimumCount = 0`: 그 종류를 생성하지 않는다. 따라서 운영 맵의 상점·회복에는 이 설정을 허용하지 않는다.
- 활성 종류에 해당하는 실제 스테이지 후보가 없으면 오류다. 빈 풀을 조용히 제거하고 다른 종류에 확률을 나누지 않는다.
- 모든 종류의 가중치가 0인 설정은 거절한다. 남은 자리를 채울 종류를 반드시 정하게 한다.
- 최소 개수 합계는 `DepthCount - 2` 이하여야 한다. 이유와 작은 맵 제한은 §6을 따른다.

Inspector Tooltip에 `남은 자리의 상대 가중치`, `챕터 맵 전체 최소 개수`, `가중치 0도 최소 배치에는 영향 없음`, `모든 경로의 방문을 보장하지 않음`을 표시한다. 커스텀 Editor나 분포 시각화 도구는 이번 필수 범위가 아니다.

`GetData()`는 매번 새 순수 불변 정책 값을 만든다. 직렬화용 입력 객체·배열 참조를 그대로 전달하지 않는다. 런타임 DB는 초기화 때 값을 읽으므로 Inspector 수정의 즉시 반영을 약속하지 않는다. 에셋 조정 후 새 실행·새 챕터 생성으로 확인한다.

## 5. 계약과 소유권

### 5.1 최소 계약

구체 이름은 구현 계획에서 조정 가능하지만 다음 책임은 유지한다.

- Core Contracts에 생성용 종류 `ChapterStageKind { Combat = 1, Shop = 2, Recovery = 3, Enhancement = 4 }`를 둔다. 실행 흐름용 `StageType`을 대체하지 않는다.
- 순수 불변 `ChapterStageDistributionRule(Kind, Weight, MinimumCount)`를 둔다. 범위·열거 검증을 맡는다.
- 순수 불변 `ChapterStagePool(Rule, StageKeys)`을 둔다. 후보 키를 복사하고 읽기 전용으로 제공한다.
- `StageMapData`는 네 종류의 정책만 소유한다. 스테이지 후보 목록을 SO에 다시 등록하지 않는다.
- `ChapterGraphSpec`은 기존 `RegularStageKeys` 대신 종류별 풀을 받는다. 정책과 키의 결합은 이 입력에 한 번만 존재하며, 별도 가변 캐시를 두지 않는다.
- 종류 순서는 enum 값 오름차순, 후보 키는 숫자 오름차순으로 정규화한다. 같은 종류가 두 풀에 나오거나 키가 풀 사이·풀 안에서 중복되거나 보스 키가 일반 풀에 포함되면 거절한다.
- 후보가 비어 있는 풀은 가중치와 최소 개수가 모두 0인 경우만 허용한다. 활성 풀은 하나 이상의 키가 필요하다.

`ChapterGraphSpec`의 공개 생성자 변경은 실제 호출처와 함께 갱신한다. 현재 확인한 직접 구성 파일은 `StageGeneratorSystem`, `ChapterGraphGeneratorTests`, `EnhancementStageRegistrationTests`다. 구현 착수 시 다시 검색한다. 과거 균등 추첨을 유지하는 숨은 null 분기나 구형 생성 경로는 추가하지 않는다. 키 목록을 중복시켜 확률을 표현하던 계약도 새 풀의 중복 금지로 대체한다.

순수 생성기는 상점·회복의 게임 정책을 하드코딩하지 않고 입력 최소 개수를 지킨다. **운영 상점·회복 최소 1 정책은 StageMapData.Validate 한 곳**에서 검사한다. Core 단위 시험은 최소 개수가 모두 0인 단순 입력이나 깊이 2 그래프를 계속 구성할 수 있다. 운영 SO에서 깊이 2를 쓰면 최소 보장 조건과 충돌하므로 거절된다.

### 5.2 DB → Core 변환

`StageGeneratorSystem.PrepareGraph`가 기존 MapKey 필터 뒤 다음 매핑을 한 곳에서 수행한다.

| DB 상세 | 생성용 종류 |
|---|---|
| CombatStageDetail + Regular | Combat |
| ShopStageDetail + Regular | Shop |
| EventStageDetail + Regular | Recovery |
| EnhancementStageDetail + Regular | Enhancement |
| Boss 역할 | 일반 풀에서 제외하고 기존 보스 슬롯으로 전달 |

후보 분류를 위해 `StageRootDataSO`에 종류를 하나 더 입력하게 하지 않는다. 실제 상세와 생성 종류가 어긋나는 두 원본을 만들지 않는다. 위 네 상세 외의 Regular 타입은 MapKey·StageKey·상세 타입을 포함한 오류로 거절하고, 새 종류가 추가될 때 이 매핑과 정책을 명시적으로 확장한다.

어댑터는 분류·검증·입력 변환만 한다. 최소 개수 배치, 확률 계산, 추첨은 Core 생성기가 맡는다. 출력은 기존 `ChapterGraphNode` → `StageProgressData` 변환을 그대로 사용하며, Buffer 형식과 View의 노드 표시 계약은 바꾸지 않는다.

### 5.3 게시와 수명

- SO는 기획 설정 원본, ChapterGraphSpec은 생성 시점의 읽기 입력, 게시된 StageProgressData는 현재 챕터 그래프 사실이다.
- 생성 중간 상태·배치 수량은 호출 내부 지역 값이다. 다른 Run·챕터와 공유하지 않는다.
- `PrepareGraph`는 그래프를 반환할 뿐 Buffer에 쓰지 않는다. 기존 챕터 진입·계속의 합동 게시 경계를 유지한다.
- 잘못된 정책이나 후보 누락은 게시 전에 예외로 거절한다. 오류에 MapKey·종류·필요 개수 또는 문제 값을 포함한다. 기존 진행 상태를 부분 수정하거나 임의 설정으로 재시도하지 않는다.
- 이미 생성·게시된 챕터를 SO 변경 때문에 다시 만들지 않는다. 새로 생성되는 챕터부터 적용한다. 진행 중 맵의 마이그레이션은 범위 밖이다.

## 6. 생성 알고리즘

### 6.1 생성 전 검증과 용량

기존 그래프의 중간 층 수를 `L = DepthCount - 2`로 둔다. 각 중간 층의 폭이 최소 1이므로 일반 노드 수 `N`은 항상 `L <= N <= L * WidthMax`다.

최소 개수 합계 `M`에 **`M <= L`**을 요구한다. 그러면 어떤 시드가 폭을 선택해도 최소 배치가 가능하다. 예: 현재 Chapter1은 L=5이므로 상점 1 + 회복 1을 항상 넣을 수 있다.

이는 의도적으로 보수적인 제약이다. 깊이 3·최대 폭 3인 맵은 운 좋게 자리가 3개 나올 수 있지만, 최소 폭에서는 1개뿐이므로 상점·회복 두 개 보장 설정을 거절한다. 폭을 강제로 늘리거나 성공할 때까지 재생성하는 정책은 도입하지 않는다. 기획자는 깊이를 늘리거나 상점·회복 하한을 제외한 추가 최소 개수를 줄인다.

검증 책임은 구분한다. Rule은 값 범위, StageMapData는 운영 최소 하한·설정 간 용량, ChapterGraphSpec은 순수 입력의 용량·풀/키 일관성, 어댑터는 실제 DB 후보 대응을 확인한다. DB 경로를 거치지 않는 Core 호출도 안전해야 하므로 입력 유효성 검사는 Core에 남긴다.

### 6.2 처리 순서

1. 시작 노드 하나, 기존 방식으로 선택한 중간 층 폭, 마지막 보스 노드 하나를 만든다. 이 단계에서는 일반 노드에 스테이지 키를 배정하지 않는다.
2. 기존 `Connect` 규칙으로 연결을 완성한다. 시작점 → 각 중간 노드 → 보스 도달 가능성과 다음 층 연결을 유지한다.
3. 일반 노드 ID를 오름차순으로 수집하고, 복사한 슬롯 목록을 Fisher–Yates로 섞는다. 각 종류의 최소 개수만큼 섞인 목록의 앞쪽 슬롯을 차례로 예약한다. 종류 처리 순서는 enum 오름차순이다. 하나의 슬롯은 한 종류에만 배정한다.
4. 예약되지 않은 노드를 ID 오름차순으로 방문한다. 양수 가중치의 총합 W에 대해 `Random.Next(W)`를 한 번 호출하고 누적 구간으로 종류를 고른다. 가중치 0 종류는 제외한다.
5. 모든 일반 노드를 ID 오름차순으로 방문해 선택된 종류의 StageKeys에서 균등하게 하나를 뽑는다. 같은 StageKey의 여러 노드 등장과 같은 종류 연속 등장은 허용한다. 후보 개수보다 최소 개수가 커도 키를 재사용할 수 있다.
6. 모든 슬롯이 채워졌는지와 종류별 최소 개수를 확인하고 기존 불변 ChapterGraphNode 목록으로 반환한다. 검증 실패를 다른 스테이지로 덮어쓰는 보정은 하지 않는다.

최소 배치는 반드시 서로 다른 노드를 사용하지만 서로 다른 깊이를 요구하지 않는다. 두 분기의 같은 깊이에 상점과 회복이 놓일 수 있다. 시작·보스 노드는 예약과 가중치 추첨 대상이 아니다.

### 6.3 확률의 의미

최소 배치 뒤 남는 자리는 `R = N - M`이다. 종류 g의 기대 개수는 다음과 같다.

`E[count(g) | N] = minimum(g) + R * weight(g) / W`

예: 일반 노드 10개, 상점·회복 최소 1개씩, 가중치 70:10:10:10이면 기대 개수는 전투 5.6, 상점 1.8, 회복 1.8, 강화 0.8이다. 실제 한 맵의 개수는 정수이며 이 기대값과 다를 수 있다. 강화가 0개인 맵도 정상이다.

같은 종류에 전투 에셋을 추가해도 종류 추첨 확률과 최소 개수는 바뀌지 않는다. 해당 종류 안에서 개별 StageKey를 고르는 확률만 달라진다. 개별 스테이지 가중치는 이번에 추가하지 않는다.

### 6.4 난수와 재현성

현재 코드는 하나의 Random으로 폭·스테이지·연결을 순서대로 뽑는다. 이 상태에서 추첨 횟수를 늘리면 가중치 작업이 길 구조까지 바꿀 수 있다. 새 구조에서는 호출별로 다음 세 Random을 만들어 수명을 분리한다.

- topology: `new Random(spec.Seed)` — 층 폭과 기존 연결 선택 전용.
- distribution: `new Random(unchecked(spec.Seed ^ 0x5F3759DF))` — 최소 자리 셔플과 나머지 종류 선택 전용.
- stageKey: `new Random(unchecked(spec.Seed ^ 0x6C8E9CF5))` — 종류 안의 구체 StageKey 선택 전용.

상수는 구현 제안이며 도입 후 테스트로 고정한다. 별도 난수 서비스·전역 저장소·범용 스트림 프레임워크를 만들지 않는다.

- 같은 정규화 입력·시드·같은 Unity/.NET 실행 환경이면 결과가 같다.
- 가중치·최소 개수·후보만 바꾸고 깊이·폭·연결·시드를 유지하면 노드 ID·깊이·폭·연결이 같다.
- 같은 종류의 후보만 추가하면 종류별 배치도 같고, 그 종류의 구체 StageKey만 달라질 수 있다.
- DB 목록의 순서 변경은 정규화 뒤 결과에 영향을 주지 않는다.
- 구버전 알고리즘과 동일 시드의 결과 일치, 서로 다른 .NET 구현 사이의 난수 결과 일치는 보장하지 않는다.
- `RandomizeSeedEachRun`은 현재 어댑터의 시드 확정 방식을 유지한다. `Environment.TickCount`의 실제 호출 단위와 저장·복원 정책을 이번에 바꾸지 않는다.

## 9. 검증 계획

### 9.1 Core EditMode — 생성 규칙

`T/ChapterGraphGeneratorTests.cs`의 기존 연결·불변 입력·동일 시드 시험을 유지하고 다음을 추가한다.

1. 여러 고정 seed와 Nearest/Random/WeightedRandom 연결 모드에서 상점·회복 최소 개수가 항상 충족된다. 시작·보스는 계산에서 제외한다.
2. 최소 개수 합계가 L인 경우와 L을 초과하는 경우, 중간 층 0개인 순수 입력을 확인한다. 초과는 생성 전 거절한다.
3. 가중치 0 + 최소 1은 정확히 1개, 0 + 최소 0은 0개다. 나머지 가중치가 하나만 양수이면 남은 자리는 모두 그 종류다.
4. 음수·상한 초과 가중치, 모든 가중치 0, 음수 최소, 알 수 없는 종류, 중복 종류/키, 보스 키 혼입, 활성 빈 풀을 거절한다. 비활성 빈 풀은 허용한다.
5. 생성 후 모든 일반 키가 해당 풀에 속하고 모든 노드가 시작에서 도달 가능하며 보스로 이어진다. ID·Edge 중복, 이전/같은 층 연결이 없다.
6. 입력 배열 변경이 결과 설정을 바꾸지 않는다. 같은 입력·seed는 전체 그래프가 같고, 풀/후보 순서만 바꿔도 결과가 같다.
7. 가중치·최소 개수 변경 전후 topology 서명이 같다. 전투 후보 수만 늘려도 종류 배치 서명이 같다.
8. 가중치 1:3 등 통제된 설정에서 최소 배치를 제외한 잔여 노드만 집계한다. 고정 seed 집합과 충분한 표본·넉넉한 허용 범위로 비율을 확인한다. 한 맵의 정확한 비율을 요구하지 않는다. 구현 계획에 seed 범위·표본 수·허용 오차를 고정한다.

### 9.2 DB·어댑터·게시 통합 EditMode

이번 기능은 SO와 Systems 어댑터를 바꾸므로 **Core 시험만으로 완료 판정하지 않는다.** 필요한 시험은 Framework 어셈블리 안에도 있다. 앞선 넉백 계획의 Core 전용 검증 제한은 이 설계에 가져오지 않는다.

- SO → GetData → Query → StageGeneratorSystem → Core → StageProgressData까지 가중치·최소 개수가 전달되는지 확인한다.
- 일반 상점과 강화가 같은 StageType이어도 다른 풀로 분류되는지, 강화만으로 상점 최소 개수를 충족하지 못하는지 확인한다.
- 후보 누락·설정 오류에서 PrepareGraph/챕터 진입이 실패하고 Map/Stage/Current/Run Buffer 사실이 변경되지 않는지 확인한다.
- `ChapterGraphPreparationTests`의 준비 시 미게시와 정상 진입 시 게시 계약을 유지한다. 다음 챕터 생성 경로에도 동일 정책이 적용되는 대표 사례를 검증한다.
- 실제 Catalog 기준 `DataBaseAssetTests`, `EnhancementStageRegistrationTests`와 관련 맵 정책 시험을 실행한다. 에셋 설정 누락·참조 누락을 확인한다.
- 기존 Framework 전체 회귀가 프로젝트 필수라면 유지한다. 실패는 기존 기준선과 비교하며, 관련 없는 테스트를 이 기능에서 임의로 고치지 않는다.

### 9.3 Unity 확인

- Editor 임포트·컴파일과 Inspector 표시/저장/재로드를 확인한다.
- 가중치·최소 개수 변경 후 새 Run/새 챕터에서 실제 맵을 확인한다. 상점·회복 각각의 노드가 표시되고 해당 종류로 진입하는지 대표 사례를 재생한다.
- 진행 중인 기존 그래프는 설정 수정만으로 바뀌지 않는지 확인한다.
- Core 논리, SO 전달, Unity 재생 결과를 나눠 기록한다. 이 설계 작성에서는 시험을 실행하지 않았다.

## 10. 구조 기준 점검과 전후 차이

| 대표 변경 | 현재 부담 | 설계 후 | 남는 필수 경계 |
|---|---|---|---|
| 상점 출현 비중 조정 | 균등 후보 개수에 의존해 다른 종류 에셋 수까지 고려해야 함 | 해당 맵 SO의 상점 weight만 조정 | 최소 보장으로 인해 최종 비율과 잔여 추첨 비율이 다름 |
| 일반 전투 에셋 추가 | 상점·회복·강화의 상대 출현 비중도 바뀜 | 전투 풀 안의 선택지만 늘어남 | 실제 StageRoot 등록·유효성 검증 |
| 상점·회복 최소 개수 조정 | 보장 기능 없음 | SO minimumCount와 용량 검증으로 조정 | 맵 전체 보장, 경로별 보장은 아님 |

- **수정 범위:** 정책·배정·어댑터·관련 시험에 머문다. 노드 표시나 상점 구매·회복 계산 구현을 수정하지 않는다.
- **이해 범위:** 배정 변경자는 풀·가중치·최소·시드·연결 불변식만 이해하면 된다. 회복량·상품 가격·강화 적용 내부는 읽지 않아도 된다. 상세 종류 매핑은 어댑터 한 곳에 있다.
- **검증 범위:** 최소 개수·분포·연결·재현성·SO 전달·게시 원자성은 실제 영향 경계이므로 필요하다. 무관한 전투 피해·카메라 내부 검증은 이 기능의 증거가 아니다.
- **SSOT:** 설정은 맵 SO, 스테이지 분류 근거는 기존 상세, 배정 규칙은 Core, 생성 후 진행 사실은 Buffer다. 후보 목록이나 실행 종류를 입력 계층에 중복 등록하지 않는다.
- **SRP:** SO 입력, 어댑터 변환, Core 생성, Buffer 게시 책임을 유지한다. 생성기 내부의 topology/배정 함수 분리는 각 변경의 난수·이해 범위를 줄이는 데 목적이 있다.
- **OCP:** 기존 네 종류의 수치 조정과 같은 종류 후보 추가는 코드 변경이 없다. 새로운 게임 종류를 만들 때 매핑·정책을 명시적으로 확장하는 것은 정상 변경이다. 범용 플러그인 구조는 만들지 않는다.
- **LSP:** IStageGeneratorSystem.PrepareGraph는 계속 부작용 없는 준비 계약을 지킨다. ChapterGraphSpec 입력 계약 변경은 호출처 이전으로 다루며 무조건적인 하위 호환을 주장하지 않는다.
- **ISP/DIP:** Core는 DB/SO·Unity 타입이나 서비스 조회를 모르고 순수 계약만 받는다. View는 생성 정책을 조회하지 않고 기존 Buffer 결과만 읽는다.
- **FW:** 서비스 등록·AddModule·Builder·초기화·종료 구조를 바꾸지 않는다. 정책 값을 넘기기 위해 전역 서비스나 Buffer 저장소를 새로 만들지 않는다.

### 13.4 설계 (권장안 기준)

**MS1 층 최소 폭.** `ChapterGraphSpec`에 `WidthMin`(1 ≤ `WidthMin` ≤ `WidthMax`)을 더한다. 층 폭은 `random.Next(WidthMax - WidthMin + 1) + WidthMin`으로 뽑는다. 모양 난수를 부르는 횟수는 같고, `WidthMin = 1`이면 지금 식과 같은 값이 나온다.

**MS2 출현 시작 깊이.** `ChapterStageDistributionRule`에 `MinDepth`(1 이상)를 더한다. 그 종류는 깊이가 `MinDepth` 이상인 중간 노드에만 놓인다. 끝 깊이는 두지 않는다. 생성기는 Pin 말고는 이 규칙을 어기는 보정을 하지 않는다.

**MS3 자리 검사는 한 함수.** `RequiredSlots`를 자리 검사 함수 하나(가칭 `ChapterStageDistributionRule.FindPlacementError(rules, middleDepths, widthMin, pinnedKind)`, 문제가 없으면 null)로 바꾼다. `StageMapData.Validate`·`ChapterGraphSpec` 생성자·SO 모드 도구(Spec을 만들어 판정)가 모두 이 함수 하나를 거친다.

검사 내용(L = 중간 층 수):

1. 활성 종류의 `MinDepth`는 L 이하다. 더 깊으면 나올 수 없는 설정이라 거절한다.
2. 깊이 1에 놓일 수 있는 가중치 양수 종류가 하나 이상 있다(`MinDepth = 1`이고 `Weight > 0`). 그래야 모든 깊이의 남은 자리를 채울 수 있다.
3. 깊이 d = 1..L마다, 그 깊이 이상에만 놓일 수 있는 최소 배치가 보장된 자리 안에 들어간다.
   - 보장된 자리 = `WidthMin × (L − d + 1)`(층마다 최소 폭만 나온 최악의 경우).
   - 필요한 자리 = `MinDepth ≥ d`인 종류의 최소 개수 합 + Pin 보정.
   - Pin 보정: 고정 노드가 있으면 1을 더한다. 단, 고정 종류의 `MinDepth ≥ d`이고 그 최소 개수가 1 이상이면 그 종류 최소 개수에서 하나를 빼 상쇄한다. 고정 노드가 어느 깊이에 생기든 성립하는 최악의 값이다.
   - d = 1이고 모든 `MinDepth = 1`, `WidthMin = 1`이면 지금 검사(`1 + 최소 합 − 고정 종류 1 ≤ L`)와 같다.

허용할 수 있는 시작 깊이 집합이 "깊이 d 이상"처럼 안쪽으로 포개지므로, 3을 통과하면 실제 그래프(층 폭이 `WidthMin` 이상)에서 MS4 배정이 늘 성공한다.

**MS4 배정 순서.**

1. 섞기는 지금 그대로다(고정 노드 밖 모든 중간 노드, 분포 난수).
2. 최소 배치는 **시작 깊이가 깊은 종류부터**(같으면 종류 오름차순) 한다. 각 종류는 섞인 순서에서 아직 비어 있고 깊이가 `MinDepth` 이상인 자리를 앞에서부터 가져간다. 가장 좁은 종류가 먼저 고르므로 넓은 종류가 좁은 종류의 자리를 빼앗지 않는다.
3. 남은 자리는 지금처럼 노드 ID 순서로 자리마다 `Next(W_d)`를 한 번 부른다. `W_d`는 그 깊이에 놓일 수 있는(`MinDepth ≤ 깊이`) 종류의 가중치 합이고, 누적 순서는 종류 오름차순이다.
4. 키 추첨·최소 개수 확인(`EnsureMinimums`)은 지금 그대로다. 확인 실패는 검사와 생성이 어긋났다는 뜻이라 예외로 둔다.

**MS5 지금 맵 보존.** `WidthMin = 1`이고 모든 `MinDepth = 1`이면 같은 시드에서 지금과 같은 그래프가 나온다. 모양은 MS1, 최소 배치 순서는 종류 오름차순으로 같고, 남은 자리의 `W_d`는 전체 합과 같다. 기존 시험에는 고정 시드의 결과를 정답으로 박아 둔 것이 없으므로(같은 입력을 두 번 생성해 비교할 뿐), 바꾸기 전에 지금 생성기로 고정 시드 그래프 서명을 기록하는 시험을 먼저 넣고, 바꾼 뒤 기본값에서 그 시험이 그대로 통과하는 것을 보존의 증거로 삼는다(계획 §12 MS-a T0). 난수를 셋으로 나눈 규칙(§6.4)도 그대로 지켜진다. 시작 깊이를 바꿔도 맵 모양은 같고, 최소 폭을 바꾸면 모양이 바뀐다.

**MS6 고정 노드.** Q-MS4 A대로 시작 깊이를 보지 않고, 자기 종류 최소 개수에 든다. 자리 검사는 MS3의 Pin 보정으로 미리 막는다.

### 13.6 검증

Unity Test Runner로 `ProjectL.Tests.Core`·`ProjectL.Tests.CoreIntegration`를 돌린다.

1. 바꾸기 전에 넣은 고정 시드 서명 시험이 기본값(`WidthMin` 1, `MinDepth` 1)에서 그대로 통과한다(MS5).
2. `WidthMin`: 여러 시드에서 모든 중간 층 폭이 최소~최대 안이다. `WidthMin > WidthMax`, `WidthMin < 1`은 거절한다. `WidthMin = WidthMax`면 모든 층 폭이 같다.
3. `MinDepth`: 여러 시드·세 연결 방식에서 각 종류가 시작 깊이보다 얕은 노드에 없다(고정 노드 제외). 최소 개수는 늘 지켜진다.
4. 자리 검사: 깊이별 경계값(딱 맞음 / 하나 초과), 시작 깊이 > L, 깊이 1에 가중치 양수 종류 없음, 고정 노드 보정(고정 종류 시작 깊이가 d 이상·미만 각각)을 확인한다. Data·Spec이 같은 문구로 거절한다.
5. 남은 자리 추첨: 깊이 1이 전투만 가능한 설정에서 깊이 1 노드는 모두 전투다. 깊이 2 이상에서 가중치 비율은 §9.1-8처럼 넉넉한 범위로 본다.
6. 시작 깊이만 바꾸면 모양 서명이 같다. 최소 폭을 바꾸면 모양이 바뀌어도 연결 불변식(도달 가능·보스로 이어짐)은 지켜진다.
7. CoreIntegration: SO → Data → 어댑터 → 생성까지 두 값이 전달된다.

Unity 확인: Inspector 표시·저장, 새 Run에서 StageSelect 맵 모양(첫 층이 2~3개, 깊이 1에 상점·회복·훈련소 없음), SO 모드 도구가 새 값을 읽고 판정한다.

### 13.7 구조 점검

- **SSOT:** 최소 폭·시작 깊이의 원본은 맵 SO 칸 하나, 배치 판정은 Core 생성기, 자리 검사는 함수 하나(Data·Spec·도구가 부름)다. 도구는 Spec을 만들어 판정하므로 규칙 사본을 갖지 않는다. 단, 도구가 SO 칸을 이름으로 읽는 기존 방식 때문에 칸 이름이 두 곳(SO와 도구 상수)에 있다.
- **SRP:** SO는 입력, Data는 운영 정책 검사, Spec은 순수 입력 검사, 생성기는 배치, 어댑터는 분류·전달이다. 지금 나뉜 그대로다.
- **OCP:** 값 조정은 에셋만 고친다. 깊이 규칙의 종류가 늘면(끝 깊이 등) 자리 검사와 배정 순서를 함께 다시 봐야 한다(Q-MS2 B를 미룬 이유).
- **FW:** 서비스·Buffer·Factory 등록 변화가 없다.
- **바꿀 때 영향:** 다음에 출현 규칙을 바꾸는 사람은 Rule·자리 검사 함수·생성기 `AssignKinds`·SO 칸·도구 읽기 다섯 곳을 본다. 도구 읽기가 빠지면 도구 판정이 게임과 달라진다(지금도 같은 구조).
