## 1. 현재 상태 (코드 대조)

- 작업 전(HEAD `fc98408f`, 2026-10-17) 기준이다. 바뀐 뒤는 C5·C6과 계획 §7이다.

### 1.1 재생 사슬

- **순차 재생 `OrderedCombatPresentation`:**
  - 결과의 사건을 Core 순서대로 하나씩 넘긴다.
  - 진행 중인 사건은 늘 하나다(`_index`·`_started`·`_completed`).
  - 사건 완료 통지를 받아야 다음 사건의 시작 조건(`CanBeginPresentationEvent`)을 본다.
- **사건 Presenter `CombatSceneEventPresenter`:** 사건을 표시한다. 공격·포효·소환·피격/사망 반응·걸음은 각 재생 부품에 맡긴다.
- **겹침을 허용하는 곳은 지금 세 곳뿐이다. 모두 "출처 하나의 남은 연출"과 겹치는 방식이다.**
  - 공격 Gate(`CombatHitGate`, H-2·H-3): 히트 뒤 후속이 공격자의 남은 연출과 겹친다.
  - 걸음 Gate(`CombatStepContactGate`, H-4): 접촉 사건이 남은 보간과 겹친다.
  - 기차 접촉(`CombatRailwayContactPlayback`): 기차 직후의 사망을 순차 재생에서 소비한다(`TryConsumeDeath`). 접촉 시각마다 `BeginConcurrentDeath`로 동시에 시작한다.

### 1.2 "한 번에 하나" 가정이 있는 곳

| 위치 | 가정 | 막히는 경우 |

| `OrderedCombatPresentation` + `CombatMovementPlayback` | 진행 중인 걸음이 하나. 표시의 `IsMovementComplete` 하나를 폴링 | ③ |

### 1.3 이미 유닛별인 것 (그대로 쓴다)

- `CombatUnitReactionSet`: 유닛별 반응 항목(`Dictionary<EntityId, Entry>`)과 수명, 늦은 콜백 무시, 프레임 시작 Version 규칙이 있다.
- 자세 대여·크기 대여(`FieldUnitView`): 유닛마다 배타적이다.
- 표시 사실(`_shownCharacters`)은 유닛별로 갱신한다(`ApplyCharacter`). 전체 다시 그리기(`RenderEvents`)는 대여 중인 자세와 보간 배치를 덮지 않는다(H-4b (a)).

### 1.4 Core가 주는 "같은 순간" 사실

- **피해 근원 열쇠 = (공격 그룹 `CombatDamageOrigin.AttackGroup`, 가해자 `CreditedCharacterId`).** Core는 피해 하나마다 그룹을 붙인다.
  - 한 공격의 직접 피격은 모든 대상이 같은 그룹이다(`AttackDirectDamageCalculator`, `CommandAttackGroups.Direct` + 공격자). 그래서 ShotGun 부채꼴, 곡사 스플래시, 포효 반응 공격 범위, Ballista 관통이 한 열쇠다.
  - 폭발은 폭발 하나가 그룹 하나다. 지뢰 효과 피해는 `ResolveObjectsAt`에서, 화약통 연쇄 폭발은 `ObstacleReactionCalculator`의 폭발마다 그렇다.
  - 반사·광란(Frenzy) 파동은 새 그룹(`AttackGroups.Next()`)이라 다른 순간이다.
  - 가시밭 적용(`ThornFieldApplicationCalculator`)은 칸마다 새 그룹이라, 같은 행동이어도 Core 사실로는 다른 순간이다(§5).
- **사망:** 피해로 생긴 `Died`는 피해와 같은 근원을 갖는다(`CombatCommandCalculator`의 피해 적용이 근원을 넘김 → `CombatCommandEvents.Health`). 근원 없이 기록되는 체력 변화(낙하 사망 `MovementProjection.ApplyFall`, 피해 뒤 아이템 반응, 재생 등)는 묶음 밖이다.
- **넉백 이동:** 근원이 없다. 출처~다음 행동 경계의 이동 후속(`CombatHitFollowUps`, H-2b)이 출처와 대상을 대응한다.
  - Core는 대상마다 경로 전체를 차례로 기록한다(`AttackKnockbackCalculator.Resolve`, 대상 순).
  - 직접 피해가 모두 기록된 뒤에 넉백이 온다.
- **기차:** 발동 직후의 직접 사망 목록(`KilledUnitIds`)이 한 묶음이다. 지금 전용 재생이 처리한다.
- **열쇠 유일성의 전제(C-1 검토 5):** Core `CommandAttackGroups`는 명령마다 번호를 다시 시작한다(Direct = 1, `Next`는 2부터). 그래서 같은 (그룹, 가해자)가 한 결과의 서로 다른 명령에서 다시 나올 수 있다. 묶음은 행동 경계 구간으로 나누므로 섞이지 않는다(확인한 경로: 이동 → 공격, 공격 → 포효, 턴 종료 투영). 시험 `CombatConcurrentGroupsTests.ActionBoundary_CutsTheGroup_EvenWithTheSameKey`가 고정한다.

### 1.5 결론

- 동시 처리를 막는 것은 기능별 코드가 아니라 1.2의 단일 칸 가정이다.
- "같은 순간"은 Core 사실(피해 근원 열쇠·이동 후속 대응)로 충분히 정의된다. **Core 요청은 없다.**
- 바꿀 것은 두 층이다.
  - 순차 재생이 "무엇을 언제 시작할지"를 묶음 단위로 판단한다.
  - 표시가 자원을 유닛별로 판단한다.

- **한다:**

## 3. 결정

### C1. 동시 묶음 — Core 사실로만 정의 (`CombatConcurrentGroups`, 가칭)

- **묶음 열쇠:**
  - 피해 근원을 가진 사건(피해·사망 `CombatCharacterEvent`. 회복은 Core가 근원을 남기지 않아 묶음 밖이다, `CombatStructureEvent`, `CombatHeldEnvironmentEvent.Origin`, `CombatObstacleReactionEvent.Origin`): (공격 그룹, 가해자)
  - 출처의 이동 후속(넉백 등 `Moved`·`Returned`·`Relocated`): 그 출처의 열쇠(공격 결과의 그룹, 공격자). 대응은 `CombatHitFollowUps`의 규칙을 그대로 쓴다.
  - **끊긴 넉백 경로(C-4 검토 결정 (a), §6.1):** 한 대상의 넉백 경로(그 묶음의 첫 이동 ~ 마지막 이동) 안에 다른 사건(넉백 가시 피해·중간 칸 발동·지형 등록 등)이 끼면 그 대상의 이동은 묶음 밖이다. 그 대상은 앞 사건이 모두 끝난 뒤 걷는다(옛 순서). 함께 출발했다가 낀 사건이 앞 대상 경로 끝을 기다리느라 경로 중간에 멈추는 것을 막는다.
- **묶음 범위:** 같은 행동 구간(`CombatActionBoundary` 사이) 안에서 열쇠가 같은 사건들이다. 같은 열쇠가 다음 행동 구간에 다시 나오면 다른 묶음이다(같은 공격자의 연쇄 공격 등).
- **묶음에 들지 않는 사건:** 근원이 없는 사건(영혼·효과·아티팩트·원본 변경·가시 소비·오브젝트 발동·턴·결과·기믹)과 행동 사건이다.
  - 이들은 지금처럼 앞 사건 전부가 끝난 뒤 시작한다(C3).
  - 기차 묶음은 C7이다.
- **사건 주체(점유 유닛):** 묶음 사건마다 표시 자원을 쓰는 유닛 하나다.
  - 캐릭터 사건 = 그 캐릭터, 구조물 사건 = 그 구조물, 보유 효과 = 그 캐릭터, 장애물 반응 = 그 장애물
  - 주체가 같은 사건은 동시에 돌지 않는다.
- 해석은 결과 시작 때 한 번 한다. 칸·이름으로 추측하지 않는다.

### C2. 시작 규칙 — 의존만 남기고 순서를 푼다

사건 i는 앞의 모든 사건 j가 아래 중 하나일 때 **시작 후보**다.

1. j가 완료됐다(지금의 사건 완료 통지와 같은 뜻. 공격은 정책별 사건 완료, 걸음은 첫 접촉 해제 또는 보간 끝).
2. i와 j가 **같은 동시 묶음**이고 **주체가 다르다.** 이때 j가 아직 시작되지 않았어도 된다(앞 유닛의 다음 사건을 기다리지 않음).

후보는 표시가 "지금 시작해도 된다"고 답할 때(C5: Gate 규칙·주체 자원) 시작한다.

규칙의 결과:
- **같은 유닛의 사건 순서는 지금과 같다.** 피격 반응 → 넉백, 광란 파동 90 → 80 순서가 유지된다.
- **묶음 밖 사건(행동·영혼·효과 등)은 앞 사건 전부의 완료를 기다린다.** 묶음 뒤의 다음 행동은 묶음 전체가 끝난 뒤다(§6 Q-C2).
- **묶음이 없는 결과는 지금과 같다(동작 보존).** 대상이 하나인 공격, 접촉 없는 걸음, 순수 이동이 그렇다. 접촉으로 일찍 사건 완료된 자발적 걸음의 남은 연출 중 다른 유닛 이동도 지금처럼 걸음 끝 뒤다(걸음 Gate 규칙 1, C-4 검토 결정, §6.1).

| 경우 | Core 순서(요약) | 새 시작 |
|---|---|---|
| ① ShotGun 3명 | 공격 → 피해 A·B·C | 히트에 A·B·C 반응이 동시에 시작 |
| ② 산탄 2명 사망 | 공격 → 사망 A·B | 히트에 A·B 사망 모션이 동시에 시작 |
| ③ 범위 넉백 2명 | 공격 → 피해 A·B → 이동 A1·A2 → 이동 B1 | A·B 반응 동시, 각자 반응 끝에 A1·B1 걸음 시작, A2는 A1 뒤 |
| ④ Ballista 관통 | 공격 → 피해 B1·B2(접촉 순) | 각자 화살이 닿는 순간 시작, 앞 반응과 겹침 |
| 지뢰 폭발 | 발동 → 피해 이동자·이웃 | 이웃은 접촉 순간 반응, 이동자는 걸음 끝 뒤(H-4 규칙 그대로) |
| 광란 2파동 | 공격 → 피해 A(파동1) → 피해 A(파동2) | 열쇠가 달라 지금처럼 차례로 |
| 넉백 경로 안에 가시 피해 | 공격 → 피해 C·A → 이동 C1·C2 → 이동 A1 → 가시 피해 A → 이동 A2 | C는 반응 끝에 걷고, A는 C 경로가 끝난 뒤 A1 → 가시 반응 → A2(C1 끊긴 경로, C-4 결정 (a)) |

### C3. 소유 — 순서는 순차 재생, 자원·Gate는 표시

- **순차 재생(스케줄러)이 소유한다.** 동시 묶음 해석(C1)과 시작 규칙(C2), 사건별 상태(시작·완료), 결과 완료 판정이다.
  - 표시를 모르는 순수 C#이다. 가짜 재생으로 순수 시험할 수 있다.
- **표시가 소유한다.** "그 사건을 지금 시작해도 되는지"에서 자원·Gate 부분이다. 공격 Gate, 걸음 Gate, 주체 유닛의 반응·걸음·대여 상태다.
  - 표시는 묶음을 모른다. 동시성은 스케줄러가 정하고, 표시는 유닛 자원이 비었는지만 답한다.
  - 메모리 원칙 "책임 분리는 소유·시점까지"에 맞춘다. 판단 식만 빼고 시점을 조정자가 쥐지 않도록, 순서 시점은 스케줄러 하나가 가진다.
- 해석의 원본은 하나다.
  - 묶음은 `CombatConcurrentGroups`만 해석한다.
  - 이동 후속 대응 규칙은 `CombatHitFollowUps`를 재사용한다. 같은 클래스를 순수 인스턴스로 한 번 더 만드는 것이지 규칙을 복제하는 것이 아니다.

### C4. 스케줄러 동작

- 결과 시작 때 사건별 상태 배열을 만든다(결과마다 한 번 할당). 첫 미완료 사건 위치를 기억한다.
- **Tick마다:**
  1. 표시 진행(`TickPresentation`)
  2. 첫 미완료 사건부터 앞으로 훑는다. 시작 후보(C2)이고 표시가 허락하는 사건을 **모두** 시작한다.
  3. 훑기는 "뒤 사건이 지나갈 수 없는 미완료 사건"(묶음 밖 미완료, 또는 같은 묶음의 같은 주체 미완료)에서 멈춘다.
- **걸음:**
  - 걸음도 사건별 완료 콜백으로 받는다(C6).
  - 경로 끝 걸음이면 완료 뒤 방향 복귀(`BeginMovementEnd`)를 거쳐 완료한다(지금과 같은 판단, 유닛별).
- 표시 계약이 없는 사건은 지금처럼 경고 뒤 건너뛴다(완료로 둔다).
- 결과 완료는 모든 사건 완료 + 표시 완료(`IsPresentationComplete`)다.
- 취소·다시 연결·세대 규칙은 지금과 같다. 늦은 완료는 세대·사건 위치로 무시한다.
- 비용: 결과 하나의 사건은 수십 개라 매 Tick 훑기로 충분하다. 시작 후보 판단(`CanStart`)이 첫 미완료부터 앞 사건을 다시 보므로 O(n × 창 크기)다(창 = 첫 미완료 ~ 훑기 멈춤). 매 프레임 새 할당은 하지 않는다.

### C5. 표시의 유닛별 자원

| 부품 | 지금 | 바뀐 뒤 |
|---|---|---|
| `CombatUnitReactionSet` | 다른 반응이 있으면 피격 불가, 사망만 동시 | **같은 유닛만 배타.** 서로 다른 유닛의 피격·사망은 함께 진행(동시성은 스케줄러가 정함) |

| 걸음 Gate 규칙 1 | 새 행동·**모든 이동**·이동자 사건은 걸음 끝까지 대기 | 새 행동·**이동자 자신의 이동**·이동자 사건. 다른 유닛 이동의 순서는 스케줄러가 정한다(같은 묶음이면 동시, 아니면 앞 사건 완료 뒤). 단 **자발적 걸음**이면 다른 유닛의 이동도 걸음 끝까지 막는다(자발적 걸음은 묶음에 들지 않아 함께 걸을 이동이 없음, C-4 검토 결정 §6.1) |
| 걸음 Gate 규칙 3(C-3 구현 중 결정, C-4 검토로 표에 더함) | 그 밖의 사건은 걸음 사건 완료 뒤 | **레인이 막지 않는다.** 그 뜻(묶음 밖 사건은 앞 걸음 사건 완료 뒤)은 스케줄러의 장벽 규칙(C2)이 맡는다. 표시는 묶음을 모른다(C3) |
| 배치 소유 (a) | `_steppingActor` 하나 | 보간 중 유닛 **집합** |
| `CanBeginPresentationEvent`·`RequireIdle` | 반응 하나라도 돌면 막음, 걸음 중이면 겹침 허용 사건만 | **사건 주체** 기준: 주체 유닛에 반응·걸음·대여가 남아 있으면 막는다. 행동 사건만 전역 유휴(공격·능력·반응·걸음 모두 끝)를 요구한다(지금과 같음). 주체 없는 사건은 모든 반응 끝·모든 레인의 걸음 사건 완료 뒤다. 시작 조건과 시작 전제는 같은 판단(`ReactionBlocks`·`MotionBlocks`)을 쓴다(C-4 검토, "시작 가능이면 시작은 실패하지 않음") |
| `TickPresentation` | 공격 → 능력 → (반응이면 반응만, 걸음 겹침이면 보간 먼저) → 걸음 | 공격 → 능력 → **모든 걸음 레인 → 모든 반응**. 새 레인에는 시작 프레임의 시간을 주지 않는다. 걸음은 Version 장치 없이 구조로 보장한다(스케줄러가 표시 진행 뒤 훑기에서 걸음을 시작). 반응은 기존 Version 규칙 그대로 |

- 묶음 밖 사건은 스케줄러가 앞 사건 전부의 완료를 기다리게 한다. 그래서 주체 기준 판단으로 바꿔도 묶음 밖 사건의 시점은 지금과 같다.
  - 피격·사망 반응의 완료 = 모션 끝
  - 걸음의 남은 보간은 걸음 Gate 규칙이 계속 판단한다.

### C6. 재생 계약 — 걸음도 사건별 완료로

- `ICombatMovementPlaybackPresenter`의 `BeginStep(step)` + `IsMovementComplete`(현재 걸음 하나를 폴링)를 `BeginStep(step, completed)`(사건별 완료 콜백)로 바꾼다.
  - `completed`의 뜻은 H-4b의 걸음 사건 완료 그대로다.
  - `BeginMovementEnd(lastStep, completed)`는 유지한다(유닛별 경로 끝).
- `CombatMovementPlayback`(한 걸음 수명 도우미)은 스케줄러의 사건 상태로 흡수하거나 걸음마다 하나로 바꾼다. 계획에서 정한다.
  - 결정(C-3 구현): 셋째 안. 걸음마다의 상태(시작·사건 완료·경로 끝)는 스케줄러가 소유하고, 도우미는 연결 수명(걸음·복귀 전달, 끊을 때 한 번 취소)만 맡는 얇은 연결로 남겼다(계획 §7.3).
- **구현 대상:**
  - `CombatSceneDisplay`(해제 뒤 가드)
  - `CombatSceneEventPlayback`(기차 가드)
  - `CombatSceneEventPresenter`
  - 시험 가짜 2개(`CombatViewSystemTests.FakeDisplay`, `FrenzyViewContractTests.RecordingPlayback`)
- View 내부 계약이라 Framework 공유 대상은 아니다. Factory 생성자는 바뀌지 않을 전망이다(바뀌면 공유 문서에 절을 더함).

### C7. 기차 — 지금 전용 재생 유지 (§6 Q-C3)

- 기차 접촉 사망은 이미 "같은 순간 묶음의 동시 시작"을 전용 재생으로 한다.
  - 순차 재생에서 소비(`TryConsumeDeath`)하고, 접촉 시각에 시작(`BeginConcurrentDeath`)하고, 묶음 완료를 장벽으로 쓴다.
- 이 작업에서는 그대로 둔다. 기차 묶음의 사망은 C1 묶음에서 뺀다(근원 없음).
- 비용: 동시 처리의 원본이 둘이 된다(스케줄러 묶음 + 기차 전용).
- 후속 이전 조건: 기차 사망을 "접촉 시각 해제가 있는 동시 묶음"(Ballista와 같은 모양)으로 옮기면 `TryConsumeDeath`·`BeginConcurrentDeath`가 사라진다. 기차 시험 묶음(`CombatRailwayContactPlaybackTests`·`CombatRailwayContactSceneTests`·`RailwayContactScheduleTests`)이 회귀 기준이다.

### C8. 완료·취소·실패

- 사건 완료 1회, 늦은 콜백 무시, 완료 전 상태 확정은 지금 규칙을 사건별로 지킨다.
- 취소는 모든 레인을 정리한다. 반응 전체, 걸음 레인 전체, 배치 소유 집합, 공격·능력 동작이 대상이다.
- 레인 하나의 실패는 결과의 실패다. 지금처럼 공유 오류 경계로 정지한다(F1). 다른 레인의 늦은 완료는 세대로 무시한다.
- 결과 끝 `Refresh`는 모든 레인이 끝난 뒤에만 부른다(`IsPresentationComplete`).

## 4. 원칙 점검

- **SSOT:**
  - "같은 순간"은 Core 사실(피해 근원 열쇠·이동 후속 대응) 하나에서만 파생한다. 묶음 해석은 `CombatConcurrentGroups` 한 곳이다.
  - 시작 시점의 원본은 스케줄러 하나다. 표시는 자원 상태만 가진다.
  - 유닛 자원 상태는 각 부품(반응 집합·걸음 레인·대여)이 원본이다. 스케줄러가 사본을 들지 않는다.
  - 기차 묶음은 C7의 알려진 이중 원본이며 이전 조건을 적었다.
- **SOLID:**
  - SRP: 스케줄러 = 순서·의존, 표시 = 자원·Gate, 묶음 해석 = 순수 클래스.
  - OCP: 새 동시 경우(예: 새 폭발 종류)는 Core가 같은 근원 열쇠를 주면 코드 변경 없이 묶인다.
  - LSP: `ICombatEventPlayback` 구현은 사건별 완료 보장을 지킨다.
  - ISP: 표시는 묶음 정보를 받지 않는다.
  - 과추상화 회피(지침 §27): 레인을 일반 "작업 그래프"로 만들지 않고 유닛 하나 = 레인 하나로 둔다.
- **Framework:** 새 Service·ServiceKey·AddModule·Builder 단계 없음. 재생 계약은 View 내부다. Factory가 바뀌면 공유 문서에 기록한다(인계 §4.5).
- **기능 변경 독립성:**
  - 새 동시 경우는 C1 열쇠 규칙 한 곳에서 생긴다.
  - 새 유닛 자원(예: 애니메이션 이벤트 레인, H-5)은 C5 표에 부품 하나를 더한다. 다만 지금은 유닛 자원을 묶는 공통 판단이 없어 Presenter의 다섯 곳(시작 조건, `RequireIdle`의 `*Blocks`, `TickPresentation`, `IsPresentationComplete`, 취소)에 그 부품을 넣어야 한다(C-4 검토 10). "유닛 자원 판단 하나"로 모으는 일은 Presenter 분리(S 계획) 후보다.
  - 시작 규칙을 바꾸는 변경(예: 묶음 뒤 사건도 주체만 보고 시작, Q-C2 B)은 스케줄러 한 곳만 바꾼다.
  - 회귀 기준: 이동·경로 끝·적 간격·넉백·포효·기차·광란 묶음, 히트 타이밍 Unity 시험 전체.

## 6. 사용자 결정 (2026-10-17)

- **결정:** Q-C1 = A "Core 피해 근원 열쇠", Q-C2 = A "묶음 전체가 끝난 뒤", Q-C3 = A "지금 유지, 후속 이전". 아래 선택지는 결정 근거로 남긴다.

- **Q-C1. "같은 순간"의 기준:**
  - A(권장): Core 피해 근원 열쇠(공격 그룹 + 가해자) + 같은 출처의 이동 후속(넉백). 사실만 쓰고, 근원 없는 사건은 지금처럼 차례로다.
  - B: 행동 구간 안이면 서로 다른 유닛 사건은 모두 동시. 더 넓지만 영혼·효과 같은 사실 순서가 흐트러질 수 있다.
- **Q-C2. 묶음 뒤 사건이 시작하는 시점:**
  - A(권장): 묶음 전체가 끝난 뒤. 영혼·효과·다음 행동의 순서가 지금과 같다.
  - B: 주체가 겹치지 않으면 묶음이 끝나기 전에도 시작. 빠르지만 사실 순서 위험이 있다.
- **Q-C3. 기차:**
  - A(권장): 지금 전용 재생을 유지하고 후속에서 이전한다. 이번 범위와 회귀를 줄인다.
  - B: 이번에 같은 구조로 옮긴다.

### 6.1 통합 검토 뒤 사용자 결정 (2026-10-18)

- C-4 통합 검토(런타임 정확성 에이전트)가 찾은 두 건을 구현 전에 물었다. 둘 다 추천안으로 결정했다.
  - **끊긴 넉백 경로 = (a) "그 대상만 차례로".** 뒤 대상 경로 안에 묶음 밖 사건이 끼면 그 대상의 이동만 묶음에서 뺀다(C1). 다른 안 (b) "걸음 구간이 겹침을 물려받음"은 Q-C2 A 범위가 바뀌고 스케줄러·걸음 구간 연결이 늘어 택하지 않았다.
  - **자발적 걸음 = "HEAD대로".** 자발적 걸음 레인이 활성이면 걸음 Gate 규칙 1이 모든 이동 사건을 걸음 끝까지 막는다(C5). 다른 안 "알려진 차이로 기록만"은 택하지 않았다.
