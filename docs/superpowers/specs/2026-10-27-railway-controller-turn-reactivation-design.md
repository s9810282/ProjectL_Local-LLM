## 1. 목적과 결정 상태

사용자는 보류한 기차 기믹을 다시 켜며, 기존 개별 유닛 턴 종료 대신 **플레이어 턴 종료와 적 전체 턴 종료 각각에서 발동 조건을 검사**하도록 지시했다. 이어서 종료 횟수를 합산하는 기준(내 턴 종료 1, 적 턴 종료 2)으로 설계·Task 작성을 요청했다.

| 구분 | 내용 |
|---|---|
| 확정 R1 | 성공한 플레이어 턴 종료와 적 전체 국면 종료마다 1회 검사한다. 개별 적 행동 종료에서는 검사하지 않는다 |
| 확정 R2 | 두 진영 종료 횟수를 합산한다. 최초·반복 간격은 이 횟수 단위다 |
| 확정 R3 | 발동 시 기차 판정·사망·승패를 정산하고 다음 턴을 진행한다. View는 결과를 재생하며 규칙을 계산하지 않는다 |
| 승인 P1 | 기존 최초·반복 숫자를 그대로 보존하고 새 단위로 해석한다. 현재 에셋은 모두 5/5다. 수치 재조정은 별도 기획 변경이다 |
| 승인 P2 | 종료 횟수는 전투 진입 시 0, 밤이 끝나 배치로 돌아가도 유지하고 새 전투에서 초기화한다 |
| 승인 P3 | 적 마지막 턴도 회수 전에 기차를 검사한다. 기차로 전투가 끝나면 밤 종료·회수·다음 턴 시작은 실행하지 않는다 |
| 승인 P4 | 발동 대상·효과는 기존 기차 규칙을 유지한다. 레일에 점유 칸 하나라도 겹친 살아 있는 필드 캐릭터를 진영 구분 없이 즉사시킨다. 구조물·본부는 포함하지 않는다 |

**2026-10-27 사용자 승인:** 제안한 기준을 승인하고 기존 5/5·밤 사이 누계·회수 전 판정을 명시적으로 확정했다. 위 P1~P4는 승인된 설계이며, 사용자는 Core 수정과 Phase A 진행도 허용했다. Phase A 뒤 멈추고 보고한다. 양측 동시 사망의 승패 우선순위는 기존 Core 승패 판정을 그대로 사용하며 기차 전용 우선순위를 만들지 않는다.

## 3. 발동 규칙

종료 누계 C, 최초 종료 횟수 F, 반복 간격 I에 대해 다음 조건으로 발동한다.

```text
C >= F && (C - F) % I == 0
F >= 1, I >= 1
```

발동 여부는 **이번 종료를 반영한 C**로 계산한다. F=5, I=5이면 5·10·15·20…에서 발동한다.

| 순서 | 경계 | C | F=5, I=5 |
|---|---|---:|---|
| 0 | 전투 진입·첫 플레이어 턴 시작 | 0 | 검사 없음 |
| 1 | 플레이어 첫 턴 종료 | 1 | 미발동 |
| 2 | 적 첫 국면 종료 | 2 | 미발동 |
| 5 | 플레이어 세 번째 턴 종료 | 5 | 발동 |
| 10 | 적 다섯 번째 국면 종료 | 10 | 발동 |
| 16 | 적 여덟 번째 국면 종료·밤 종료 직전 | 16 | 미발동, 누계 보존 |
| 20 | 다음 밤 적 두 번째 국면 종료 | 20 | 발동 |

- 배치·전투 진입·턴 시작·개별 행동·호버·미리보기·결과 확인·View Tick은 C를 올리지 않는다.
- 거절된 종료, 오래된 턴 요청, 중복 요청은 C와 사건을 변경하지 않는다.
- 적 유닛이 행동하지 못했더라도 정상적인 적 전체 국면 종료가 성립하면 1회 센다.
- 앞선 공격 등으로 이미 전투가 끝났으면 종료를 추가 생성하거나 기차를 발동하지 않는다.
- 대상이 없어도 발동 경계라면 기차 사건을 내고 통과 연출을 재생한다.
- 레일이 없는 비기차 스테이지의 전투 진행은 기존과 같다. 기차 설정이 있는데 레일이 비었거나 중복·범위 밖이면 기존 준비 검증에서 실패한다.

## 4. 사실 소유권과 계약

### 4.1 종료 누계

제안: `CombatTurnFacts.CompletedControllerTurnCount` (`long`, 0 이상)를 두 진영의 **수락된 종료 누계**로 둔다. `ControllerTurnSequence`는 시작 순번·오래된 요청 방지용이며 종료 누계로 재해석하지 않는다. `CompletedPlayerTurnCount`도 밤 진행용 의미를 유지한다.

진영 종료 사실은 적 종료 직후 Deployment에서도 의미가 남으므로 현재 진영·밤 진행에서 추측하지 않는다. 누계 원본은 Buffer에 게시한 턴 사실 하나이며, 기차 전용 카운터·View 카운터·다음 발동 카운터를 따로 저장하지 않는다. 발동 시각은 C/F/I에서 계산한다.

새 필드가 필요한 경우 생성자·SameValues·사실 복사·명령 합성·Buffer의 전이 검증·초기화를 함께 변경한다. 운영 복사 지점에서 기본 0으로 조용히 되돌아가면 안 된다. Buffer는 새 전투 0, 정상 종료 +1, 그 외 보존을 검증한다. 정상 종료와 상태 변경은 동일 게시 단위여야 한다. 재시도 시 같은 원본에서 계산한 결과를 중복 적용하지 않는 기존 expected/final 및 결과 순번 경계를 유지한다.

### 4.2 설정 명칭과 에셋

제안 명칭은 `FirstActivationAfterControllerTurns`, `RepeatIntervalControllerTurns`이며 SO 필드는 `firstActivationAfterControllerTurns`, `repeatIntervalControllerTurns`다. `RailwayGimmickSpec`, DB `RailwayData`·입력 DTO·도구의 단위를 함께 바꾼다. 옛 UnitTurns 별칭을 새 규칙의 두 번째 원본으로 남기지 않는다.

SO 직렬화 변경에는 `FormerlySerializedAs`를 사용해 기존 5/5를 보존한다. YAML 에셋·JSON/도구 입력은 각 형식의 실제 로딩 경로를 확인해 별도로 이전한다. 직렬화 속성이 모든 형식에 적용된다고 가정하지 않는다. 에셋의 railwayEnabled 상태, 레일 좌표, GUID, 프리팹, 외형 값은 보존한다. 현황은 Normal_A·Boss 켜짐, Normal_B·Normal_C·Test 꺼짐이다. 꺼진 스테이지를 일괄 활성화하지 않는다.

진입 설정은 `StageConfig` → 준비 사실 → 명령 입력의 기존 경로를 추적해 Core가 읽도록 한다. View DB 조회나 전역 DB 조회를 추가하지 않는다. 불변 설정의 기존 준비 소유자를 재사용하고, 실제 누락된 명령 전달 계약만 좁게 확장한다. 동일 설정을 여러 가변 저장소에서 관리하지 않는다.

**Phase A 확인:** `CombatPreparation.RailCells/StageGimmicks` → `CombatStateData` → `CombatInputAssembler` → `CombatBattleFacts.RailCells/GimmickDefinitions` → `CombatCommandInput.Battle` 경로가 이미 있다. 설정 저장소·생성자 인자를 추가하지 않았으며 입력 복사도 같은 불변 Battle 문맥을 보존한다. SO 편집 작업본의 `railFirstActivation`/`railRepeatInterval` JSON 이름은 원래부터 단위 중립적이어서 보존했다. SO 접근 상수·화면 단위 설명만 바꾸었다. 실제 SO는 YAML을 다시 쓰지 않고 FormerlySerializedAs로 읽는다. 실제 역직렬화·재저장은 Unity 시험 대기다.

### 4.3 결과·사망 계약

기존 `CombatGimmickEvent`와 `RailwayGimmickActivationSnapshot`의 기믹 ID·영향 레일·처치 ID 계약을 재사용한다. 레일별 또는 대상별 중복 사망을 만들지 않는다. 직접 사망 ID 순서는 결정적으로 유지한다.

기차 판정은 순수 Core 계산으로 수행하고, 즉사 대상의 사실 변경은 현재 공통 사망·영혼·아이템 정리·깃발·보상·Run 통계·승패 정산 경로에 넣는다. HP만 0으로 바꾼 Changed 결과로 끝내지 않는다. 죽은 캐릭터 한 명은 정산·통계·사건에서도 한 번만 처리한다. 공격자가 없는 환경 사망에 가상의 공격자·공격 처치 귀속을 부여하지 않는다. 보상 자격과 동시 패배/승리 우선순위는 기존 공통 규칙을 따른다.

옛 기차 살상 구현은 현재 파일에 남아 있지 않으므로 역사 코드를 그대로 복원해 현 명령·정산 계약을 우회하지 않는다. 현재 사망 정산 도구로 연결 가능한지를 Phase A에서 확인한다.

## 5. 종료 처리와 게시·재생 순서

공통 흐름은 다음과 같다. 새로운 타이머·Job·Flow를 만들지 않는다.

1. 기존 종료 허용 조건과 요청 신선도를 검사한다.
2. 해당 종료 누계를 +1 하고 종료 사실을 만든다.
3. 종료 시점의 필드 배치를 기준으로 기차 발동 여부·일괄 직접 사망을 계산한다.
4. 공통 사망·승패를 정산한다. 종료됐다면 여기서 전투 결과를 확정한다.
5. 계속되는 경우에만 다음 진영 준비 또는 밤 종료 정리·회수를 수행한다.
6. 종료·기차·직접 사망·후속 정산·필요한 밤 종료 사건을 순서대로 담아 원본 대비 최종 변경 하나로 게시한다.
7. View가 기존 결과 확인 경계에서 기차 접촉 사망·후속 사건을 재생한 뒤 다음 처리로 진행한다.

플레이어 종료와 적 종료가 같은 기차 기능 계산기를 호출하도록 하고, 각 종료 경계는 호출 순서만 조정한다. 동일 명령 안의 투영/합성은 기존 도구를 우선 사용하며 종료된 중간 결과 뒤에 다음 단계를 합성하지 않는다. 불필요한 중간 결과를 Buffer에 게시하지 않는다.

적 마지막 국면에서는 **EnemyPhaseEnded → Railway 묶음(해당 시) → 후속 정산 → NightEnded·회수(계속될 때)** 순서다. 회수 후 빈 필드에서 검사하면 안 된다. 기존 아이템 밤 종료 만료도 기차 사망 정산 뒤다. 해당 순서와 사건 Expected/Final 연속성을 함께 검증한다.

약한 지반의 별도 작업은 독립 기능이다. 이번 설계에서 턴 종료 붕괴·토네이도 등을 새로 호출하지 않는다. 공유 사망 정산에 이미 포함된 동작은 기존 계약을 따르되, 다른 기능의 새 경계가 필요하면 구현을 멈추고 설계를 먼저 조정한다.

## 6. View·조립·소유 영역

View는 Buffer 결과로 받은 기차 사건을 기존 열차 이동·접촉 사망 경로로 재생한다. 사망 직전 Expected 사실을 사용하고 최신 Buffer 위치로 대상을 다시 고르지 않는다. 접촉 시점에 Core 상태를 수정하지 않는다. 열차 통과와 직접 사망 연출이 모두 완료돼야 묶음을 완료한다. 사망·승패가 확정됐더라도 마지막 결과 재생은 유지한다.

기차 기능의 카메라·소리·이펙트·다중 열차·Cancel/Release는 기존 계약을 재사용한다. FieldCamera·Architecture·무관한 UI를 수정하지 않는다. 사건 그룹 형식이 기존 재생기와 맞으면 View 코드 변경은 필요 없다. 맞지 않으면 Phase 경계에서 차이를 보고하고 계약 변경을 승인받는다.

Core 구현은 Core 작업자 영역이다. 최초 요청은 문서 작성이었으며, **후속 사용자 지시로 Core 수정을 명시적으로 허용받았다.** Phase A 보고 뒤 사용자는 Phase B를 요청했고 이어서 중간 검증을 건너뛰고 D까지 진행하도록 범위를 확장했다. [Core 경계 인계 §5.56~5.57](../handoffs/2026-09-24-view-core-data-boundary-handoff.md)에 단계별 변경 범위를 기록한다. 인계 문서의 기존 다른 변경은 보존한다.

| OCP | 기존 두 종료 지점에 좁은 기차 호출을 연결. 다른 보류 기능을 위한 범용 스케줄러를 만들지 않음 |
| LSP | 기차 미설정 전투·기존 명령의 허용/거절·결과 확인 계약을 유지 |
| ISP | 기차 계산에는 종료 누계·설정·필드 사실·정산 문맥만 전달. 전체 DB/Runtime 서비스 묶음을 전달하지 않음 |
| DIP/P1/P6 | Core는 순수 값과 기존 규칙에 의존. Unity·View·Framework 조립 내부·전역 DB에 의존하지 않음 |
| JMH/FW | 기존 생성/등록/Export/소비 경로 유지. FW-001~003 새 서비스·Builder 불필요, FW-004 Buffer 우회 금지, FW-013~016 사건·수명·결과 순서 유지. View 자원은 기존 Scope/Handle 계약 유지 |

기능 독립성의 변경 시나리오: F/I나 살상 대상 규칙 변경은 기차 계산·설정·해당 테스트에 머문다. 양쪽 턴 종료에 살상 코드를 각각 넣으면 두 턴 경로와 밤 회수를 함께 이해해야 하므로 채택하지 않는다. 열차 속도·외형·접촉 표시 변경은 기존 View 기차 구현에 머물고 Core 턴 코드를 바꾸지 않는다. 공통 종료 전이·사망·게시 계약을 바꾸는 경우에만 양 진영·밤 경계 통합 검증을 함께 수행한다. Factory는 의존성 전달만 담당한다.

## 8. 완료 기준과 리뷰 지점

- F=1/I=1, F=5/I=5, 다른 F/I에서 두 진영 합산 종료 기준과 정확히 일치한다.
- 중복·거절·미리보기·개별 행동에는 진행하지 않고 밤 경계·전투 초기화가 일관된다.
- 직접 사망·환경 후속·승패·보상·통계가 한 번만 정산되고 종료 후 다음 턴이 시작되지 않는다.
- 밤 마지막 적 종료에서 회수 전 레일의 대상이 판정되고, 계속되는 경우만 회수된다.
- View의 접촉 사망·피해자 없음·다중 대상·취소·최종 결과 재생이 유지된다.
- 설정 이전 후 기존 숫자·레일·켜짐·GUID가 보존되며 다른 보류 기능은 켜지지 않는다.

설계 승인 전 코드를 바꾸지 않는다. 기본적으로 각 Phase 종료 시 보고·중단하되, 이번 B~D는 사용자의 후속 지시로 중간 중단·검증을 생략했다. 새 경계·효과·수치 정책이 필요하면 먼저 문서를 수정해 결정받는다.

## 9. B~D 반영 사항과 검증 유보

- `CombatGimmickCalculator.TryAdvance`는 입력의 종료 누계와 F/I로 판단하고, 레일과 겹치는 살아 있는 필드 캐릭터를 ID 순서로 한 번씩 즉사시킨다. 빈 피해자도 사건을 낸다. 잘못된 레일/중복·잘못된 형식의 기믹은 예외다. 이 계산기는 누계를 올리거나 결과를 설치하지 않는다.
- 사건은 `Railway → 연속 Died → 공통 후속 정산`이다. 기차 ID는 준비 기믹 목록 위치 +1로 고정한다. `Finish`와 기존 명령 합성을 사용하고 새 사망·보상·게시 경로를 만들지 않는다.
- 환경 즉사에 명령 행위자가 잘못 귀속되지 않도록 내부 정산 입력의 ActorId만 비운 뒤 원본 입력으로 합성한다. 직접 피해/공격으로 위장하지 않는다. **현재 공통 정책의 영혼 생성·깃발 드롭은 보류된 no-op이며 복원하지 않았다. 귀속자 없는 환경 사망에는 처치 골드·경험치와 그 목록 기반 Run 처치 수가 붙지 않는다.** 클리어 보상·승패·사망 정리는 기존 정책을 따른다. 이 정책을 바꾸는 것은 이번 기차 재활성화 범위 밖이다.
- `EndPlayerTurn`은 누계 +1 뒤 기차를 붙인다. `EndEnemyPhase`는 누계 +1과 EnemyPhaseEnded를 먼저 만든 뒤 기차를 붙이고, 계속되는 밤 마지막 적 종료에서만 `EndNight`로 아이템 만료·회수를 진행한다. 중간 세계는 Buffer에 게시하지 않는다.
- 기존 `CombatEventTypeTable` Railway 경로 → `CombatSceneEventPlayback` → `CombatRailwayContactPlayback` 및 열차·사망 완료 대기·취소 경로를 그대로 사용한다. 사건 구조가 같아 View 생산 코드·Factory·씬·프리팹 변경은 없다. 실제 화면 인수는 미실행이다.
- 재현용 시험 소스는 추가/갱신했지만 **이 최신 B~D 변경은 컴파일도 시험도 실행하지 않았다.** Phase A의 통과 기록을 B~D의 성공 증거로 재사용하지 않는다. 남은 일괄 확인 항목은 계획 §9다.
