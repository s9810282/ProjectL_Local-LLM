## 1. 중요 발견 사항

### R1 · P1 — 이동 부품이 17개 특성의 설정 구조를 다시 소유한다

**설계 위치:** D3의 17개 형식/필드 표, 새 `MovementDefinitionComparison`에 이를 모으는 방식.

현재 Core는 다음 경계를 이미 갖고 있다.

- [TraitRegistry](../../../Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/CoreSystem/CoreCaculator/Application/Combat/Traits/TraitRegistry.cs)의 `GetRequiredRegistration`/`BuildDefinition`은 특성 등록과 특성별 Factory를 통해 설정을 해석한다.
- [EntrenchmentTraitFactories](../../../Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/CoreSystem/CoreCaculator/Application/Combat/Traits/EntrenchmentTraitFactories.cs)는 진지 구축 명세를 진지 구축 정의로 바꾼다.
- [TraitStatusSnapshot](../../../Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/CoreSystem/CoreCaculator/Contracts/Snapshots/Traits/TraitStatusSnapshot.cs)은 추상 `SameValues`를 두고 각 상태 타입이 자기 값을 비교한다. [AppliedStatus](../../../Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/CoreSystem/CoreCaculator/Contracts/CombatEffects/AppliedStatus.cs)도 같은 소유 방식을 쓴다.

초안대로면 특성의 필드/새 재합성 형식을 추가할 때 특성 구현과 등급 합성 외에 **이동 전용 타입 분기/필드 비교표까지 수정**해야 한다. 데이터 원본을 복사하는 문제는 아니지만, 어떤 필드가 그 특성의 설정을 이루는지에 관한 지식이 이동 부품에 중복된다. 기본/보유 정의의 비교를 한 파일에 모았다는 사실만으로 SSOT·OCP·캡슐화가 충족되지는 않는다.

**영향:** Core의 특성별 확장 방식에서 벗어나며 OCP·설정 캡슐화·Core 내부 변경 독립성이 약하다. Application에 이동 문맥 정책을 두는 위치 자체가 오류는 아니다. 문제는 그 정책이 개별 특성의 내부 설정 스키마까지 알아야 한다는 점이다.

**권장:** 이동 부품은 Unit/Profile 조합만 비교하고, 특성 설정 동등성은 특성 타입이나 기존 특성 등록 경계가 소유하도록 다시 설계한다. Core의 기존 명시적 `SameValues` 패턴이 우선 검토할 대안이다.

### R2 · P1 — 비교 지원 누락을 정상 StaleContext로 숨길 수 있다

**설계 위치:** D3의 "17개 외에는 참조 비교", "새 재합성 형식은 목록에 수동 추가" 정책.

나중에 등급 합성이 새 형식을 재생성하는데 이동 비교 쪽 추가를 빠뜨리면, 같은 설정인데도 참조가 달라 다시 거절된다. 안전을 위해 무조건 같은 것으로 취급하지 않는 점은 맞지만, **구현 누락이 사용자에게 상황 변경으로 보이는 구조**가 남는다. 정적 검토 때 목록 두 개를 맞추는 것만으로 새 타입의 지원을 계약상 강제하지 못한다.

**권장:** 새 특성 구현/등록 때 설정 비교 계약도 반드시 제공되게 한다. 미지원 구성은 컴파일 또는 구성 검증 경계에서 드러나게 하고, 실제 값 불일치는 정상 StaleContext로 구분한다. 값 비교와 참조 비교를 섞는 정책을 유지하려면 타입별 근거와 구성 시 검증을 명시해야 한다.

### R3 · P2 — 실제 사용하는 프로필과 문맥 수집 대상의 관계를 설명하지 않았다

**설계 위치:** D4에서 기본/보유 수집 범위를 그대로 두고 중복 의존 검토를 제외한 결정.

- [CombatCommandCalculator.RequiredProfile](../../../Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/CoreSystem/CoreCaculator/Application/Combat/CombatCommandCalculator.cs)는 OwnedId가 있는 경우 정확한 보유 프로필을 우선 선택하고, 조건에 따라 기본 프로필로 대체한다.
- [CombatMovementCalculator](../../../Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/CoreSystem/CoreCaculator/Application/Combat/CombatMovementCalculator.cs)는 이 선택 결과를 효과·발자국 등 이동 계산에 사용한다.
- [MovementContextCalculator.Capture](../../../Assets/ProjectL/Script/Systems/RuntimeSystem/InGameSystem/CoreSystem/CoreCaculator/Application/Combat/MovementContextCalculator.cs)는 CharacterKey로 기본 정의를 수집하면서 OwnedId로 보유 프로필도 별도로 수집한다.
- 현재 영혼 수집의 `CombatCommandCalculator.Collect`는 보유 기록/캐릭터 사실/메인 상태를 읽고, 서브 기본 체력은 캐릭터 사실에서 파생한다. 해당 코드에서 기본 UnitSpec을 다시 고르지는 않는다.

따라서 초안의 "현재 범위 유지"만으로는 문맥의 정의 의존이 실제 계산의 선택 정책과 왜 일치하는지 설명되지 않는다. 사용하지 않은 기본 프로필까지 비교하면 관련 없는 정의 변경으로 거절하는 범위가 넓어질 수 있다.

**권장:** 행위자·수집자·강제 이동 관련 개체가 실제 읽는 프로필/정의 경로를 대조하고, 기존 RequiredProfile 선택을 재사용할지 결정한다. 모든 기본 정의를 즉시 제거하자는 결론은 아니다. 필요한 의존을 빠뜨리지 않는 근거가 먼저다. 이 항목은 현재 실행 거절의 직접 원인이라고 확정한 것이 아니다.

## 3. Core 구조에 맞춘 수정 방향

### 우선 검토안 A — 특성 타입이 명시적 값 비교를 소유

- TraitSpec에 명시적인 설정 값 비교 계약을 두고 각 구체 타입이 자기 설정만 비교한다. 기존 TraitStatusSnapshot.SameValues처럼 소비자는 특성별 switch 없이 호출한다.
- 이동 전용 비교 부품은 UnitSpec 필드·OwnedId·Method 등 문맥 조합 책임만 갖는다.
- 전역 Object.Equals/GetHashCode 변경과 분리할 수 있다. 상태·DTO·Domain의 의존 방향도 유지한다.
- 비용: 현재 Contracts/Commands/Traits에 TraitSpec 직접 파생 선언이 있는 파일이 37개다(보류/폐기 계약 포함). 추상 비교 계약을 선택하면 이 형식들의 구현과 기존 시험 가짜 타입 3개(InvalidFocus, ReservedTraitSpec 두 곳)의 컴파일용 최소 대응까지 계획 범위에 넣어야 한다. 새 시험 작성/실행을 허용한다는 의미는 아니다.

### 대안 B — 기존 특성 등록에 타입별 비교 계약 연결

- TraitRegistry/TraitRegistration 경계에 타입별 비교를 명시적으로 연결하고 새 등록 때 제공을 검증한다.
- 단일 이동 switch 대신 특성별 비교 구현을 소유시킬 수 있다. 다만 비교를 위해 매번 Registry/Domain 정의를 새로 만드는 방식은 피해야 한다.
- Spec 공개 계약 변화는 줄일 수 있으나 등록·비교기 연결의 수정 범위가 커진다. Framework의 새 서비스/Builder 등록과는 다른 Core 내부 특성 등록이다.
- Factory에 실제 비교 기능까지 계속 붙이는 형태는 생성과 기능 책임을 섞으므로 권장하지 않는다.

**최초 추천:** 현재 Core의 자기 값 비교 선례와 단순한 호출 경로를 기준으로 A를 권장했다. 이후 사용자 지시로 A를 채택한 설계/계획을 작성했다(§5). 계획 개정 당시 두 소스 제한을 폐기했고, 후속 MC1 구현 결과는 §6에 기록했다.

### 함께 확정할 사항

1. 실제 RequiredProfile 선택과 Capture 의존 범위의 관계(R3).
2. Trait 목록 순서의 의미. UnitSpec은 입력 순서를 보존하고 Domain.UnitDefinition은 TraitKey로 정렬한다. 순서가 설정 의미인지, Key 기준 집합 동등성인지 명시해야 한다. 현재 거절의 직접 원인으로 단정하지 않는다.
3. Method·Behavior·Occlusion·KillReward 참조 유지의 경계. 현 합성은 이를 재사용하므로 즉시 결함은 확인되지 않았다. 이 조건을 유지하는 이동 문맥 정책과 모든 객체의 완전한 의미 동등성을 혼동하지 않는다.
4. 값 비교 지원 누락이 일반 StaleContext로 묻히지 않게 하는 방식(R2).

**기존 상태 비교를 설정 비교로 대신 쓰지는 않는다.** EntrenchmentTraitStatusSnapshot에는 반경/피해 감소율이 없고 형식만 비교하므로, 이를 재사용하면 설정 변경을 놓친다. 설정 동등성 계약을 별도로 소유시켜야 한다.

## 4. 검증·결정 상태

- 이번 검토는 설계/현 코드의 정적 대조다. 빌드·시험·실제 이동 재현을 하지 않았다.
- 후속 계획 개정 당시에는 문서만 수정했다. 이후 MC1 구현으로 진행했으며 결과는 §6에 기록한다. **컴파일 미확인.**

| R3 · 선택/의존 | 기존 RequiredProfile 선택 정책을 재사용. 행위자/수집자의 선택된 기본형 또는 보유형을 수집하도록 설계. 위치 교환·환경 강제 이동/면역·조기 종료의 포함 증명을 MC2.1 선행 조건으로 지정 | **의존 감사 미완료.** 빠진 의존이 발견되면 범위 변경을 먼저 확인하고 Capture 축소/임의 확장을 하지 않음 |
| Trait 순서 | TraitKey 기준 집합 동등성으로 명시. UnitSpec의 중복 금지와 Domain 정렬을 근거로 함 | MC2에서 효과 구성의 순서 비의존까지 정적 확인 |
| 원본 객체 참조 | Method·Behavior·Occlusion·KillReward는 전투 고정 원본 동일성 계약으로 한정 | 완전한 의미 동등성으로 확대 해석하지 않음 |

개정 순서는 MC1 특성 계약 → MC2 의존 감사/문맥 연결·선택 → MC3 사용자 Unity 인수다. 코드 Phase마다 멈춰 보고한다. 구조 보완을 **계획에 반영한 상태**이며 R1~R3의 구현 해결이나 실제 결과 8의 원인 확인 완료로 표시하지 않는다.

## 6. MC1 구현 정적 검토 (2026-11-02)

- R1: 설정 비교를 TraitSpec 파생 타입 37개에 배치했다. 공통 형식/키 검사와 구체 설정 비교를 나누고, 개별 타입의 필드 62개를 대조했다. 이동 전용 특성 목록/분기는 추가하지 않았다. 실제 소비자 연결은 MC2가 남아 있다.
- R2: SameValuesCore를 추상 계약으로 추가하고 기존 파생 타입 40개(운영 Spec 37·시험 가짜 3)의 override를 확인했다. 컴파일러 강제 계약은 추가됐지만 **컴파일을 실행해 확인한 것은 아니다.** 새 설정 필드의 비교 누락은 타입별 검토 대상으로 남는다.
- 기존 생성자·설정/등록·시험 검증 본문은 보존됐다. 시험에는 컴파일용 override만 추가했고 새 시험이나 assertion은 없다. 새 어셈블리 참조·전역 동등성·상태 사본·Tick/폴링·서비스 조립 변경은 없다.
- 소스 diff 공백 검사·LF/UTF-8·UnityEngine 참조 부재 확인. R3와 Trait 목록 순서/Unit/Profile 조합의 실제 연결 검토는 MC2에서 진행한다.
- MC1 리뷰 지점에서 중단한다. 결과 8의 실제 실패 항목·이동 수락 재현·Unity 컴파일은 아직 미확인이다.

## 7. 후속 사용자 지시 검증 (2026-11-02)

"테스트 돌려" 지시로 Unity Test Runner의 Core EditMode 4,637건을 실행해 4,636 통과·1 실패를 확인했다. 실패는 도발 활성화 횟수 검사이며 11월 1일 결과에도 동일하게 존재한다. 수정 코드의 Unity 컴파일은 확인됐고 기존 시험 3곳의 가짜 타입 대응 시험군도 전부 통과했다. §4~6의 컴파일/시험 미확인은 각 기록 시점의 상태다.

상세 실행 결과·이전 실패 대조는 [인계 §9](../handoffs/2026-11-02-shotgun-movement-stale-context-core-request.md#9-mc1-사용자-지시-테스트-실행-2026-11-02)에 기록했다. 새 시험·MSBuild·시험 내용/도발 규칙 수정은 없다. R3의 감사·이동 연결과 새 동등성 계약의 직접 확인은 이번 기존 시험 결과로 완료 처리하지 않는다.

## 8. MC2.1 후속 감사 — R3의 추가 의존 확인 (2026-11-02)

환경 피해의 CaptureIncoming은 움직이지 않은 진지 구축 오라 제공자의 프로필도 읽는다. 현재 행위자/수집자 집합이나 캐릭터 상태만으로 그 반경/감소율 설정을 보호할 수 없으므로 감사 통과로 처리하지 않았다. 위치 교환/강제 이동의 도착 전 종료/면역과 OwnedId 없는 대상도 도착 수집자 조건만으로 프로필 포함을 보장하지 못한다.

세부 표·소스 근거는 [인계 §10](../handoffs/2026-11-02-shotgun-movement-stale-context-core-request.md#10-mc21-프로필-의존-감사와-중단-2026-11-02)이다. 계획 MC2.2대로 구현 전 중단했고 코드 변경은 없다. Capture를 유지한 값 비교 연결(MC2A)과 실제 의존 추적 설계(MC2B)의 분리안을 확인 대기로 기록했다. R3 해결 완료로 표시하거나 이동에 특성별 오라 판정을 복제하지 않는다. 특성 순서 비의존은 Domain의 TraitKey 정렬과 효과 엔진의 Origin 정렬 경로를 확인했지만 비교 연결은 아직 구현하지 않았다.

## 9. 사용자 승인 후 MC2A 구현 정적 검토 (2026-11-02)

사용자 "진행해"로 §8의 분리안을 승인받아 값 비교만 연결했다. Capture 수집 범위와 실제 의존 누락 보강은 분리했다. R1/R2의 타입별 계약을 이제 기본/보유 정의의 공통 비교가 사용하며, R3는 MC2B의 잔여다.

- UnitSpec 독립 설정 18개와 프로필 OwnedId/Method/Definition, 특성 키 집합/자기 값 비교를 정적 대조했다. 새 비교 부품은 구체 특성 타입을 알지 않는다.
- 동일 참조/null, 특성 길이/키/값, 발자국 순서, 기존 원본 객체 참조 계약을 확인했다. 특성 배열 순서만 다른 경우는 같은 것으로 처리한다.
- 편집 전/후 Capture·Matches·다른 SameValues 조건·나머지 상태 비교가 동일함을 확인해 기존 사실 수집/거절 경계를 유지했다.
- 새 서비스/등록/조립/Buffer·DTO·View·시험 변경은 없다. 순수 C#과 internal 무상태 계산 경계를 유지하고 새 배열/정렬/캐시·특성 switch·Tick은 추가하지 않았다.
- 새 파일/meta·GUID·diff 공백·LF/UTF-8 확인 완료. **MC2A 컴파일 미확인**, 시험/재생 미실행이다. MC1 시험 결과를 이번 연결 코드의 통과 증거로 확대하지 않는다.

파일별 결과와 사용자 인수 항목은 [인계 §11](../handoffs/2026-11-02-shotgun-movement-stale-context-core-request.md#11-mc2a-값-비교-연결-구현-2026-11-02)에 기록했다. MC2A 리뷰 지점에서 멈춘다.

## 10. MC2B 설계 정적 리뷰 (2026-11-02)

[별도 설계](2026-11-02-movement-profile-read-tracking-design.md)와 [구현 계획](../plans/2026-11-02-movement-profile-read-tracking-plan.md)에 실제 프로필 읽기 추적을 구체화했다. 현재는 구현 전 사용자 리뷰 지점이다.

- **Core 구조/캡슐화:** Application의 지역 수집기와 명시적 인자 전달을 사용한다. 불변 CombatCommandInput/Contracts/Domain에 관찰자나 가변 실행 상태를 넣지 않는다. 기존 공개 서명을 유지하고 내부 타입을 공개 메서드 인자로 노출하지 않는다.
- **SSOT/S/O:** 기존 RequiredProfile의 실제 결과를 기록하므로 Capture에 선택/오라 후보/특성 분기를 복제하지 않는다. 수집과 선택·효과·동결을 분리한다. 새 특성은 기존 선택 경계를 쓰면 이동 분기를 추가하지 않는다.
- **L/I/D:** 기록 유무에 따른 기존 선택 결과/예외/규칙 의미를 유지한다. 공유 계산에는 프로필 수집기만 전달하며 전체 투영 객체·서비스 컨테이너를 요구하지 않는다. 새 인터페이스/등록은 필요하지 않다.
- **FW/변경 독립성:** 서비스/Builder/수명/UI/렌더 변경 없음. 조립은 이동/피해 생성 경계에 모은다. 특성 수치·선택 규칙·추적 정책의 수정 소유자를 나누되, 공통 전달 인자의 추가에 필요한 통합 확인은 계획에 남겼다.
- **C#/Unity/분기:** 내부 sealed 자료·불변 결과·GC 지역 수명, 새로운 Tick/폴링/전역/스레드 상태 없음. null 수집기는 기존 비추적 계산이며, 혼합 선택/입력 외 개체 같은 구성 오류는 정상 StaleContext로 숨기지 않는다.
- **공개 경계:** 공개 ProjectRoute만 추적하고 기존 VisibleTo/생성자 재필터를 유지한다. 숨겨진 환경 원본이나 전체 프로필 목록을 문맥에 추가하지 않는다. 같은 수집기를 피해 뒤의 존재/도발/처치 경로까지 전달해야 한다.
- **남는 검토:** 새 소비 함수가 수집기를 전달하는지는 정적 경로 검토가 필요하다. 모든 런타임 사실의 최소 의존이나 미래 전달 누락을 자동 증명하는 설계는 아니다. 구현·컴파일·Unity 인수까지 완료했다고 표시하지 않는다.

문서만 변경했으며 MB1/MB2 코드는 미착수다. **컴파일 미확인.**

## 11. MB1 사전 대조 보완 — 결속력 방어 간접 읽기 누락 (2026-11-02)

초기 MC2B 전달 목록에서 CombatEffectiveStatsCalculator.CohesionDefenseBonus를 빠뜨렸다. TraitPresenceReconciler의 수신자 방어 계산이 이 메서드를 거쳐 RequiredProfile을 읽으며, 앞선 출처 목록에서 제외한 죽은 수신자도 이 읽기에 도달할 수 있어 기존 기록에 포함됐다고 가정하지 않는다.

동일 수집기를 이 내부 메서드까지 전달하는 것이 선택/방어 규칙의 SSOT와 부정 후보 기록 계약을 유지하는 변경이다. 별도의 결속력/사망 if를 복제해 우회하지 않는다. 추가 파일 1개 및 내부 선택적 인자·호출 전달만 늘리는 [개정안](2026-11-02-movement-profile-read-tracking-design.md#9-mb1-사전-대조-보완--결속력-방어의-간접-읽기-후속-지시로-구현)을 작성했다.

사전 대조 시점에는 기존 범위 18 C#을 19 C#으로 늘리는 안의 사용자 확인을 기다렸다. 후속 최종 진행 지시로 이 보완을 구현했으며 현재 결과는 §12를 따른다.
