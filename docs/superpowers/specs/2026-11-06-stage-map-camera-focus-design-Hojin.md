# 스테이지 노드 선택과 맵 복귀의 카메라 정렬 설계

- 작성일: 2026-11-06
- 상태: [구현 계획](../plans/2026-11-07-stage-map-camera-focus-plan-Hojin.md)의 Phase 1 코드·정적 검토·문서 인계를 완료하고 독립 검토 지적 2건을 보완했다. **컴파일 미확인**, 사용자 Unity 확인은 해당 계획 U1~U8을 따른다.
- 목적: 노드를 선택해 이동하거나 전투에서 맵으로 돌아왔을 때, 플레이어와 앞으로 선택할 노드가 함께 보이게 한다.
- 관련 기능: [챕터 최초 맵 진입 연출](2026-11-06-stage-map-intro-design-Hojin.md). 최초 연출의 구현/확인 상태는 [별도 계획](../plans/2026-11-06-stage-map-intro-plan-Hojin.md)을 따른다.

## 1 사용자 선택과 적용 시점

사용자는 플레이어를 화면 아래쪽에 두고 다음 진행 구간을 더 넓게 보여주는 구도를 확인했다. 전투 후 스테이지 선택으로 돌아올 때의 카메라 정렬은 로딩 화면에 가려진 동안 끝내고, 노드를 클릭해 이동할 때는 플레이어와 카메라가 함께 부드럽게 이동하는 **2번 방식**을 선택했다.

동행은 캐릭터가 **뜨기 시작하는 순간부터 수평 이동을 거쳐 착지할 때까지의 전체 이동 시간**에 적용한다. 카메라는 도착할 플레이어의 앞쪽을 비추는 구도로 이동한다. 정상 흐름은 **유효한 노드 클릭 → 캐릭터·카메라 이동 시작 → 둘 다 이동 완료 → 팝업 표시 또는 전투 진입**이다. 카메라만 먼저 이동을 끝내고 캐릭터가 출발하는 별도 대기는 추가하지 않는다.

| 시점 | 보여줄 동작 |
|---|---|
| 전투 노드 클릭으로 표시 이동 시작 | 상승·수평 이동·하강 전체에 카메라 동행. 캐릭터 착지와 카메라 정렬이 모두 끝난 뒤 덱 출전 화면을 열고, 출전 요청 수락·준비 뒤 전투 진입 |
| 상점·회복 등 비전투 노드 클릭 | 기존 요청이 수락되어 실제 마커 이동이 시작될 때 카메라도 시작. 캐릭터 착지와 카메라 정렬이 모두 끝난 뒤 해당 팝업 표시 |
| 같은 챕터의 전투 종료 후 맵 복귀 | 로딩 가림 아래에서 Buffer의 현재 플레이어 위치로 즉시 정렬한 뒤 맵 공개 |
| 상점·회복 완료 | 선택할 때 맞춘 구도를 유지. 팝업 종료를 위한 추가 카메라 이동이나 페이드 없음 |
| 새 Run·챕터의 최초 진입 | 기존 노드 낙하·선·보스 왕복 연출 우선. 이 기능이 최초 왕복의 시작/복귀 구도를 덮어쓰지 않음 |

여기서 클릭은 기존 입력의 유효한 누름/뗌으로 선택이 성립한 경우다. 누르는 순간, 배경 드래그, 갈 수 없는 노드, 거절된 비전투 요청에는 카메라 이동을 새로 시작하지 않는다. 현재 Core의 선택 규칙이나 전투 출전 확정 순서를 변경하지 않는다.

## 2 비교한 방식

| 방식 | 특성 | 결정 |
|---|---|---|
| 클릭 후 화면 가림 → 카메라 정렬 → 플레이어 이동 | 카메라 이동 자체를 감출 수 있지만 노드 선택마다 화면 전환이 추가됨 | 선택하지 않음 |
| 클릭으로 시작한 플레이어 이동의 전 구간에 카메라 동행 | 맵을 계속 보면서 현재 위치와 다음 구간의 관계를 확인하고, 두 표시가 함께 끝남 | **사용자 선택** |
| 카메라를 먼저 앞쪽으로 이동한 뒤 플레이어 출발 | 이동 전에 앞쪽 시야를 확보하지만 캐릭터 출발 전 대기 단계가 추가됨 | 사용자가 제시한 대안. 이번에는 전 구간 동행을 채택 |

전투 복귀의 로딩 중 정렬은 위 클릭 표현과 별개로 유지한다. 맵이 보인 뒤 뒤늦게 플레이어 쪽으로 이동시키는 복귀 연출은 넣지 않는다. 매 프레임 플레이어를 계속 화면에 고정하는 기능도 아니며, 선택 이동이 끝나면 일반 맵 조작으로 돌아간다.

## 3 구도 설정과 전체 이동 시간의 동기화

전체 이동 시간에 동행하고 두 표시가 모두 끝난 뒤 다음 화면을 여는 동작은 §1의 사용자 선택을 따른다. 목표 화면 높이·보간 곡선·입력 유지 정책과 구체적인 연결 방법은 아래의 Codex 제안이다.

- View SO에 별도 `Camera Focus` 설정을 두고 `Enabled=true`, `Player Viewport Y=0.35`를 초기값으로 제안한다. 화면 아래가 0, 위가 1이며 플레이어의 바닥 위치를 기준으로 한다. Y는 유한한 0~1 사이의 값이어야 한다.
- 기존 카메라 각도·렌즈·가로 구도를 유지하며 맵 진행축으로만 움직인다. 목표 구도는 실제 노드의 월드 위치를 준비된 카메라 구도에 투영해 계산한다. 보스나 맵 끝에서는 기존 이동 범위가 우선하므로 항상 정확히 35%에 오지는 않는다.
- 목표 화면 높이에 도달하려면 필요한 축 투영이 유효해야 한다. 진행축이 화면 높이를 바꿀 수 없거나, 허용 범위로 제한한 뒤 대상이 화면 밖에 남는 구성은 대상 노드와 구도를 명시한 구성 오류로 다룬다. 임의 회전·줌으로 보정하지 않는다.
- 클릭 직전의 실제 카메라 구도에서 부드럽게 출발한다. 사용자가 수동으로 둘러본 뒤 클릭해도 시작 위치를 먼저 순간 이동시키지 않는다. 목적 노드에 착지했을 때 최종 구도에 도달하고 그대로 유지한다.
- 별도 카메라 이동 시간을 만들지 않는다. 상승·수평 이동·하강을 모두 포함한 `ChessPieceMotionSettings.TotalSeconds`를 공통 기간 D로 사용하고, 같은 `IDelayService.CurrentTime`의 시작 시각 S로부터 전체 진행률 `u = Clamp01((CurrentTime - S) / D)`를 구한다. 카메라만 `deltaTime`을 별도로 누적하거나 `Time.time`·unscaled 시간으로 진행시키지 않는다.
- 카메라는 시작 offset에서 목표 offset까지 `3u² - 2u³`으로 부드럽게 보간하는 안을 사용한다. 상승 중에도 출발하고 하강 중에도 이어서 움직여 착지 시 목표 구도에 도달한다. 수평 위치만으로 진행률을 계산해 상승 때 멈추거나 하강 전에 끝내지 않는다. 카메라의 목표는 바닥에 있는 목적 노드로 계산하여 캐릭터의 높이·모델 보정에 따른 상하 흔들림은 만들지 않는다.
- 이동 거리 0으로 기존 마커가 즉시 완료되면 카메라도 같은 도착 처리에서 최종 구도를 한 번 적용한다. 시작 시각·기간·진행률은 유한해야 하며, 실제 이동의 D는 양수여야 한다. 큰 프레임 지연으로 끝 구간을 건너뛰어도 최종 구도를 정확히 적용한다. 매 Tick의 배열·delegate 생성이나 씬 검색을 추가하지 않는다.
- 공통 시간의 끝에 도달한 사실만으로 다음 화면을 열지 않는다. **마커의 실제 완료 확인과 카메라의 최종 구도 적용 성공이 모두 필요**하다. 한쪽이 실패하거나 문맥을 잃으면 팝업 표시·전투 표시 완료 전달을 진행하지 않는다. 카메라 목표가 시작 구도와 같아 이동량이 0인 경우에도 마커 완료 조건은 유지한다.
- 자동 이동 중 수동 드래그·휠·에디터 Alt는 기존 이동 입력 차단을 유지한다. 앞서 논의했던 '수동 조작으로 자동 이동을 중단'하는 안은 사용자 선택이 없으므로 채택하지 않는다. 설정 창에서는 기존 마커 이동과 카메라가 함께 정지하고, 완료 뒤 새 조작을 허용한다.

`Camera Focus.Enabled=false`는 이 기능의 클릭 동행과 복귀 정렬만 생략한다. 최초 맵 진입 연출의 별도 설정·이력·입력 차단은 유지한다. 일반 상점/회복 종료와 맵 갱신마다 다시 정렬해서 사용자의 수동 구도를 덮어쓰지 않는다.

## 4 현재 코드와 연결 경계

현재 전투 노드는 `StageCombatDeparture.TryBegin`에서 클릭 후 먼저 마커를 이동시키고, 착지 후 덱 출전 화면을 연다. 실제 선택 요청은 출전 확정 뒤 제출하므로 이때의 마커·카메라는 **선택 전 표시**다. 상점·회복은 `StageMapNodeMovement.PresentAccepted`에서 수락된 요청의 이동을 시작한다. 두 경로를 하나의 'Core 현재 위치 변경' 사건으로 합치지 않는다.

| 부품 | 맡을 일 |
|---|---|
| 기존 `StageMapCameraDrag` | 유일한 Catalog 핸들·offset 소유 유지. 최초 왕복과 새 정렬이 같은 자동 조작 소유권을 사용하고 동시에 쓰지 못하도록 함 |
| 새 StageMap 전용 카메라 정렬 부품 | 목표 구도 계산, 전체 이동의 시간 진행률 소비, 시작 구도 보관과 완료/취소. 필요한 좁은 카메라 조작 계약만 받음 |
| `StageCombatDeparture` | 클릭으로 시작한 두 표시의 시간과 완료를 연결. 둘 다 완료된 뒤 출전 화면을 열고 요청 제출·대기·수락·취소를 구분 |
| `StageMapNodeMovement` | 수락된 마커 이동과 카메라를 연결하고, 둘 다 완료된 뒤에만 팝업 복원 허용/전투 표시 완료를 전달 |
| `StageMapViewScope`·Scene·로딩 준비 | 유효한 Run/맵/준비 세대와 준비 원인·가림 문맥을 확인하고 복귀의 1회 정렬을 연결. 표시 수명 정리 |
| 기존 View Factory·설정 SO/Data | 부품 생성/주입과 설정 변환. 카메라 계산이나 진행 판정은 넣지 않음 |

각 StageMap 이동 주체는 기존 `ChessPieceMotion`에 넘기는 것과 **동일한 설정 객체의 TotalSeconds**를 사용한다. `Begin` 바로 직전에 Delay의 현재 시각을 한 번 읽어 시작 문맥으로 잡고, 같은 호출 흐름에서 마커와 카메라를 시작한다. 이 시간 getter와 현재 경로 준비는 시간을 진행시키지 않으므로 마커 예약과 같은 시작 시각을 사용할 수 있다. Begin 실패나 재진입으로 문맥을 잃으면 카메라도 시작/적용하지 않고 해당 시도의 자원을 정리한다.

활성 이동의 View Tick에서 같은 Delay 시각으로 전체 진행률을 계산해 카메라에 전달한다. Global Delay의 마커 갱신 뒤 두 표시를 확인하고, 완료 프레임에는 최종 구도를 적용한 뒤 다음 화면에 완료를 전달한다. 기존 `ChessPieceMotion`·경로·공용 Delay 구현을 수정하거나 마커 경로 수식을 카메라에 복제하지 않는다. 현재 플레이어의 확정 위치는 Buffer, 선택 전 출전 목적지는 기존 Departure, 표시 배치는 기존 NodeView/Display가 각각 원본이다. 카메라 부품이 전체 Services나 Core를 조회하거나 Buffer에 진행을 쓰지 않는다.

전투 복귀는 기존 순서인 AfterLoad 카메라 연결 → 범위/에디터 초기 구도 → 맵 준비 → Reveal을 이용한다. 준비 원인은 **로딩을 동반한 씬 진입 / 화면에 보이는 같은 맵 재그리기 / 개발 직접 진입**으로 구분한다. `StageMapLoadingPreparation.Begin(bool isCovered)`가 받은 가림 정보와 준비 원인을 해당 Scope/준비 버전에 연결하며, 단순히 `IsLoading`이나 '새 준비'만으로 복귀 정렬을 허용하지 않는다.

최초 Intro가 재생될지/생략될지는 Intro의 기존 준비 결과가 결정한다. **유효한 가림 문맥의 씬 진입이며 Intro가 생략된 경우**에 현재 노드 구도를 한 번 적용한다. 이 준비는 가림 문맥 확인과 정렬까지 끝나야 Complete가 되며 일반 Scope Tick이 먼저 완료를 게시해 정렬을 건너뛰지 않게 한다. 핸들 미준비는 정상 Pending으로 같은 준비 버전·원인을 유지한다.

`RequestMapRedraw`를 호출하는 상점·회복 종료와 개발 다시 그리기는 같은 맵 재그리기로 처리한다. 앞선 씬 진입의 가림 문맥을 재사용하지 않고, 현재 카메라 구도를 유지하며 새 정렬을 하지 않는다. 일반 Tick의 반복 RefreshDisplay에도 정렬을 넣지 않는다. 가림이 없는 개발 직접 진입은 명시된 개발 진입의 최초 준비에서만 적용할 수 있으며 운영 복귀의 '유저에게 이동이 보이지 않음' 보장과 구분한다. 공용 Loading 구현이나 새로운 화면 가림 기능은 추가하지 않는다.

## 5 완료 취소와 소유권

- 한 선택 이동의 시작 snapshot과 토큰은 Run·맵·Scope·선택 문맥에 귀속한다. 새 연결이 생기면 이전 토큰의 적용/복원은 무효다. 최초 Intro와 선택 이동의 자동 소유권이 겹치는 호출은 기존 상태 경계에서 차단한다.
- 같은 챕터·노드 번호라도 RunId나 맵 준비 버전이 바뀌면 이전 이동이다. Scope의 일반 CanWork는 Run 검사로 대신 쓰지 않는다. 이동 시작에 캡처한 문맥을 카메라 적용·완료·취소 복원 전에 확인하고, View Tick보다 먼저 실행되는 마커의 Delay 콜백도 StageMap 전용 전달 부품에서 검사한다. 이 부품은 기존 Delay의 시각·기간을 그대로 사용하며 공용 Delay·ChessPieceMotion을 수정하거나 새 시계를 만들지 않는다.
- 비전투 이동은 마커 착지와 카메라 최종 적용이 모두 끝난 뒤 자동 소유권을 반환하고 기존 이동 완료를 게시한다. 그 이후에만 상점·회복 팝업을 표시한다. 팝업을 닫을 때 추가로 카메라를 옮기지 않는다. 요청 수락 전 거절은 카메라를 건드리지 않는다.
- 전투 선택 전 이동도 두 표시가 모두 완료된 뒤에만 덱 출전 화면을 연다. 이동 완료는 출전 수락이 아니므로 취소용 시작 snapshot과 자동 소유권을 계속 보관한다. 출전 버튼의 `Submit`은 요청 제출일 뿐이며 **Submitted/Pending 동안에도 복원 정보와 토큰을 유지**한다.
- 같은 요청의 실제 수락·준비가 확인된 `CompleteAccepted`에서 현재 구도를 유지하는 처리를 확정하고 자동 소유권을 반환한다. 두 표시의 완료 전에 전투 표시 완료를 전달하지 않는다. 덱 출전 취소·요청 거절·실행 전 취소는 기존 마커 원위치 복원과 같은 처리에서 클릭 전 구도를 복원한다. 수락 확정 뒤의 정상 해제는 클릭 전 구도로 복원하지 않는다. 사용자에게 새로운 복귀 대기 연출을 추가하지 않는 제안이다.
- 같은 전투 요청의 수락 결과가 뒤늦게 도착해도 클릭 때 수행한 카메라 이동을 두 번 시작하지 않는다. 기존 Departure가 인수한 요청을 기준으로 중복을 막는다.
- 씬 이탈·Run/맵 교체·오류는 세대를 먼저 무효화하고 카메라 제어권/참조를 해제한 뒤 표시와 Catalog lease를 정리한다. Supersede된 이전 Scope는 새 카메라에 복원하지 않는다. 정리 실패를 정상 완료로 바꾸지 않고 기존 오류 경계에 보고한다.
- 자동 정렬은 수동 offset 상태도 함께 맞추되 EditorPrefs·사용자 저장 구도에는 쓰지 않는다. 완료 뒤 같은 PreviewFraming 재적용이나 첫 수동 조작으로 카메라가 튀지 않아야 한다.
- 수동 인계에는 Alt뿐 아니라 Inspector의 Position/Rotation/Size 직접 편집과 잠금 해제도 포함한다. 현재 표시 구도를 읽어 편집을 시작하며 Size/회전만 바꿔도 위치가 과거 값으로 돌아가지 않는다. Inspector Repaint는 저장하지 않고 자동 이동 중 직접 편집·확정도 차단한다. 사용자가 명시한 확정은 기존 저장 경로를 유지하고, 조정 취소 및 잠금은 확정 구도로 돌아가는 의도적인 동작으로 구분한다.

## 6 범위와 구조 원칙

수정 범위는 StageMap View, 해당 설정 SO/Data·운영 에셋, 기존 View Factory와 관련 문서다. Core·Buffer 구현·FieldCamera·Architecture·공용 Camera/Loading/Delay·전투 View·최초 노드/선 표현과 원본 에셋을 수정하지 않는다. 새 서비스·입력 Layer·UI·상시 추적·회전·줌·페이드는 추가하지 않는다. 다른 작업자의 변경과 선행 Intro의 미확인 상태를 보존한다.

원칙은 [프로젝트 적용 기준 §4 및 §4.6](../handoffs/2026-09-30-combat-view-design-session-handoff.md#4-반드시-지킬-설계-원칙), [JMH 지침 §2·§23·§26~28](../framework/Framework%20Development%20Guidelines.md), [FW 계약](../../../Assets/ProjectL/Script/Systems/Documentation/framework-programmer-guide.md)을 따른다.

| 기준 | 설계에서의 적용 |
|---|---|
| SSOT | 확정 진행=Buffer, 선택 전 목적지=Departure, 시간=기존 Delay의 현재 시각과 동일 이동 설정의 TotalSeconds, 구도 설정=View SO, 핸들/offset=CameraDrag. 별도 누적 시계·이력·현재 노드 사본을 추가하지 않음 |
| SRP | 정렬 계산은 전용 부품, Scope는 수명 연결, Factory는 생성/주입 |
| OCP | 기존 StageMap 내부 연결 지점으로 확장하고 공용 서비스에 기능 분기 추가 없음 |

## 7 구현 뒤 사용자 확인

1. 전투와 비전투의 유효한 클릭에서 캐릭터가 뜨기 시작할 때부터 착지할 때까지 카메라가 함께 움직인다. 수평 이동 전에 멈춰 있거나 하강 전에 정렬을 끝내지 않으며 착지 시 다음 노드가 보이는 구도를 유지한다. 누르기만 한 상태·배경 드래그·무효 선택에는 시작하지 않는다.
2. 마커 완료·카메라 완료를 각각 확인하기 전에는 덱 출전 화면·상점/회복 팝업·전투 표시 완료가 먼저 나가지 않는다. 큰 프레임 지연·이동 거리 0·카메라 이동량 0에서도 최종 구도 적용과 완료 전달은 한 번이다.
3. 상점/회복의 요청 대기·거절, 전투 출전 취소·Submit 후 Pending 중 거절/실행 전 취소, 실제 수락·중복 관찰을 구분한다. Pending 중에는 클릭 전 구도로 복원할 수 있고 수락 뒤에는 원위치 복원이나 이중 이동이 없다.
4. 전투 복귀는 로딩 가림이 걷히는 첫 화면부터 현재 위치에 맞는다. 정상 Pending 중 준비 원인·버전은 유지된다. 매 Tick·상점/회복 종료의 RequestMapRedraw·개발 다시 그리기는 복귀로 오인하지 않으며 수동 구도를 덮지 않는다.
5. 최초 노드 낙하·선·보스 왕복의 시작 구도, 완료 조건, 이력, 입력 차단이 유지된다. 신규 정렬과 자동 소유권이 겹치지 않는다.
6. 수동으로 먼 곳을 본 뒤 클릭, 화면 비율/에디터 구도 변경, 갈림길·시작/보스 경계에서 순간 튐과 화면 밖 대상이 없는지 확인한다.
7. 상승·수평 이동·하강 각각에서 설정 창을 열면 둘 다 정지하고 닫으면 함께 이어진다. 중도 취소·씬 재연결·Run/맵 교체·카메라 핸들 지연에서 이전 세대 쓰기와 잠금 잔존이 없다.
8. 새 SO 설정을 끄거나 목표 높이를 바꾼 경우와 기존 `DataBaseAssetTests`를 사용자가 Unity에서 확인한다. View 시험 코드·시험 도우미 작성, MSBuild·Unity 자동 실행, 커밋·push는 하지 않는다.

## 8 보완 기록

- 2026-11-06 사용자 요청: 노드 클릭에 따른 캐릭터의 상승·수평 이동·하강 전 구간에 카메라가 동행하고, 두 표시가 모두 완료된 뒤 팝업/전투로 넘어가도록 명시했다. 기존 평면 위치 기반 진행률을 전체 이동 시간 기준으로 교체했다. 카메라 선행 방식은 비교안으로 남겼다.
- 같은 날 검수 2건 반영: 로딩을 동반한 씬 진입과 화면에 보이는 맵 재그리기의 원인/가림 문맥을 분리했다. 출전 Submit 뒤 Pending 동안 복원 snapshot/token을 유지하고 실제 CompleteAccepted에서 확정하도록 경계를 명시했다.
- 2026-11-07: 별도 구현 계획을 Phase 1개·Task CF1~CF7로 작성했다. 가림 없는 개발 직접 진입은 초기 준비를 유지하되 선택 사항인 자동 정렬은 이번 구현 계획에서 생략한다. 구현 상태와 사용자 확인 기록은 해당 계획에서 관리한다.
- 같은 날 계획 검토 보완 2건: Run/준비 버전 검증을 이동·Delay 콜백에 연결하는 계약과 Inspector 직접 편집의 현재 구도 인계를 계획에 구체화하고, 위 수명·편집 조건에도 반영했다. 게임 코드 구현은 시작하지 않았다.

2026-11-07 사용자의 Phase 1 실행 지시로 코드·운영 SO 연결을 작성했다. 검토 결과와 최종 인수 상태는 구현 계획 §5에서 관리한다. **컴파일 미확인**이며 Unity 사용자 확인 완료를 뜻하지 않는다.
