# Movement Undo Restoration Design

**Date:** 2026-10-30. **Status:** Updated after U0 for the confirmed input-independent Core contract; this revision is documentation only. U0 evidence is recorded in the plan; U1-U3 implementation, runtime/test/asset/scene changes, commit and push are not authorized by this revision.

**Implementation plan:** [Movement undo restoration](../plans/2026-10-30-movement-undo-restoration-plan.md).

**Current delivery scope:** Core rules, immutable public API, existing Buffer transaction/validation and a concrete View handoff. The user is the Core programmer. View implementation, UI/scene wiring and presentation acceptance belong to the View owner and do not block a verified Core delivery.

## 1. Intent, decisions and boundaries

Restore cancellation of a mistaken, already executed player movement using the former develop implementation as evidence, adapted to current controller turns, cost-free actions and atomic Buffer publication. This is not a rewind of combat or a restoration of the old AP system.

| Decision | Status |
|---|---|
| Category-configured maximum movement distance; one ordinary move and one ordinary attack per unit per owning-side turn; no move after attack | Confirmed in the preceding cost-removal work. Preserve R4. |
| End the player turn without exhausting actions | Confirmed; undo availability must never become an end-turn prerequisite. |
| Restore original position and movement opportunity; attack commits movement | Confirmed intended basic undo behavior. |
| A movement that causes damage, acquisition or a trait effect is committed and cannot be cancelled | Explicit user answer in this design session. Do not implement full effect rollback. |
| Adapt develop code to the current system | Explicit request. Selective port, not a branch merge or whole-file restoration. |
| A attacks after A and B move: only A's move is committed; B may still undo | Explicit user answer. An attack is not a blanket commit of other units' moves. Independent invalidation conditions remain explicit below. |
| Cancelled movement is removed from the distance statistic | Explicit user correction. Future distance-based XP must not be inflated by move/cancel cycles. No distance-based XP formula is implemented here. |
| Return may be displayed at the origin without reverse walking | User agrees with this presentation direction but assigns implementation judgment to View. Core publishes facts, not timing or animation instructions. |
| Core exposes one explicit movement-undo query/command contract, independent of the input gesture | Confirmed after U0. Planning/View decide buttons, shortcuts and whether to support selecting the saved origin. Origin-click undo is optional, not a Core acceptance requirement. |

**Confirmed input boundary:** A saved checkpoint determines the return placement for an explicit UndoMove; it does not give that cell a global click meaning. Core neither interprets pointer input nor converts an ordinary Move/Attack into undo because its target matches an origin. Tile-targeted items keep their own action semantics. No origin-click-specific command, preview lane, service or duplicate checkpoint state is required. Planning/View own input-mode priority, selected-actor/request lifetime and any optional origin-click mapping described in section 6.

**Confirmed attack scope:** A and B may each retain one reversible move. A's attack commits A's move; it does not by itself invalidate B's record. An actual effect on B invalidates B. Selecting a unit, changing aim, requesting previews and rejected commands do not commit movement. Replace the earlier blanket shared-world invalidation proposal with per-record actor/origin dependency checks: an unrelated attack, kill, reward, soul creation or terrain change elsewhere must not commit B's move.

**Confirmed distance accounting:** Category maximum movement allowance and `CharacterStageRecord.DistanceMoved` are different facts. Successful undo restores the movement opportunity with the full current category allowance and subtracts exactly the statistic increment of the cancelled move. Example: a unit with maximum range 4 and prior stage distance 10 moves 3 cells (distance 13), undoes (distance 10, next move may use up to 4), then moves 2 cells (distance 12). A move/cancel cycle has zero net statistic gain. Committing an already recorded move does not add its distance again; rejected undo subtracts nothing. Return animation/path is never added as movement. Preserve all other stage-record fields, XP, resources and turn counters. Future distance-based XP must consume this cancellation-corrected value at its own settlement boundary; no XP formula or XP rollback is added here.

Non-goals: attack undo; enemy undo; a stack of moves per unit; redo; AP/budget/refund revival; buff/debuff redesign; undo-specific traits; distance-based XP implementation; changing movement range, attack count, repeated-cell rejection, terrain behavior or reward formulas; enabling a second ordinary move before a successful undo; new Job/Flow/Framework systems; View code, UI/scene/prefab or presentation implementation; mandating origin-click input. Do not touch FieldCamera/Architecture, delete missing-script assets, or alter unrelated local changes.

## 4. Gameplay contract

### 4.1 Eligibility and cancellation

Only a living player field unit in the active player combat turn may undo its own recorded ordinary movement. The record must belong to the current battle, controller-turn sequence and original move command. The unit must still have `ActionUse.Moved` and exactly the expected post-move facts. Enemy/automatic, deployment, reserve, dead, finished-battle and stale requests fail without mutation.

Only a move with at least one actual entered path cell can create a record. A safe partial path may create one if the stop is only `NextStepInvalid`; Completed is also allowed. Forced relocation, falling, death, terminal results and other stop reasons do not. Preserve repeated-cell rejection and reject a second ordinary move while ActionUse is Moved. A closed ordinary loop or two ordinary moves back to the checkpoint is not a supported way to create a same-cell undo case. Check eligibility from the checkpoint provenance, actual entered distance, effects and current facts; endpoint equality alone grants no permission.

Successful undo restores the actor's anchor/rotation/occupied cells and `ActionUse` from Moved to Available, subtracts the checkpoint's RecordedDistance from its current stage distance, consumes that record, and appends one result and one `Returned` event. Keep HP, combat stats, traits, items, effects, damage/kill statistics, XP, resources, random states, turn counters and other units unchanged. No movement-entry/arrival, pickup, trait trigger, reaction, reward or forward-distance tally runs for the return. An ordinary attack can subsequently be made once, or another move can be selected using the full unchanged category maximum distance; the cancelled path does not reduce that allowance. A second undo with the consumed token is rejected and cannot subtract distance again.

Destination must be in bounds and currently enterable for the same footprint using existing placement/entry rules. An occupied origin is a temporary rejection: do not move the occupant, choose a substitute cell or destroy an otherwise valid checkpoint. If the blocker leaves without invalidating the record, return can become available again. Only current single-cell ordinary movement is supported; do not silently broaden footprint/movement-method support.

Before permitting return, create a pure hypothetical current-world placement at the origin. Resolve its position modifier with `PositionTileModifierCalculator` and call `TraitPresenceReconciler.Calculate` on the proposed character layout. If normalization or any character's passive facts would change beyond the permitted placement/action reset and exact distance reversal, reject with `ReturnWouldCauseEffect`. Do not apply these hypothetical effects or emit their events. This is necessary when another unit moves near the empty origin without changing the mover's current facts. It reuses existing passive rules and does not run traversal, arrival, pickup or trigger processing.

### 4.2 What makes a move irreversible

Evaluate the final command after movement completion, passive reconciliation, record settlement and pending reactions. The allowlist is deliberately small:

1. Only the moving character changes semantically, and only its placement, Available -> Moved and the ordinary distance statistic may differ.
2. Its stage-record delta is exactly the executed voluntary path distance for an owned ally; damage taken/dealt and kills are unchanged. Other character facts are value-equal.
3. State other than undo metadata is value-equal, including environment, progress/RNG, structures, thorns, turn, trait-turn, rewards and allocation. Soul field/counts, main persistent facts, owned records and inventory/currency are unchanged semantically. No-op proposals do not count as changes merely because a new object was allocated.
4. Ordered events contain only ordinary `Moved` evidence for that actor. Any supported non-ordinary-move evidence seals the new move even if net values later cancel out. Unsupported event representations are contract errors handled before publication under section 5.1a; they are never silently ignored or interpreted as a global commit. This closes net-zero side-effect loopholes without hiding missing event coverage.

Implement the comparison once in `MovementUndoPolicy`; use existing With/SameValues contracts to normalize the few permitted differences rather than copying every trait's implementation. Add shape-guard tests so newly introduced facts cannot silently escape eligibility checks. New effects are sealed by default; supporting cancellation of them is future explicit work.

Consequences must be visible in tests and handoff: Acceleration gain, StationaryFire's moved-state change, DustScreen/GroundCompaction trails, weak-ground entry changes, collection and even passive presence changes prevent cancellation. A trait merely being equipped does not prohibit undo; an actual effect/event or fact change does. The rule applies to actual execution, not a promise inferred from an earlier preview.

### 4.3 Lifetime and confirmed per-unit attack scope

| Transition | Pending records |
|---|---|
| Safe player move | Add the mover's new record; retain other unchanged units' records. |
| Actor attacks, equips/unequips/replaces an item, leaves the field, dies or changes other facts | Remove that actor's record. A rejected command preserves it. |
| Another unit attacks without changing this actor or shared dependencies | Retain this actor's record, as explicitly selected by the user. Do not globally clear records just because the command kind is Attack. |
| Accepted command changes shared world facts | Remove only records whose actor or saved origin dependencies changed. A remote kill/reward/soul or unrelated terrain change preserves B. A new/changed source at B's origin invalidates B. Mere destination occupancy remains a temporary rejection. Never revert shared world facts. |
| Actor facts diverge from recorded expected facts, including passive aura changes | Remove that record. A later return to the same values must not revive an expired record. |
| Undo succeeds | Consume only its token; retain other valid records. |
| Preview, selection, aim change, rejected input | No mutation of gameplay records. |
| EndPlayerTurn, controller change/start, night/deployment transition, battle completion/abandon/end/new battle | Clear all records in the existing lifecycle/publication boundary. |
| Non-command CharacterChanges / SoulActionChanges | Invalidate only records whose actor facts or original-cell source facts actually changed, in the same transaction. Value-equal/no-op proposals and unrelated changes preserve records. Failed preparation changes nothing. |
| Quantity-only inventory grant | Preserve all records. Inventory quantities are not a dependency of position/action/distance cancellation. Equipping or activating an item is a different operation with actual character/effect evidence. |

No undo crosses a turn or battle. RecordInputOnly cannot fabricate an authoritative checkpoint and does not offer executed-movement undo. Unsubmitted path editing/cancel remains the existing View-only operation.

## 5. State, calculation and publication

### 5.1 Minimal history owned by the existing combat state

Add immutable `MovementUndoCheckpoint` with `BattleInstanceId`, `ControllerTurnSequence`, `MoveCommandNumber`, `ActorId`, original `Anchor`, `Rotation`, copied `OccupiedCells`, `RecordedDistance`, `OriginFacts` and `ExpectedActorAfterMove`. RecordedDistance is the move's actual increment to StageRecord.DistanceMoved, verified against input/final facts and actual entered path cells (zero for an unowned actor whose statistic is not tracked). It is not the requested path length, category allowance or the actor's cumulative distance. ExpectedActorAfterMove is an immutable historical expected-value guard, never an alternative live character or a snapshot to reinstall. Restore only placement/action use and reverse RecordedDistance. Validate positive identities/command number, nonnegative recorded distance, matching actor and single-cell shape.

`MovementUndoOriginFacts` is a copied immutable dependency snapshot for the one original cell, not a second world store. Capture deterministically ordered existing tile facts at that cell (including inactive/hidden sources), their relevant terrain-binding membership, thorn fact and soul entries. Compare with the final projected world after every accepted command and again during evaluation. Source addition/removal/value changes invalidate that record; changes elsewhere do not. Do not snapshot global RNG, currency or all characters as a blanket expiry key. Occupancy and geometry-dependent passive rules use current facts in section 4.1 rather than freezing all occupants. Keep origin snapshots internal to the Core calculation contract; public availability exposes no hidden source details.

Add `CharacterStageRecord.UndoMovement(int distance)` as a pure immutable value operation: reject negative values and values greater than DistanceMoved, return self for zero, otherwise subtract exactly distance and preserve damage/kill fields. It grants no publication authority. Do not permit negative arguments to Add, weaken IsAtLeast globally, or expose a direct mutable statistic setter.

Retaining an existing checkpoint also inspects ordered effect evidence, not only final equality: damage/healing, trait/status effects or forced movement affecting its actor, or source/collection changes affecting its saved origin, invalidate it even when later steps restore equal final values within the same composed command. MovementUndoPolicy consumes the uniform derived evidence in section 5.1a, not individual trait/artifact/soul event payloads. Unrelated actor and remote evidence does not seal the record.

Add immutable `MovementUndoState` containing a deterministic, copied collection of at most one record per actor, with `Empty`, lookup and value equality. Add optional trailing `movementUndo` to `CombatCommandState`; update With, SameValues, composition, copies and shape guards. Preserve metadata through internal movement/attack projections; change it once at the outer command boundary. Do not store a second record in CharacterBuffer, View, Core services or the result-history list. No whole-world clone, per-frame history or new Framework service.

`MovementUndoPolicy.Reconcile(CombatCommandTransition resolved)` derives final metadata from the original input records and the fully resolved result. Run it after `BossRoarCalculator.ApplyPendingReactions` for normal Calculate and Advance; never midway through sub-actions. Rejected commands preserve input metadata. Internal preview projections never create authoritative records. Factor existing state equality so eligibility can compare gameplay facts excluding undo metadata without duplicating the equality rules.

### 5.1a Effect evidence contract and ownership

Add a small pure reader at the existing immutable combat-contract boundary, `C/Contracts/Combat/CombatChangeEvidenceReader.cs`, and its immutable value `CombatChangeEvidence.cs`. This is a value decoder, not a service, event bus, registration framework or second event stream. No new authoritative state or serialized/persisted evidence list is created. Read existing source events on demand; the original ordered events remain the only playback facts.

`CombatChangeEvidence` contains `Kind`, copied/deduplicated `AffectedEntityIds` and `ChangedSourceCells`. Kind is one of `OrdinaryMove`, `Return`, `Action`, `Effect`, `Lifecycle`, `Observation`. Entity IDs describe actual action owners/effect recipients; source cells describe actual environment/thorn/soul-source changes relevant to saved origins. They are not targeting ranges, camera areas, every cell crossed by another unit, or every entity mentioned for display/credit. Data carries no CanUndo/InvalidateAll policy flags. Only Lifecycle permits the existing turn/battle-wide reset policy.

Required pure entry points:

- `ReadAll(IReadOnlyList<CombatEvent> facts) -> IReadOnlyList<CombatChangeEvidence>`: validates supported concrete-type/Kind pairs and required wrapper companion facts in the same ordered stream, then returns evidence in that order. Single-event decoding is a private helper, not an API that promises stream validation. Nested immutable activation/damage/source records are interpreted only here; no rule execution, random draws, callbacks or access to a Buffer/service. Missing required companions fail before publication, rather than relying only on producer tests.
- `ReadCharacterChanges(IReadOnlyList<CharacterCombatFacts> before, IReadOnlyList<CharacterCombatFacts> after) -> CombatChangeEvidence`: compares actual published actor facts and the validated prepared final views, not merely CharacterChanges.Characters. Return Effect with changed/created/removed entity IDs; value-equal allocations yield empty scope. This covers Main-only persistent HP updates that rebuild an actor even when Characters is empty, without a second roster lookup or requiring redundant CharacterStateChange rows.
- `ReadChanges(SoulFieldChange change) -> CombatChangeEvidence`: returns Effect with cells of actually added/removed/changed soul entries, from both expected and final entries as applicable. Quantity/metadata changes of a soul at the saved origin matter; a remote soul does not. Use existing fact equality, not reference equality or every cell in the whole field snapshot.

| Existing event family | Evidence obligation |
|---|---|
| Character movement/placement/return, health, trait-state, held-state, mark, pull, fall, item and experience events | Decode exact affected entity IDs from immutable fields. Ordinary voluntary Moved and Returned are distinguished from forced relocation/effects. An item grant is not an item-equipment/activation event. |
| Movement-source, object creation/activation, thorn and soul events | Decode actual affected entities and changed source cells. Compare each event's own expected/final values; a later restoring event does not erase earlier evidence. Activation at a source and collection are semantic effects even if final command values match. |
| Attack, effect/trait/category/artifact activation, roar, obstacle and gimmick wrappers | Use their typed action/recipient/source facts and the producer's documented companion events. Do not mark every attack/roar AreaCell as changed. A wrapper is Observation only when its actual gameplay changes are fully covered by other typed facts in the same ordered stream; characterize that producer guarantee with tests. If necessary evidence is absent, extend that existing fact narrowly instead of reconstructing a trait's behavior in the reader. |
| Controller/night/combat boundary and terminal outcome events | Lifecycle, following the existing owning boundary. No unrelated event may be classified Lifecycle merely to simplify invalidation. |

Unsupported concrete types, unsupported Kind variants or malformed/incomplete scope are `InvalidOperationException` contract failures before any Buffer install, reported through the existing fault boundary. Do not catch them and return empty scope, preserve records silently, clear every record, or convert them into a normal player rejection. A known effect with no relevant actor/cell may have empty scope only when its mapping and producer evidence establish that result. The new-move allowlist still rejects any supported non-OrdinaryMove event.

Ownership is explicit: effect authors provide accurate immutable facts; the contract reader decodes their shape; MovementUndoPolicy decides cancellation from normalized evidence and final-state guards; Buffer checks provenance/allowed deltas and installs prepared state. A new buff/debuff reusing existing fact shapes needs no undo-policy change. A new event shape needs one reader mapping and contract/producer tests, not an examination or edit of undo lifetime, distance accounting, inventory transactions or View.

Coverage gates enumerate all concrete CombatEvent types in the production assembly and exercise all producible Kind variants through valid fixtures; they also check wrapper companion-fact completeness, including removing a required companion from a valid stream. An added type or variant without coverage fails tests. If a wrapper does not contain enough explicit facts to validate companion identity/scope, add the missing immutable evidence at its existing producer; never reconstruct the feature's rules or call a wrapper Observation by default. Include net-zero intermediate effects on B/origin, ordinary occupancy changes, remote kill/soul/terrain effects and missing-scope failures. The reader must not import trait calculators or become a parallel effect engine.

### 5.2 Commands and query

- Add `CombatCommandKind.UndoMove = 15` and `CombatViewCommandKind.UndoMove = 15`, subject to a fresh enum audit before implementation. Do not reuse removed IDs 8/9 or revive ReturnToCheckpoint's AP contracts.
- Add optional `ExpectedMoveCommandNumber` to the current command DTO/request/input path and copies. `CombatViewCommandData.UndoMove(actorId, battleInstanceId, controllerTurnSequence, moveCommandNumber)` carries no client-supplied origin, restored stats or arbitrary state.
- Add `MovementUndoFailureReason` and immutable `MovementUndoAvailability` carrying CanUndo, failure, original command number and destination when valid. Reasons cover no checkpoint, wrong phase/controller, stale battle/turn/token, actor changed/unavailable, destination occupied/invalid, ReturnWouldCauseEffect and pending reaction. Use generic public failure text; do not publish hidden environment details.
- Reuse the enclosing CombatActionAvailability.BattleInstanceId, ControllerTurnSequence and ActorId with the original move command number for request identity. The published destination is the saved checkpoint placement, useful for return information; it is not a clickable-cell command or a client-selected destination. Do not add a separate API or state for the optional origin-click gesture.
- Append optional `MovementUndoAvailability movementUndo` to `CombatActionAvailability`. Existing constructors default to unavailable. `GetActionAvailability` asks `MovementUndoCalculator.Evaluate` alongside move/attack admission. Reuse the existing ActionAvailability preview kind and tracker; no new preview kind or movement-preview context masquerading as undo.
- `MovementUndoCalculator.Calculate(input)` reevaluates the current record and destination, checks expected token and pending boss reactions, and constructs a minimal transition. It does not call ordinary move admission: that correctly rejects Moved units. Share stable battle/controller/actor validation where useful without weakening CanStartMove.
- Return evaluation refuses pending reactions; undo is not a way to trigger or bypass them. The existing normal reaction boundary remains authoritative; valid undo has no reaction to append. Tests must cover this invariant.
- Only an explicit UndoMove request can execute cancellation. An ordinary Move/Attack or item action targeting a checkpoint cell retains its own command semantics and normal validation. Core validates the requested actor/token, not View selection or pointer mode; a valid explicit A undo cannot be rejected solely because View currently shows B selected, which Core does not own.

### 5.3 Atomic result contract

Add immutable `MovementUndoResult` (actor, original command number, From/To, original rotation and `DistanceReverted`) as optional `UndoMovement` on transition/result. DistanceReverted must equal the live checkpoint's RecordedDistance; it is never client supplied. Keep `UnitActionUseSettlementSnapshot(actor, Moved, Available)`; its existing constructor accepts enum values, while Buffer authorizes this transition only for UndoMove with matching live checkpoint and typed result.

Keep ordered `CombatEvent` as playback authority: emit one `CombatCharacterEvent(Returned, currentActor, returnedActor)`. Do not also emit synthetic Moved/trait events or replay the original forward event list. From/To are result facts, not checkpoint-creation authority. If value contracts allow equal coordinates, their shape tests do not establish an executable same-cell undo; native success still requires the accepted movement provenance above. Preserve normal placement ReturnUnit semantics.

At `CombatStateBuffer.PrepareCommand`, validate token/source, legal checkpoint creation/removal, expected actor, exact placement/action/distance-only return, unchanged other statistics/world, settlement/result/event agreement, command owner and current turn. Validate structural evidence at this boundary; Core remains the gameplay eligibility owner. A direct forged transition must not reset arbitrary units, reduce unrelated statistics or manufacture checkpoints.

Creation provenance must include accepted player Move, Available -> Moved, a nonempty actual PathMovement, original placement equal to the input actor and requested-path origin, token equal to input.Number/current battle/turn, and expected actor equal to the fully published actor including its incremented stage record. RecordedDistance must equal final.DistanceMoved minus input.DistanceMoved and the actual movement tally for that tracked actor. Validate movement-event/path agreement and the reversible evidence contract; checkpoint shape alone is insufficient. Share pure structural validation with the contract/policy instead of duplicating feature rules in Buffer. Retained entries must come unchanged from the input records; no extra entries may appear on attack, preview, rejection or undo.

Use `BattleTransactions.Apply(CombatCommandTransition)` for preparation/install across character and combat stores and result numbering. Extend its existing preparation to include metadata; failures leave position, action use, checkpoints, results and handled counters unchanged. Duplicate processed command numbers retain current exactly-once behavior.

Validate OriginFacts against canonical capture from the input's original cell during checkpoint creation. An arbitrary sparse dependency list is not valid evidence, even when its record shape is correct.

Character preparation currently precedes CombatStateBuffer.PrepareCommand. Extend the internal `ICharacterBufferStore.PrepareCommandChanges(CharacterChanges changes, RunDeckSnapshot membership, MovementUndoResult undoMovement = null)` path to accept narrow typed distance-reversal evidence. BattleTransactions supplies it only for an accepted UndoMove; ordinary commands and all non-command PrepareChanges paths supply null. CharacterBuffer checks only the named actor may decrease DistanceMoved, exactly by DistanceReverted, with all other record fields unchanged and no underflow. CombatStateBuffer then checks the same amount against the live source checkpoint and exact result/event/settlement before any installation. A forged typed result may not bypass that second store's source validation. Keep prepare-all/install-all ordering: ordinary command records retain IsAtLeast, while non-command record writes retain exact SameValues (neither increases nor decreases are allowed). No permissive boolean switch, special mutable store or second transaction. Both position and statistic changes succeed or fail together.

For existing `Apply(CharacterChanges)` and `Apply(SoulActionChanges)`, compare current published character facts with `PreparedCharacterChanges.Views` via ReadCharacterChanges, plus actual soul-field deltas via ReadChanges. Add `MovementUndoState.WithoutAffected(CombatChangeEvidence evidence)` as an immutable dependency-matching operation: remove records whose ActorId is affected or whose original cell is a changed source cell; Lifecycle yields Empty, and no match returns the same state instance. The pure Core policy and non-command publication use this same operation. It does not inspect trait rules or infer effect scope. Ordinary occupancy changes are not source-cell changes; destination entry remains a current-world check. Main-only HP changes and a later restore must permanently invalidate the matching checkpoint on the first change.

Internal store methods `PrepareMovementUndoInvalidation(evidence)` / `InstallMovementUndoState(prepared)` prepare/install this selective metadata update and query revision (below) within existing BattleTransactions. The prepared value is the CombatStateData plus expected/final QueryRevision; a small internal tuple is sufficient, with no new service or transaction. Derive evidence from validated before/after facts, never caller-supplied arbitrary impact lists. Validate provenance and expected revision before the first install; failures preserve gameplay, metadata and revision. Direct completion supplies its existing lifecycle evidence. Install does no fallible rule work and emits no fake result. EndBattle drops state; PrepareBattle requires Empty.

Leave `ItemInventoryTransactions.PublishGrant`, its constructor and BufferSystemGroup composition unchanged. A quantity-only grant cannot affect the actor/origin/distance facts used by undo and therefore needs no invalidation or combat dependency. Verify successful and failed grants preserve return availability/tokens. If a future grant also equips an item or changes a character, that operation must publish its real changes through the existing character/equipment boundary; do not add a speculative global reset now.

### 5.4 Query freshness is not checkpoint lifetime

Selective pruning deliberately preserves B's record when C moves into or out of B's origin. That still changes CanUndo. The prior MovementUndoState identity alone is therefore insufficient, especially for direct changes with no new command result. Do not delete B's checkpoint just to refresh a query.

Add one `long QueryRevision` owned by CombatStateBuffer and exposed through its existing read sink. It is publication-version metadata, not a copy of gameplay state or a second turn counter. Start at 1 for an installed battle, paired with BattleInstanceId. Prepare its next checked value before installation; advance it on every accepted command and on actual non-command published character/soul changes or lifecycle change, even when the undo-state instance is unchanged. Do not advance it on previews, rejected/duplicate commands, no-op direct changes or inventory-only grants. Install/reset it at the existing transaction/lifecycle boundary, never in View or Core policy.

Append `SourceRevision` (default 0 for unbound pure calculations) to CombatActionAvailability and provide an immutable WithSourceRevision copy. CombatPreviewService captures QueryRevision before assembling ActionAvailability, stamps the response, and rechecks battle/request/revision before publication. The native ActionAvailability publisher rejects a stale/unbound revision without advancing the answered counter; the current request may be recomputed. Pure calculators do not read or manage Buffer versions. Keep other preview contracts unchanged in this scoped work.

Handoff the query key as battle + controller turn + QueryRevision + selected actor + request lifetime (existing result sequence may still invalidate presentation caches). Core always reevaluates UndoMove at execution; the original move token remains usable across unrelated revisions when currently valid. Cover blocked -> unblocked origin and changed hypothetical passive coverage with the same checkpoint/token, Main-only mutation, stale in-flight query, no-op identity, and quantity-only grant stability. No new View implementation belongs to this plan.
