## 1. 목표와 범위

기존 유닛을 골라 새 이름·키를 입력하고 `생성·등록`을 누르면 EntityKey 추가 → Unity 컴파일 → UnitDataSO·UnitVisualDataSO 복제 → 같은 키 지정 → 두 테이블 등록까지 이어진다. 생성 후 같은 창에서 두 SO를 편집한다.

이번 시작점은 사용자가 하던 **기존 유닛 복제**다. 특성·연출·애니메이션 등 참조는 원본과 공유하며, 참조한 에셋까지 재귀적으로 복제하지 않는다. 빈 기본값으로 생성하는 모드, 일괄 생성, 삭제, 기존 키 변경, 스테이지 배치·로스터·로드아웃 수정은 이번 범위에 넣지 않는다.

Core 변경 허용 범위는 사용자가 선택한 EntityKey 항목 추가 자동화다. 전투 규칙·AI·Core 실행 로직 변경을 포함하지 않는다. 도구를 구현한다고 임의의 실제 몬스터나 시험용 enum 항목을 저장소에 추가하지 않는다.

## 2. 현행 코드에서 확인한 계약

| 사실 | 코드 근거 |

## 3. 창의 사용 흐름

메뉴: `ProjectL > 유닛 통합 에디터`.

1. 원본 Unit SO 선택. 같은 키의 Visual SO를 찾아 함께 표시한다. 후보 없음·중복은 원인과 에셋 경로를 표시하고 생성을 막는다. 구조물 Visual만으로는 유닛을 생성할 수 없다.
2. 새 enum 이름(`Unit_...`), 숫자, 표시 이름 입력. 숫자는 소스와 에셋에서 사용하지 않은 양의 정수를 제안하며 직접 수정할 수 있다. 기존 enum 숫자는 바꾸지 않는다.
3. 출력 폴더 두 곳과 등록할 테이블 두 개를 표시한다. 기본 폴더는 각 원본 SO의 폴더다. 기본 파일 이름은 enum 이름 및 대응하는 `UnitVisual_...` 이름이다. 최종 경로를 생성 전에 보여준다.
4. 원본이 등록된 테이블이 하나면 선택한다. 후보가 여럿이면 직접 선택하게 한다. 테이블의 Catalog·Group 연결도 확인하여 실제 로딩 대상에 등록되는지 표시한다. 불명확한 테이블을 임의로 고르거나 Catalog를 자동 수정하지 않는다.
5. `생성·등록`으로 재컴파일을 포함한 작업을 시작한다. 진행 중 중복 실행과 입력 변경을 막는다. Play 중·컴파일 중에는 시작할 수 없다.
6. 완료하면 생성한 두 SO와 등록 상태를 표시한다. 같은 창에 `규칙`·`외형` 영역을 제공해 능력치·특성·프리팹·아이콘·연출을 편집한다. 키는 읽기 전용으로 한 번만 표시한다. 생성 직후에는 원본 값이 복제되었음을 표시한다.
7. 결과에 SO·테이블 선택 버튼을 제공한다. 출현 설정은 기존 스테이지 도구에서 연결한다는 안내를 보여준다.

신규 enum 대신 이미 정의됐지만 두 SO가 아직 없는 키를 사용하는 모드도 제공한다. 컴파일 실패 후 재시도·이미 키를 먼저 작성한 경우를 지원하며, 기존 항목의 개명·번호 변경 수단으로 쓰지 않는다.

## 4. 생성 전 검사와 저장 경계

- enum 이름은 `Unit_` 접두사와 보수적인 C# 식별자 형식으로 제한한다. 이름·정수 값은 소스와 현재 로드된 enum 양쪽에서 중복을 확인한다. 구조물 키·None은 거절한다.
- 검색한 Unit·Visual SO에서 등록 여부와 관계없이 새 키의 사용 여부를 확인한다. 짝을 연결하는 허용 관계는 Unit 하나와 Visual 하나이며, 동일 종류의 중복을 허용하지 않는다.
- 원본 두 SO, 선택 테이블의 타입·직렬화 필드, prefab 참조, 출력 폴더, 파일명·최종 경로·기존 파일 충돌을 확인한다. Assets 아래의 기존 출력 폴더만 허용하고 StreamingAssets 및 하위 폴더는 제외한다.
- CreateAsset 반환 후 영속 에셋 여부, 요청 경로, 실제 파일·meta, MainAsset, GUID 역조회를 확인한다. 로그만 남기고 생성이 실패한 경우에도 즉시 예외를 보고하며 다음 에셋 생성·등록을 진행하지 않는다.
- 기존 규칙 검증을 별도 숫자 규칙으로 복제하지 않는다. 생성과 편집 검증은 SO의 GetData 및 해당 Data의 기존 Validate 경로를 좁은 어댑터에서 재사용한다. internal 타입 접근을 위한 반사는 타입·메서드 계약을 확인하고 예외의 실제 원인을 보존한다. 이를 이유로 Systems의 공개 범위·asmdef·Framework를 바꾸지 않는다.
- 새 키가 로드된 뒤 복제본의 기존 검증을 통과해야 테이블에 등록한다. 원본이 유효해도 특정 키에 묶인 역할 규칙 등이 새 키에서 실패할 수 있다.
- 테이블에 같은 객체를 중복 추가하지 않는다. 등록 직전에 현재 에셋 상태를 다시 읽어 외부 변경을 확인한다.
- 실패 메시지는 대상·필드·경로와 원인을 포함한다. 구성 오류를 null이나 성공 결과로 바꾸지 않는다.

enum 수정과 에셋 생성 사이에는 컴파일이 있으므로 하나의 Undo로 가장하지 않는다. 실패 재개는 완료 단계를 보존하고, 명시적 취소만 생성물을 제거한다. enum 원본 복구는 별도 백업으로 분리한다.

## 5. 재컴파일·복구 수명

상태: `입력 → 사전 검사 → enum 반영 → 컴파일 대기 → 재검사 → SO 생성 → 테이블 등록 → 완료`. 실패 시 `오류/재시도 대기`에 머문다.

- 창과 별개의 작업 조정자가 수명을 소유한다. 창을 닫아도 진행 중인 요청을 잃지 않는다.
- 프로젝트 Library 아래 도구 전용 기록에 작업 ID, 단계, 원본·테이블 GUID, 원본 변경 감지 값, 새 키, 출력 경로, 생성된 에셋 GUID, 각각의 등록 완료 여부, 취소 요청 여부, enum 수정 전후 해시·백업 경로, 컴파일 시작·완료·오류·도메인·시각을 저장한다. 기록은 진행 체크포인트이며 런타임 DB가 아니다. 실제 등록 상태는 현재 테이블에서 재확인한다.
- enum 소스는 대상 enum과 명시적 정수 선언을 확실히 읽을 수 있는 형식에서만 수정한다. 조건부 선언·계산식 등 지원하지 않는 형식이면 소스를 바꾸지 않고 오류를 표시한다. 파일 전체를 정형 템플릿으로 재작성하지 않는다.
- 원본 백업과 원본 파일과 같은 볼륨의 숨김 임시 파일을 각각 완전히 기록하고 Flush(true)한다. 교체 직전 원본 해시를 재검사하고 File.Replace로 교체한다. 원본 파일에 직접 Write/SetLength하지 않는다. 기존 항목·숫자·주석·BOM·개행을 보존하고 Unity에 스크립트 변경과 컴파일을 요청한다.
- 백업 위치는 `Library/ProjectLUnitAuthoring/backups/<작업 ID>/EntityKey.cs.original`이다. 기존 백업을 덮지 않고 해시가 다르면 중단한다. 백업 경로를 창에 표시하며 다른 작업자의 수정을 덮을 수 있는 자동 소스 복원은 하지 않는다.
- CompilationPipeline의 시작·어셈블리 오류·완료 이벤트를 기록한다. 콜백은 작업 기록만 저장하고 에셋 처리는 편집기가 안정된 Update에서 한다. 도메인 재로드 후 정확한 이름·숫자가 없으면 명확한 오류 상태로 전환한다.
- 컴파일 중에는 기다린다. 컴파일·임포트가 멈췄는데 완료 이벤트를 확인할 수 없거나 완료 후 재로드를 확인하지 못하는 상태가 30초 기준을 넘으면 재시도 가능한 오류로 전환한다. 성공 완료 이벤트와 로드된 키를 확인한 경우에만 SO 작업으로 넘어간다. 이미 로드된 기존 키를 선택한 요청은 컴파일 없이 진행한다.
- 컴파일 오류면 SO·테이블에 손대지 않는다. 입력을 보관하여 수정 후 재시도할 수 있게 한다. 에디터 재시작 때 남은 요청은 상태를 표시하고 명시적으로 재개한다.
- 아직 생성할 SO가 있으면 템플릿·출력 경로·테이블·키 충돌을 재검사한다. 대기 중 원본이 바뀌었으면 중단한다. 두 SO가 이미 생성됐으면 원본을 다시 복제하지 않고 생성물의 현재 내용을 검증·보존한다.
- 생성 GUID가 기록된 SO는 동일 GUID·경로·Key인지 검증하여 재사용한다. 등록은 각각 저장 후 체크포인트를 남긴다. 테이블 저장 후 기록 전에 중단된 경우 실제 참조가 있으면 중복 추가 없이 등록 완료를 기록한다. 완료 기록이 있는데 참조가 사라졌거나 생성물의 GUID·경로·Key가 다르면 외부 변경으로 중단한다.
- 일반 실패와 재시도에서 생성물·등록 참조를 삭제하지 않는다. 보관된 유효한 수정 내용과 GUID를 유지하고 남은 단계부터 진행한다. 최종 완료 기록 이후 결과 선택·Ping 같은 UI 오류는 완료 상태를 실패로 되돌리지 않는다.
- `요청 취소 · 생성물 삭제`를 명시적으로 선택한 경우에만 이번 작업의 확인된 GUID와 선택 테이블 참조를 제거한다. 삭제 전 취소 상태를 기록하고 각 삭제 뒤 체크포인트를 저장한다. 취소 도중 종료·실패한 요청의 재개는 취소 정리를 이어가며 새로 생성하지 않는다. 다른 변경이 담긴 테이블 전체를 과거 사본으로 덮어쓰지 않는다.
- 복구 중 실패도 기록한다. 존재 여부만으로 소유권을 추측하지 않는다. 기존 버전 기록의 등록 완료 필드가 없으면 실제 테이블을 대조하여 보완하며, 기록된 GUID의 생성물을 다시 만들지 않는다.
- enum이 이미 컴파일된 뒤 SO 생성이 실패하면 새 enum은 유지하고 재시도할 수 있게 한다. 취소 시 이 상태를 명시한다. enum을 자동 삭제하거나 파일 전체를 이전 버전으로 복원하지 않는다.
- 일반 SO 값 편집은 Undo를 지원한다. 키·코드 변경과 파일 생성의 취소는 일반 값 편집 Undo와 구분한다.

## 6. 책임 분리와 구조 점검

| 구성 | 책임 |
|---|---|
| UnitAuthoringWindow | 입력·진행 상태·결과 및 SO 편집 표시, 협력 객체 연결 |
| UnitAuthoringAssets | SO 검색·짝 조회·직렬화 경로·기존 검증 호출·테이블 및 Catalog 연결 조회 |
| UnitEntityKeySource | enum 구문·중복 검사, 최소 범위 소스 편집과 충돌 감지 |
| UnitAuthoringOperation | 사전 검사·컴파일 대기·재개·생성·등록·복구 순서 |
| UnitAuthoringPendingStore | 작업 기록 저장·복원, 단일 진행 요청 식별 |

위 이름은 예정이며 모두 `Tool/Editor`에 둔다. 공통 기반이나 스테이지 도구로 옮기지 않는다.

- **SSOT:** 유닛 규칙은 Unit SO, 표현은 Visual SO, 키 정의는 EntityKey, 등록은 기존 테이블이 원본이다. 새로운 런타임 통합 SO를 만들지 않는다. 편집 창은 SerializedObject를 사용하며 필드별 영구 사본을 만들지 않는다.
- **S:** 화면·enum 편집·에셋 입출력·작업 수명·진행 기록을 변경 이유에 따라 분리한다.
- **O:** 규칙·외형 필드는 기존 직렬화 필드와 drawer로 표시해 SO 필드 추가 때 창에 별도 데이터 구조를 추가하지 않는다.
- **L:** 기존 SO와 GetData·Validate 계약을 유지한다. 별도 SO 하위 타입으로 동작을 바꾸지 않는다.
- **I:** 협력 객체는 작업에 필요한 소수 인자를 받는다. 서비스 전체를 담은 가짜 공용 인터페이스를 만들지 않는다.
- **D:** 창은 작업 요청을 넘기고 저장 순서는 조정자가 맡는다. Unity 에셋 API와 소스 파일 I/O는 각 경계에 모은다. 단일 구현을 위한 불필요한 인터페이스는 추가하지 않는다.
- **JMH/FW:** 런타임 서비스·Builder·UISystem 화면이 아닌 Editor 도구다. FW-001~003·008~009를 적용하려고 런타임 등록을 추가하지 않는다. FW-004의 런타임 내부 상태 우회를 하지 않고 SO 입력 계층을 편집한다. FW-012의 DB 등록 요구조건은 기존 테이블과 검증 경로를 유지한다. 구독·임시 객체는 소유자가 해제한다.
- **독립성:** UI 배치 변경은 Window, enum 문법 변경은 KeySource, SO 경로 변경은 Assets, 재로드·복구 변경은 Operation/Store에 한정한다. 공유 경계는 작업 요청과 상태다. 스테이지·전투 입력·카메라의 수정 및 회귀 확인을 이 도구에 끌어오지 않는다.

## 7. 구현·인수 제한

Test 코드 작성·MSBuild 실행을 하지 않는다. 사용자가 Unity에서 컴파일·에디터 조작·DB 검증을 확인한다. 실제 에셋 값을 바꿔 확인할 때는 기존 DataBaseAssetTests를 사용자 확인 항목에 포함한다.

구현 시 Core 경계 인계 §5에 사용자 허용 범위와 도구가 EntityKey를 변경하는 동작을 기록하고, 문서 제목도 최신 주제·날짜로 갱신한다. 커밋·push는 사용자가 한다.

## 8. 구현 기록 — 2026-11-10

- 예정한 5개 책임을 C# 6개 파일로 구현했다. Window의 편집 화면만 `UnitAuthoringWindow.Editing.cs`로 나눴다. 모두 Tool.Editor의 기존 어셈블리 범위다.
- 작업 기록은 `Library/ProjectLUnitAuthoring/request.json`, 동일 에디터 세션의 자동 재개 표식은 SessionState에 둔다. 창을 닫아도 컴파일 후 재개하며, 에디터 재시작·실패 후에는 창에서 재개한다.
- 테이블은 원본이 등록된 테이블을 우선하고, 두 테이블을 함께 포함하는 Catalog를 확인한다. 여러 Catalog가 있으면 연결 경로를 표시하며 실행할 Bootstrap의 Catalog 선택까지 변경하거나 추정하지 않는다.
- enum 편집은 현행 단일 namespace·단일 enum·명시적 10진 정수·끝 쉼표 형식을 보수적으로 지원한다. R3 수정으로 원본 백업·완성된 임시 파일·교체 전 해시 대조·File.Replace를 사용하며 기존 BOM·개행·선언을 보존한다.
- 편집은 실제 두 SO의 SerializedObject와 기존 PropertyDrawer를 사용한다. 값 변경은 Undo와 에셋의 dirty 상태에 반영되며, 검증·저장 버튼은 양쪽 검증 후 해당 두 에셋만 저장한다. 키 변경은 제공하지 않는다.
- R1 수정으로 일반 예외는 생성 에셋과 등록 체크포인트를 보존한다. 프로세스 강제 종료가 에셋 생성과 GUID 기록 사이에 발생한 경우 소유권을 확정할 수 없는 파일을 삭제하지 않고 재시도 시 경로 충돌로 중단한다. 해당 경로는 사용자가 확인해야 한다.
- 문서 인계 §5.83과 제목을 갱신했다. 실제 EntityKey·SO·테이블은 이번 작업에서 변경하지 않았다. 정적 점검만 수행했으며 컴파일·에디터 재로드·저장·재생은 사용자 확인 대기다.
