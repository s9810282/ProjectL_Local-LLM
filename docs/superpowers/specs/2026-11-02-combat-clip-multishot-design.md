# 전투 공격 클립의 여러 발 발사 설계 — 선택 ClipEvent2·3 (2026-11-02)

- 작성: View 작업, 2026-11-02, 3차(리뷰 보완 반영).
- 상태: **사용자 승인으로 MS-a~MS-c 코드 완료·MS-c 리뷰 지점. MS-d 미착수, 컴파일 미확인.**
- 변경 이유: 사용자 "ClipFire를 만들거면 ClipEvent를 2,3 번을 만드는게 낫지않니"에 따라 발사 전용 이름표 제안을 철회하고 선택적인 범용 이벤트 번호로 정리했다. 이 개정은 구현 승인이 아니다.
- Task: [Phase별 계획](../plans/2026-11-02-combat-clip-multishot-plan.md).
- 검토: [7기준 리뷰 R1~R5](2026-11-02-combat-clip-multishot-review.md). 아래는 권장 보완을 채택한 현재 계약이다.
- 기존 계약: [클립 설계](2026-10-19-combat-unit-animation-clip-design.md), [투사체·피격 소리 설계](2026-10-27-combat-projectile-hit-sound-design.md), [이펙트 수명 설계](2026-10-31-combat-effect-lifetime-design.md). 아래에서 명시한 확장만 대체한다.

## 1. 목표와 범위

기존 단발 클립을 그대로 두고, Akimbo의 양손 권총 두 발 모션에 투사체 두 개를 맞춘다. Core의 기존 결과는 한 번 소비한다.

- 기존 `ClipStart / ClipEvent / ClipEnd`는 각각 하나씩 필수다.
- **`ClipEvent2`, `ClipEvent3`는 필요한 클립에만 추가하는 선택 항목**이다. 모든 공격 클립을 수정하지 않는다.
- 이벤트는 범용 연출 시점이다. 무엇을 발사하거나 표시할지는 View 설정/조립이 정한다. 이름표 함수가 Core 호출이나 발사를 직접 실행하지 않는다.
- Core·Buffer·FieldCamera·Architecture·전투 진행 정책은 변경하지 않는다. 실제 탄별 피해/방어/특성 판정, 다른 대상으로 발사, 근접 연타, 코드 모션 연사는 범위 밖이다.
- 새 Test 코드를 작성하지 않고 MSBuild도 실행하지 않는다. 컴파일·재생 확인은 사용자 Unity 인수다.

## 2. 현재 사실과 대안 판단

| 위치 | 현재 사실 |
|---|---|
| `CombatClipEvents` | 세 이벤트를 하나씩 요구하고 다른 함수 이름·중복을 거절한다. |
| `CombatClipData / CombatClipEventCursor` | 중간 이벤트 시각 하나를 보관한다. 커서는 enum의 다음 숫자로 진행한다. |
| `CombatClipPiece / CombatPieceRun` | 첫 이벤트를 `ClipEvent` 신호로 내며, 같은 조각의 동일 신호 반복은 한 번으로 처리한다. |
| `CombatAnimationEvents / ICombatUnitClip` | 총구·이펙트 지점이 각각 하나다. Unity의 실제 이벤트 호출은 끈다. |
| `CombatClipAttack.ComposeRanged / CombatFirePiece` | 첫 이벤트에 한 발을 연결하고 접촉 때 피해 후속 표시를 해제한다. |
| 운영 Akimbo | `New/Playerable/Akimbo.prefab`, `CombatUnitAnimation_Akimbo`, 공용 `CombatAttack_Linear`. 첫 이벤트 0.8초, 끝 약 1.5초다. |

| 안 | 판단 |
|---|---|
| 모든 클립에 이벤트 2·3 필수 | 기존 단발의 작업량을 늘리므로 채택하지 않는다. |
| 선택 `ClipFire` | 기존 입력은 보존할 수 있지만 발사 전용 시점과 일반 시점을 따로 확장해야 한다. 이번 개정에서 철회한다. |
| **선택 `ClipEvent2 / ClipEvent3`** | 기존 단발 무수정, 발사·소리·이펙트가 같은 범용 시점을 선택할 수 있다. 이번 제안이다. |
| 같은 `ClipEvent` 함수 반복 | 현재 중복 검사·단일 시각·신호 중복 제거와 충돌한다. 이름만 두 번 찍어 해결되지 않으며 이번 안으로 삼지 않는다. |

이번 입력의 추가 번호는 2·3까지다. 더 많은 이벤트 번호가 실제로 필요해지면 별도 범위로 확장한다. 처음부터 모든 번호의 함수나 무제한 이벤트 편집기를 만들지 않는다.

## 3. MS1 — 선택 범용 이벤트와 재생 신호

### 입력 규칙

- `CombatAnimationEvents`에 이름표 함수 `ClipEvent2()`, `ClipEvent3()`를 추가한다. 기존 세 함수와 같이 잘못 실제 호출되면 진단만 한다.
- 선택 이벤트는 번호별로 최대 하나다. 2번 없이 3번만 추가할 수 있다. 시각은 유한하고 `0 <= Start <= Event1 <= Event2 <= Event3 <= End <= clip.length`다. 없는 번호는 비교에서 제외한다.
- 같은 시각이면 `Start → Event1 → Event2 → Event3 → End` 순이다. 두 총구를 동시에 쏘는 입력도 표현할 수 있다.
- 중복·빠진 필수 이름표·모르는 함수·순서 오류는 기존처럼 DB 생성에서 예외로 실패한다. 부속 클립은 계속 이벤트가 없어야 한다.
- 주 클립의 선택 시점이라는 형식은 공격/피격에 공통이다. 선택 이벤트가 존재하는 것만으로 기존 동작이 추가되지는 않는다.

### 값·커서·호환

- 클립 시각의 원본은 AnimationClip이다. SO에 이벤트 시각이나 발사 간격을 다시 저장하지 않는다.
- 불변 `CombatClipTimings`가 시작·끝·번호별 중간 시각을 소유하고 `CombatClipData`와 커서가 같은 값을 읽는다. 중간 항목은 readonly 값 형식이며 내부에서 생성한 배열의 읽기 전용 래퍼만 노출한다. 외부 배열/List를 받아 보관하거나 backing 배열을 반환하지 않는다. 기존 `EventTime`은 첫 항목을 읽는 호환 접근이다.
- 기존 세 시각으로 만드는 생성/호출은 유지한다. 추가 이벤트가 없는 기존 입력은 기존과 같은 시점·개수의 신호를 낸다.
- `CombatClipEventCursor`는 실제 존재하는 이벤트 순서를 진행한다. **현재 enum 값에 1을 더하는 구현은 교체한다.** 선택 번호가 늘어도 기존 enum의 정수값을 재배치하지 않는다.
- `CombatClipPlayback / CombatClipPiece`는 각 번호에 대응하는 `ClipEvent / ClipEvent2 / ClipEvent3` 신호를 낸다. `CombatPieceSignal`에도 서로 다른 번호를 추가하므로 기존 실행기의 동일 신호 중복 제거는 유지할 수 있다.
- 한 Tick에 여러 시점을 넘으면 각각 순서대로 한 번 낸다. 취소 뒤에는 나머지 신호를 내지 않는다. 별도 시계·Coroutine·Animator 강제 Evaluate를 추가하지 않는다.

## 4. MS2 — 이벤트와 발사의 연결

이벤트가 있다고 무조건 총알을 쏘게 하지 않는다. `CombatUnitAnimationSO` 공격 칸에 선택 목록 `shots`를 두고 **이벤트 번호 + 발사 지점 번호**를 연결한다. 이벤트 번호의 데이터 타입은 DB/View 값 계층에서 정의하며 런타임 Pieces의 enum에 역참조하지 않는다.

| 설정 | 해석 |
|---|---|
| `shots` 비어 있음 | 기존처럼 `ClipEvent`에서 지점 0으로 한 발. 기존 SO 수정 없음. |
| 명시 목록 있음 | 그 목록이 전체 발사 목록. 기본 한 발을 추가하지 않는다. |
| 사용하지 않은 `ClipEvent2 / 3` | 발사 없이 다른 연출 시점으로만 사용할 수 있다. |

Akimbo의 입력 예:

| 이벤트 | 연결 동작 |
|---|---|
| `ClipEvent` | 지점 0의 첫 번째 권총 발사 |
| `ClipEvent2` | 지점 1의 두 번째 권총 발사 |
| `ClipEvent3` | 필요 없으므로 넣지 않음 |

검사와 값 변환:

- 연결한 이벤트가 해당 공격 클립에 실제 존재해야 한다. 지점 번호는 0 이상이며 총구가 해당 프리팹에 존재해야 한다.
- 같은 이벤트에 다른 지점을 연결하는 동시 발사는 허용한다. 같은 `(이벤트 번호, 지점 번호)` 중복은 거절한다. 같은 지점을 다른 이벤트에 재사용할 수 있다.
- 명시 발사 목록은 직선/곡사 공격 클립에서만 허용한다. 근접·주 공격 클립 없는 목록은 DB 검사에서 거절한다.
- 명시 발사에 선택한 이벤트는 클립 끝보다 앞서야 한다. 기존 암시적 단발은 `EventTime == EndTime`까지 허용하던 계약을 그대로 유지한다.
- 정규화된 발사 목록은 `CombatClipAttackData`가 소유한다. 암시적 단발과 명시 입력의 구분은 입력 출처 정보이며 별도 SO 체크박스로 다시 입력하지 않는다. Tick에서 SO/클립 이벤트를 재조회하지 않는다.

## 5. MS3 — 기본 지점과 추가 지점

- 기존 직렬화 필드 `muzzle`, `effectPoint`는 지점 0으로 유지한다. 기존 프리팹을 배열로 일괄 이전하지 않는다.
- 선택 목록 `additionalAttackPoints`의 원소 0은 지점 1, 원소 1은 지점 2다. 각 원소는 muzzle/effectPoint 한 쌍이다. Akimbo에만 두 번째 손의 한 쌍을 더한다.
- 지점 입력은 `CombatAnimationEvents`가 소유하고 CaptureAttackPoints로 복사한 `CombatAttackPoints` 정의가 번호를 한 곳에서 해석한다. `UnitClipChannel / ICombatUnitClip / FieldUnitView`는 그 정의의 읽기를 전달한다. 기존 번호 없는 읽기는 지점 0으로 유지한다.
- 사용할 총구와 프리팹 소속을 DB 유닛 검사에서 확인한다. 해당 발사의 큐가 effectPoint를 사용하면 그 지점도 검사한다. 없는 지점을 기본 총구로 조용히 대체하지 않는다.
- 총구는 각 발사 때, 지연 이펙트 지점은 큐 시작 때 읽는다. 매 Tick의 씬 검색은 추가하지 않는다.

## 6. MS4 — 개별 접촉과 한 번의 피해 표시

> 2026-11-10 사용자 요청으로 **유닛·건물 피해 숫자**를 탄별 정수 분할로 변경했다(DN1 유닛, DN2 건물). 아래의 첫 탄 숫자 금지/숫자 한 번은 이전 정책이다. 체력·피격·사망/파괴 후속의 한 번 해제는 유지한다. 현재 설계·Task·검증 상태는 [연발 정수 피해 숫자 DN1·DN2](../plans/2026-11-10-combat-volley-damage-numbers.md)을 따른다.

`CombatClipAttack`은 공통 방향·클립·가로채기 앞 항목을 유지한다. 원거리의 탄별 조립은 `CombatClipRangedAttack`(예정 이름)에 분리한다.

- 각 발사 조각은 선택한 클립 이벤트 신호 뒤에 연결한다. 첫 발은 `After(played, ClipEvent)`, 둘째는 `After(played, ClipEvent2)`다. 시각 오프셋이나 추가 발사 시계를 만들지 않는다.
- `CombatFirePiece`는 지점 번호로 한 발을 쏘고 접촉/도착을 알린다. 투사체 손잡이 회수를 소유하며 피해 후속을 직접 해제하지 않는다.
- `CombatVolleyReleasePiece`(예정 이름)는 시계 없는 외부 진행 조각이며 발사별 최초 접촉 여부만 소유한다. `Begin`에서 보호된 Hit/End 콜백과 접촉 입력을 준비한 뒤 클립/발사를 시작시킨다. 0초 이벤트도 이 순서를 따른다.
- 마지막 최초 접촉은 완료 상태를 먼저 확정하고 **`release → Hit → End`**를 한 번 통지한다. 통지 중 취소/세대 변경/재진입이 일어나면 기존 보호된 콜백이 늦은 신호를 막는다. 개별 발사는 주입받은 접촉 콜백만 호출하고 집계의 상태/맥락을 직접 다루지 않는다. `Cancel`은 입력을 닫고 완료/해제를 알리지 않는다. 집계는 손잡이를 소유하지 않으며 다른 탄이 아직 날고 있으면 전체 실행이 계속 기다린다. 집계 Tick에서 목록을 훑지 않는다.
- 보통 두 번째 탄 접촉에 체력·숫자·피격·사망 표시를 연다. 두 번째 탄이 먼저 닿아도 첫 탄까지 기다린다. 첫 탄에 가짜 피해/피격 사건을 만들지 않는다.
- 실제 체력·피해·대상은 Core 결과를 그대로 사용한다. 기존 Gate의 대상 해제·사건 진행 정책을 복제하거나 변경하지 않는다.
- 단발도 같은 한 발 목록과 접촉 집계를 사용해 기존 접촉 1회에서 기존 후속을 연다. 근접의 해제 조각은 변경하지 않는다.
- 전체 종료는 클립 끝·모든 투사체 종점 도착·기존 지연 큐/대기 항목까지 기다린다. 가로채기 복귀는 집계 `Hit`에 연결한다.
- 취소·세대 교체·표시 꺼짐·씬 해제는 대기 발사를 막고 모든 발사 손잡이를 회수하며 집계를 폐기한다. 늦은/중복 콜백으로 피해 표시를 열지 않는다. 누락/실패를 임의 타임아웃 성공으로 바꾸지 않는다.

## 7. MS5 — 번호별 소리·이펙트

새 발사 전용 큐 시점은 추가하지 않는다. 기존 범용 `Cue`에 대응하는 선택 시점 `Cue2 / Cue3`를 추가한다. 기존 enum 숫자는 유지하고 뒤에 추가한다.

| 시점 | 의미 |
|---|---|
| `Cue` | `ClipEvent` 시점, 기존 의미 유지 |
| `Cue2 / Cue3` | 해당 번호의 클립 이벤트 시점 |
| `Hit` | 모든 탄 접촉 뒤 피해 후속 표시 해제 직후, 공격당 한 번 |
| `Contact` | 각 탄의 실제 접촉, 기존 지연 0 이펙트 규칙 유지 |
| `Start / End` | 기존 공격 전체 시작/클립 끝, 한 번 |

- 이번 실제 번호별 큐 소비 확장은 원거리 공격 클립에 한정한다. 해당 조립은 존재하는 번호별 신호만 공통 도우미 한 곳에서 연결한다. 공통 클립 읽기/신호는 피격에도 전달할 수 있지만, 근접/피격의 새 Cue2/3 소비 기능은 별도 범위로 미룬다. 첫 이벤트의 기존 소비는 유지한다.
- 클립 없는 코드 모션·근접·피격·사망·사실 사건 등 이번에 지원하지 않는 `Cue2 / 3` 조합은 DB에서 거절한다. 미설정 신호 예외를 무시/false로 완화하지 않는다.
- SO의 기존 공격 소리 `sound`는 유지하고 선택 `additionalSounds`는 시점만 추가 입력한다. 값 변환에서 이를 사건 소리 시점 목록 하나로 합친다. 런타임의 첫 소리 호환 접근이 필요하면 그 목록의 첫 항목을 읽는다. 소리 종류는 기존 사건 소리 조회가 정하며 프리셋을 복제 입력하지 않는다.
- 빈 큐 판정·허용 사건 검사·번호별 이벤트 사용/존재 검사·재생 조립은 같은 사건 소리 목록을 읽는다. 이벤트 사용 검사는 효과·흔들림·플래시·피격 소리·사건 소리를 모두 포함하는 한 경로로 모은다. 소리에만 Cue2를 쓰는 입력도 DB에서 실제 클립/이벤트를 검사하고 Tick에서 재검사하지 않는다.
- 기존 소리·이펙트·흔들림 조립을 재사용한다. `Cue` 전체를 탄 수만큼 반복해 기존 Start/End까지 중복시키지 않는다.
- 총구 이펙트는 번호별 큐가 어느 발사 지점을 쓰는지 알아야 한다. 기존 이펙트 입력에 선택 `actorPoint` 번호를 추가하며 기본값은 0이다. `ActorMuzzle / ActorEffectPoint`에서만 사용하고 다른 자리에 0이 아닌 값을 넣으면 거절한다. 이벤트 번호와 손 번호를 같은 값이라고 가정하지 않는다.
- Akimbo: 첫 총구 이펙트는 `Cue + actorPoint 0`, 둘째는 `Cue2 + actorPoint 1`. `Cue2`를 쓴다고 자동으로 오른손이라고 추측하지 않는다.
- 발사 지점·효과 지점의 입력 원본은 같은 프리팹 정의다. 큐는 그 번호만 선택한다. 보정·놓기·해제는 기존 `CombatCuePoints / CombatEffectPiece / CombatEffectWindow`를 사용한다.
- 직렬화 입력은 private SerializeField/Serializable 값으로, 실행 값은 생성 뒤 불변으로 분리한다. 새 발사/큐 목록은 생성 시 복사해 읽기 전용 래퍼 또는 index 읽기로 제공한다. 지점 목록을 외부에서 재정렬/교체하지 못하게 하고 대여는 현재 자세만 반환한다. Transform의 정상 애니메이션 이동까지 불변으로 취급하지 않는다.
- 투사체 비행/착탄 소리는 기존 프리셋·지연을 탄마다 실제 발사/접촉에 연결한다. 공통 소리 조립 도우미를 재사용하고 이중 재생하지 않는다. 대상의 피격 소리/플래시는 기존 후속 소비 때 한 번이다.
- 임의 유닛이 쓰는 특성 공격 표시 덮어쓰기는 클립 이벤트/지점 존재를 보장할 수 없으므로 `Cue2 / 3` 및 기존 행위자 지점 제약을 DB에서 지킨다. 공격자 자신의 외형으로 재생하는 추가 공격은 같은 발사 목록을 재사용한다.

## 8. Akimbo 에셋 적용과 미확인

- 실제 두 발사 프레임·먼저/나중 손은 Unity에서 확인한다. 현재 첫 이벤트 0.8초가 두 실제 발사 중 어느 시점인지는 이번 조사로 확정하지 않았다. 필요하면 기존 첫 이벤트도 실제 첫 발에 맞추고 `ClipEvent2`를 둘째에 둔다. 임의 간격을 확정하지 않는다.
- 명시 `shots` 두 줄과 추가 총구 한 쌍은 Akimbo에만 넣는다. 클립을 다른 유닛과 공유한다면 Akimbo용 복제 클립으로 연결하고 원본을 유지한다.
- 새 `CombatAttack_Akimbo`는 기존 직선 투사체/코드 모션 부품을 참조한다. `UnitVisual_Akimbo.attackPresentation`만 새 설정으로 연결하고 공용 `CombatAttack_Linear`는 변경하지 않는다.
- 기존 소리가 한 발 분량이면 `Cue`와 추가 `Cue2` 소리를 낸다. 이미 두 발 분량인 리소스라면 기존 소리 한 번을 유지하고 시작 시점을 실제 리소스에 맞춘다. 소리 분량 확인 전 중복 재생으로 확정하지 않는다. 새 오디오 제작/편집은 범위 밖이다.
- 현재 공용 직선 설정의 이펙트 목록은 비어 있다. 사용자가 지정한 총구 효과만 연결하고 임의로 효과를 고르지 않는다. 빈 목록과 두 투사체 발사 완성은 구분한다.

## 9. 구조 점검

### SSOT·SOLID

- **SSOT:** 피해/체력/대상은 Core/Buffer, 시점은 클립, 이벤트→발사는 공격 클립 SO, 지점→Transform은 프리팹, 자원은 기존 대여/투사체 손잡이, 접촉 집계는 실행별 집계 조각, 대상 해제는 기존 Gate가 각각 소유한다. 시각·피해·해제 상태를 다른 부품에 복제하지 않는다.
- **S:** 클립 읽기/커서, 원거리 조립, 개별 발사, 접촉 집계, 큐 구현을 변경 이유로 나눈다. Presenter에 Akimbo 상태를 추가하지 않는다.
- **O:** 세 번째 발은 선택 이벤트·발사 연결·지점 입력으로 추가한다. 유닛 키 분기는 없다. 4번 이후 이름표는 현재 범위 밖임을 명시한다.
- **L:** 기존 단발/첫 이벤트 접근, 일반 클립 수명, 취소, `Hit`의 해제 후 신호 계약을 유지한다. 없는 시점/지점을 조용히 대체하지 않는다.
- **I:** 새 입력은 View 클립/큐/지점 계약에 한정한다. Core 서비스·Buffer에 발사 횟수를 늘리지 않는다.
- **D:** 조립은 기존 클립 대여·발사 함수·효과/소리 창구를 사용한다. 씬 검색이나 Core 직접 호출을 하지 않는다. 미래 교체만을 위한 새 서비스 계층을 만들지 않는다.

### JMH 지침·FW 계약

[개발 지침](../framework/Framework%20Development%20Guidelines.md), [FW 가이드](../../../Assets/ProjectL/Script/Systems/Documentation/framework-programmer-guide.md), [프로젝트 적용 §4.6](../handoffs/2026-09-30-combat-view-design-session-handoff.md#46-기능-변경의-독립성--조립과-기능-구현-분리)을 기준으로 점검한다.

- FW-001~003: 새 System/Service/Builder/Module 등록은 없다. 생성은 기존 조립, 보관/수명은 기존 실행이 맡는다. Factory→Group→상위 Export→소비자 경로는 유지한다.
- FW-004·011·014: 대여·투사체 손잡이·효과 창구를 통해 반환한다. Framework 풀 내부/소유 객체를 직접 우회하지 않는다.
- FW-012: 새 효과 종류/테이블을 만들지 않는다. 효과 연결 시 기존 Render 등록을 확인한다.
- FW-013·016: 실제 Unity 이벤트 호출·별도 EventBus/Update·Runtime 재초기화를 추가하지 않는다. 기존 재생 세대와 수명을 사용한다.
- 입력/UI/Job/FieldCamera 구현을 변경하지 않아 FW-005~010·015의 새 적용 지점을 만들지 않는다.

### 기능 변경의 독립성

| 변경 | 이후 수정·이해 범위 | 확인 범위 |
|---|---|---|
| 둘째 발 시각 조정 | Akimbo 클립의 이벤트 2 | Akimbo 모션/발사 |
| 세 번째 발 추가 | 해당 클립·발사 연결·필요한 지점 | 해당 유닛 |
| 둘째 시점의 VFX 변경 | 해당 공격 설정의 Cue2 큐 | 그 효과 |
| 투사체 속도/궤적 변경 | 기존 투사체 부품/전략 | 해당 투사체 종류 |
| 피해 표시 해제 정책 변경 | 접촉 집계·원거리 조립 | 단발/복수 탄·가로채기·후속 |
| 근접 피해 지연 변경 | 기존 근접 조립 | 근접, 접촉 집계와 무관 |

이번 최초 변경은 공통 클립 시각/신호·큐·지점 계약에 닿으므로 대표 단발·피격 클립·취소 회귀가 필요하다. 이후 Akimbo의 발사 시각/횟수/VFX 조정이 Core·상태 효과 전체 확인으로 번지지 않게 한다.

## 10. 리뷰·검증 상태

사용자 승인으로 리뷰 보완을 계약에 반영하고 MS-a~MS-c 코드를 완료했다. R1 집계 수명, R2 소리 정규화, R3 시각/발사/소리 목록·지점 캡슐화, R4 원거리 클립의 선택 큐 소비 제한, R5 빈 번호 허용을 코드에 반영하고 정적으로 대조했다. MS-d의 Akimbo 에셋 적용과 사용자 컴파일/재생 인수는 남아 있다. **컴파일 미확인**이다. 현재 상태 원본은 [계획](../plans/2026-11-02-combat-clip-multishot-plan.md)이며 설계와 다른 결정은 구현 전에 묻는다.
