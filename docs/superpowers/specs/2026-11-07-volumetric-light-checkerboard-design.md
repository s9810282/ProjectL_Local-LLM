# 볼륨메트릭 라이트 짝수·홀수 분할 계산 설계 — 2026-11-07

작성: Codex / 사용자 요청: 현재 표현을 유지하고 매 프레임 계산을 짝수·홀수로 분할해 최적화한다.

## 1. 현재 기준과 범위

현재 작업 트리의 Feature/Compute/Settings는 앞선 산란 조사 때와 달리 `totalScattering` 스칼라를 배경에 더하는 버전이다. 현재 파일을 기준으로 하며 과거 산란 구현·프리셋을 복원하지 않는다. 기존 `CSMain`은 모든 픽셀에서 LightingSteps만큼 그림자를 읽는다.

사용자 요청을 픽셀 체커보드의 시간 분할로 적용한다. 프레임 전체를 건너뛰지 않고 `(x+y)&1` 두 그룹을 교대로 계산한다. 빛 방향·배치·카메라·효과 수식·Settings 서비스·Renderer 에셋·활성화 계약은 변경하지 않는다. 기존 산란 설계에서 제외했던 시간 재사용은 이번 별도 요청 범위다.

## 2. 계산과 자원

1. 카메라마다 RG32_SFloat 히스토리 하나를 둔다. R은 기존 totalScattering, G는 계산 때의 device depth다. 최종 배경색은 저장하지 않는다.
2. 첫 프레임은 전체 계산한다. 이후 CSMain의 dispatch 폭을 ceil(width/2)로 줄이고 `pixelX=2*threadX+((y+parity)&1)`로 실제 픽셀을 선택한다. 홀수 너비도 경계 검사한다. 미선택 픽셀은 기존 히스토리를 유지한다.
3. 별도 CSComposite는 현재 프레임의 배경에 히스토리 효과를 합성한다. 현재 depth가 저장된 값과 다르면 그 픽셀을 즉시 다시 계산해 전경 이동/가림 해제의 이전 효과를 재사용하지 않는다. RG32의 depth 비교는 정확 일치 기준으로 보수적으로 처리한다.
4. 카메라 VP/설정/주광원 변환·그림자 강도·cascade 수가 바뀌거나, 연속 프레임이 아니거나, RT 크기가 바뀌면 전체 갱신한다. 에디터 비재생·SceneView·동적 해상도·TAA 선택 상태에서도 전체 갱신한다. 카메라 이동 중과 TAA 사용 중에는 분할 절감이 없다. 재투영은 이번 범위가 아니다.
5. 고정 카메라에서 이동 차광물의 공중 그림자는 미선택 픽셀에 최대 한 프레임 이전 값이 남을 수 있다. 깊이가 같아도 그림자는 바뀔 수 있기 때문이다. 고속 그림자의 격자/깜빡임은 사용자 인수 항목이다.
6. Compute 두 패스가 같은 히스토리를 ReadWrite로 선언하고, 합성 결과를 기존 active color로 Copy한다. 새 RT는 첫 전체 계산으로 모두 초기화한다. 과거의 배경·UI·유닛 화면을 재사용하지 않는다.

정지 장면의 무거운 레이마칭 픽셀 수는 초기화 뒤 대략 절반이다. 전체 합성·Copy와 히스토리 메모리 대역폭은 남으므로 GPU 시간 50% 절감은 보장하지 않는다. RG32 히스토리는 1920×1080에서 약 15.8 MiB/카메라다.

## 3. 소유권·계약 점검

- 히스토리 자원/유효성은 전용 내부 캐시 클래스 한 곳이 소유한다. Feature는 패스와 입력을 조립하고 Compute는 기존 효과 계산/합성을 맡는다. 설정 값의 원본은 기존 Settings다(SSOT, SRP).
- BaseRenderFeature의 Pass.Dispose에서 캐시도 해제한다. 소멸한 카메라·사용 중단 카메라의 캐시를 회수한다. 설정 서비스/Scope/Factory/Group 등록은 추가하지 않는다(FW-001/002/010~012 기존 계약 유지).
- SOLID: 기존 서비스 치환·호출 계약 유지(L/I/D), 기존 Feature 안의 기능 확장(O), 자원 수명과 GPU 계산 분리(S). 새 공용 추상화는 만들지 않는다.
- 대표 변경 범위: 분할 패턴 변경은 Compute/Feature, 히스토리 무효화·해제는 내부 캐시, 조립/서비스 변경은 없음. Core·FieldCamera·Architecture 및 다른 효과 수정·검증을 요구하지 않는다(기능 변경 독립성).

## 4. Phase와 인수

단일 구현 Phase: 히스토리 수명 → 절반 dispatch/현재 배경 합성 → 정적 검토 → 사용자 Unity 확인에서 멈춘다. Test 코드·MSBuild·Unity 재생/컴파일 실행 없음. 보고 상태는 **컴파일 미확인**.

사용자 확인: 고정 카메라에서 초기 전체→짝수/홀수 번갈아 갱신, 홀수 너비/해상도 변경, 이동/줌/재활성화 직후 전체 갱신, 다중 카메라 분리, 유닛 이동·가림 해제, 빠른 그림자 변화의 잔상/격자, 기능 재생성/씬 전환 메모리, GPU Profiler의 레이마칭/합성/Copy 합계. 전체 효과의 색/강도와 조명 방향은 변경 전과 비교한다.

## 5. 구현 결과와 정적 검토

- 기존 Feature/Compute와 새 내부 `VolmetrickLightHistoryCache.cs`(.meta 포함)에 구현했다. Settings 파일·서비스·씬·PC Renderer·광원 값은 수정하지 않았다. 기존 직렬화 필드와 GUID도 유지했다.
- `TraceVolumetricLight`로 기존 계산을 추출하고 두 커널이 같은 함수를 사용한다. jitter는 실제 픽셀 좌표를 사용하므로 짝수·홀수 그룹에 따라 노이즈 위치가 바뀌지 않는다. 사용하지 않던 ShadowSteps/ShadowsColor의 CPU 전달만 제거했고 공개 설정 계약은 유지했다. LightingSteps는 최소 1로 방어한다.
- RG32 히스토리는 첫 전체 dispatch로 초기화한다. RT 재할당 시 즉시 무효화하며 GPU RT가 유실된 경우도 다시 할당한다. 실제 합성 dispatch가 기록될 때만 완료 프레임과 다음 parity를 갱신한다.
- 캐시는 다른 카메라의 Acquire가 있을 때 소멸/마지막 사용 후 2프레임 초과 항목을 회수한다. 기능 전체가 꺼져 있는 동안은 기존 BaseRenderFeature의 자원 보존 계약에 따라 유지하며 Pass.Dispose에서 모두 해제한다.
- 분할 좌표를 대수적으로 검토했다: `(pixelX+y)&1=parity`, 두 그룹이 중복 없이 전체를 덮고 홀수 너비의 초과 픽셀은 경계에서 제외된다. 예: 1920×1080은 그룹별 1,036,800픽셀, 961×409는 196,525/196,524픽셀이다. 스레드 그룹 반올림에 따른 소규모 초과 스레드는 경계 검사로 종료한다. 실행 테스트 수치가 아니다.
- 설치된 URP/Core의 ReAllocateHandleIfNeeded/ImportTexture/ReadWrite/RenderGraph 의존성 및 Unity 6000.0.73f1의 useDynamicScaleExplicit XML API를 대조했다. 패스 순서는 Trace→Composite→Copy이며, 두 Compute의 히스토리 ReadWrite 선언으로 이전 절반을 보존한다.
- 현재 Compute는 Texture2D 경로다. 배열/XR 타깃은 제외하며, RG32의 Sample/LoadStore 지원을 확인한다. 기기에서 지원하지 않으면 기능을 등록하지 않는다. 기존 PC 대상의 실제 지원·비용은 Unity 확인이 필요하다.
- 정적 diff/공백/.meta GUID 중복 확인 완료. **컴파일 미확인**, GPU 시간·화면 품질·메모리 수명은 실행 미확인이다. View 규칙에 따라 Test 코드 작성·MSBuild·Unity 컴파일/Play는 실행하지 않았다.
