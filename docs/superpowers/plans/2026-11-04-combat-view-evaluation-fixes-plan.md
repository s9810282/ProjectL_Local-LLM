# 전투 View 평가 후속 수정 — 1차~4차와 다음 작업 (2026-11-04)

> 출처: [전투 View 평가·점검](../specs/2026-11-04-combat-view-evaluation.md)의 중간 문제 29개를 코드로 다시 확인해 정한 순서(같은 날 채팅).
> 사용자 지시: "0단계 → 1차 → 2차 실행", G3-01은 "손에 남김". 이어서 "3차, 4차 진행해봐"(§8).
> 상태: **1차~4차 코드 완료, 컴파일 미확인**(전투 View 작업 규칙상 MSBuild 없음), 새 시험 없음, 시험 변경 없음, Unity 확인 대기, 커밋 전(패치 파일 둘로 전달, §8.5). 3차·4차 실행 기록은 §8이다. C7-02 2단계는 하지 않았다(Q-N10). 남은 작업의 순서는 §6이다.

## 1. 1차

### 1.1 G3-01 재생 중 놓기 → 손에 남김

- 문제: 배치 단계에서 앞 결과(등장·발동 연출)가 재생되는 동안(`CombatInputFacts.IsPresenting`, P < S)에도 유닛을 집을 수 있다. 그런데 놓으면 `CanSubmit`이 거절하고 반환값이 버려져, 유닛이 안내 없이 원래 자리로 돌아갔다.
- 결정(사용자): 손에 남김. 재생 중 칸 위에서 놓으면 놓지 않고 손에 남기고, 재생이 끝난 뒤 다음 누름·뗌에서 놓는다. 칸 밖에서 놓으면 예전처럼 취소다.
- 바꾼 곳
  - `V/Input/Interaction/PlacementDragInteraction.cs` `SelectReleased`: 제출 전에 `facts.IsPresenting`이고 칸 위면 `_pressStartedDrag = false` 뒤 돌아간다. 클릭으로 집은 상태와 같아진다.
  - `V/Input/Interaction/CombatItemDragInteraction.cs` `SelectReleased`: 대상을 먼저 찾고, 대상이 있고 재생 중이면 끝내지 않고 돌아간다. 아이템은 `CanSelect`가 `CanSubmit`을 봐서 재생 중에는 집을 수 없으므로, 집은 직후 결과가 도착한 좁은 틈만 해당한다.

### 1.2 C10-07 커서 스냅이 누를 수 없는 자리로 끌고 감

- 문제: 스냅은 포인터 자리의 UI만 보고 칸 중심으로 바로 옮겼다. 아래쪽 칸이 덱 UI 밑으로 반쯤 들어가면 커서가 UI 밑 칸 중심으로 끌려가 그 칸을 누를 수 없었다. 칸 중심이 화면 밖이면 커서가 창 밖으로 나갔다.
- 바꾼 곳
  - `V/Display/Feedback/CombatPointerMapper.cs` `TryCellCenterToScreen`: 칸 중심이 `camera.pixelRect` 밖이면 false.
  - `V/Input/Assist/CombatCursorSnap.cs` `PointerMoved`: 옮기기 전에 칸 중심을 다시 매핑해, UI에 가렸거나 다른 칸으로 잡히면 옮기지 않는다. 그 칸은 기억해 같은 칸 안에서는 다시 묻지 않는다(추가 Raycast는 칸이 바뀔 때 한 번).

### 1.3 C10-03 Nexus 착지 이펙트를 무한정 기다림

- 문제: 진입 완료 조건이 "착지 ∧ 이펙트가 풀로 돌아옴"이고 이펙트는 자연 끝이라 시간 상한이 없었다. `FallingRocks`를 Looping으로 바꾸거나 `ParticleStopNotifier`를 빼면 Nexus 스테이지 진입이 영원히 멈춘다(지금 에셋은 약 1초).
- 바꾼 곳: `V/Presentation/Entry/CombatEntryNexusAppearance.cs`. 착지 뒤 3초(`ImpactWaitLimitSeconds`, 상수)가 지나면 경고 한 줄을 남기고 기다림을 끝낸다. 남은 이펙트는 진입이 끝날 때(적 등장 뒤 `Complete` → `Cancel`) 거둔다. 지금 에셋(약 1초에 끝남)에서는 동작이 그대로다.
- 정한 것: 상한은 상수로 둠(설정 칸으로 빼면 에셋 기본값까지 다뤄야 해서). 착지만으로 완료하는 안은 쓰지 않음(적이 없는 스테이지에서 이펙트가 착지 프레임에 잘림).

### 1.4 C11-02 재생 중 유닛마다 상태 읽기 할당

- 문제: 유지 이펙트 맞추기가 Render마다 필드 유닛마다 `StatusEffectReadModel.Capture`(새 목록·배열)를 불렀다.
- 바꾼 곳: `V/Presentation/Effects/CombatStatusEffectSource.cs`. 사실 객체(`CharacterCombatFacts`, 불변 class)가 지난번과 같으면 지난 읽기를 다시 쓴다. 근거는 HUD의 GH3와 같다(보인 사실은 바뀐 유닛만 새 객체로 바꿈). 사전 둘을 번갈아 써서 이번에 없던 유닛은 저절로 빠진다.

## 2. 2차

### 2.1 C10-01 카메라를 옮긴 뒤 포인터 아래 칸을 다시 집지 않음

- 문제: 키·휠·화면 가장자리로 시점을 옮겨도 포인터 소비자에게 알리지 않았다. 공격 미리보기는 옛 칸 A에 남는데 클릭은 새로 집은 칸 B를 제출했다. 배치 Drag도 같았다.
- 바꾼 곳
  - `V/Input/Contracts/ICombatCameraControl.cs`: `Pan`이 실제로 움직였는지 bool로 돌려준다. `ZoomSeconds`(줌 렌즈가 옮겨 가는 시간)를 더했다. 구현은 `CombatCameraView` 하나다.
  - `V/Presentation/Cameras/CombatCameraView.cs`: 위 두 계약을 구현.
  - `V/Input/Cameras/CombatCameraInput.cs`: `Tick`이 "포인터를 다시 집어야 하는지"를 돌려준다. 시점이 바뀐 Tick, 줌 렌즈가 옮겨 가는 동안, 그리고 마지막으로 바뀐 뒤 한 Tick 더 참이다(실제 카메라 자리는 같은 프레임 뒤쪽, Cinemachine LateUpdate에서 옮겨지므로). 줌 렌즈 보간은 보낸 다음 프레임부터 진행하므로 보낸 Tick에는 남은 시간을 줄이지 않는다(§3 검토 M1). `TryGetPointer`를 더했다. `Clear`가 둘을 멈춘다.
  - `V/Input/CombatInputRouter.cs`: `RefreshPointer`를 더했다. 실제 포인터 이동과 같은 판정식·소유자로 보내되, 커서 스냅과 공격 Drag 후보의 이동 Drag 승격은 하지 않는다.
  - `V/Input/CombatSceneInput.cs` `TickCamera`: 카메라 입력이 참이면 마지막 포인터로 `RefreshPointer`를 부른다. 인자에 캐릭터 목록을 더했다.
  - `V/CombatViewSystem.cs` `Tick`: `TickCamera` 호출에 캐릭터 목록을 넘긴다(한 줄).
- 정한 것
  - 이동 경로를 끄는 중에 화면 끝 스크롤로 시점이 움직이면 경로가 포인터 아래 칸을 따라 늘어난다(채팅에서 알린 동작).
  - 공격 모드에서 자기 유닛을 누른 채 카메라만 옮기면 이동 Drag로 넘어가지 않는다(마우스를 움직이지 않았으므로 지금 동작 유지).
  - 다시 집기는 카메라를 움직여도 될 때(`CombatInputPolicy.CanMoveCamera`, 확인창 열림 아님 포함)만 한다.

### 2.2 C7-02 1단계 같은 프레임 UI 가림 답 한 번

- 문제: 포인터가 움직인 프레임에 Router·유닛 호버·환경 호버·경로가 같은 좌표로 UI Raycast를 4~5번 했다. 2.1의 다시 집기로 시점이 움직이는 동안에도 돈다.
- 바꾼 곳: `V/Display/Feedback/CombatPointerMapper.cs` `HitsUi`. 같은 프레임·같은 좌표·같은 EventSystem이면 앞의 답을 쓴다. `Unbind`·`Release`가 기억을 비운다. 칸 집기(카메라 Ray)는 기억하지 않는다(같은 프레임 안에서 카메라가 옮겨질 수 있어서).
- 남은 것(2단계): 프레임 포인터 표본 하나로 칸 집기까지 모으는 것은 `CombatEnvironmentHover`·`CombatPathInput`(GC 작업 파일)을 고치므로 0단계 확인 뒤.

## 3. 검토

1차·2차를 마친 뒤 읽기 전용 검토자 3명이 작업 트리 diff를 따로 봤다(컴파일·1차 동작·2차 동작). 컴파일은 아무도 돌리지 않았으므로 정적 확인이다.

- **컴파일 오류 없음.** 바꾼 서명(`ICombatCameraControl.Pan`·`ZoomSeconds`, `CombatCameraInput.Tick`, `CombatSceneInput.TickCamera`)의 구현체·호출처를 시험 폴더까지 grep했다. 구현체는 `CombatCameraView` 하나, 호출처는 각각 하나다. out 변수 범위·using·연산자(`CellCoord !=`)·cref도 확인했다. 시험 코드에서 바꾼 형식을 쓰는 곳은 없다.
- **M1(중간, 반영):** 휠 줌 뒤 마지막 다시 집기가 렌즈가 끝나기 한 프레임 전의 카메라를 봤다. 줌 보간(`CameraZoomEvent`, Global 묶음의 Delay)은 보낸 다음 프레임부터 진행하는데, 카운터는 보낸 Tick부터 남은 시간을 줄였다. 남은 시간을 먼저 줄이고 그다음 줌을 보내도록 순서를 바꿨다. 팬은 그 Tick에 자리를 쓰고 다음 Tick이 LateUpdate 뒤 자리를 보므로 문제없다.
- **낮음 셋(주석, 반영):**
  - `CombatEntryNexusAppearance`: 상한에 걸린 이펙트는 "진입 정리가 바로" 거두는 것이 아니라 진입이 끝날 때(적 등장 뒤 `Complete` → `Cancel`) 거둔다. 주석과 이 문서를 고쳤다. 동작은 그대로 둔다(상한은 프리팹이 잘못됐을 때만 걸리고, 경고가 남는다).
  - `ICombatCursorDevice.TryCellCenterToScreen` 계약 설명에 "카메라 화면 밖이면 false"를 더했다.
  - `CombatCursorSnap.SnappedCell`·클래스 설명: 이제 "옮겼거나, 칸 중심이 가려 옮기지 않기로 한 칸"이다.
- 검토자가 확인한 것(문제 아님)
  - G3-01: 손에 남김은 재생 중(P < S)일 때만이고, 대기·후처리·종료·Layer 거절은 예전처럼 끝난다. 손에 남긴 뒤 우클릭·Esc·선택 취소·전투 진입은 Drag를 끝낸다. 정보창은 Drag 중이면 열리지 않는다.
  - C11-02: `CharacterCombatFacts`는 get 전용 sealed class이고 `Capture`는 그 객체만 읽는다. 출처 인스턴스와 `Sync` 호출처는 하나씩이다.
  - C10-01: 다시 집기가 건너뛰는 수신 창구·조정자 검사는 `CanMoveCamera`(입력 준비·진입 연출·확인창)와 Tick의 `CanContinue`가 대신한다. 예외는 `GameBootstrap.Update`가 같은 오류 경계에 보고한다. 공격 조준은 같은 칸이면 일찍 돌아가고 경로는 응답을 기다리는 동안 멈추므로, 시점이 계속 움직여도 미리보기 요청이 칸 변화보다 많이 쌓이지 않는다.
  - C7-02: 같은 프레임에 새로 켠 UI는 원래도 그 프레임 Raycast에 잡히지 않아, 기억 때문에 달라지는 것은 같은 프레임에 닫힌 UI를 한 프레임 더 막는 쪽뿐이다(보수적).

## 4. Unity 확인 (사용자)

0단계를 먼저 한다. 그다음 1차·2차(U1~U11), 3차·4차(U12~U24) 순서로 본다. 한 번에 봐도 된다.
패치 둘로 나눴으므로(§8.5) 0단계(`032608bf`) → 패치 1 → 패치 2 순서로 컴파일하면 오류가 어느 쪽에서 왔는지 바로 가린다. 한꺼번에 적용했으면 파일 이름으로 가린다(§8.4).

| # | 대상 | 확인할 것 |

| U1 | G3-01 배치 | 유닛 A를 놓고, A의 결과가 재생되는 동안 유닛 B를 집어 초록 칸에 놓는다. B가 손에 남아 포인터를 따라오고, 재생이 끝난 뒤 한 번 더 클릭하면 놓이는지. 덱 카드로 고른 경우도 같은지. 칸 밖에 놓거나 우클릭·Esc를 누르면 취소되는지. |

| U8 | C10-01 줌 | 휠 줌이 끝난 뒤 호버가 포인터 아래 칸에 맞는지. |
| U9 | C10-01 경로·공격 Drag | 이동 경로를 끄는 중 가장자리 스크롤로 경로가 따라 늘어나는 것이 괜찮은지. 공격 모드에서 자기 유닛을 누른 채 키로 시점만 옮기면 이동 Drag로 넘어가지 않는지. |

| U11 | C7-02 | HUD·덱·가방·정보창 위로 마우스를 움직이며 UI 위 클릭이 필드로 새지 않는지(공격 버튼 클릭 뒤 칸 공격 안 됨). 환경 설명이 UI 위에서 숨는지. 원하면 Profiler에서 마우스를 움직이는 프레임의 `RaycastAll` 호출 수가 줄었는지. |
