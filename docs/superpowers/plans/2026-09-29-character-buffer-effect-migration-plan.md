### 3.1 Calculation and storage responsibility boundary

Core Application owns gameplay decisions: definition eligibility, initial roster policy, deterministic draw order, purchase availability and payment calculation, healing amounts, soul growth, and applied Effect/Trait/Category values. It consumes immutable Contracts facts and returns decisions or change proposals. It never allocates owned IDs, retains mutable runtime owners, or clears Buffers.

Systems processing services obtain definition and current-state facts through the existing Framework initialization/binding route, invoke Core calculations, and submit accepted proposals to Buffer publication APIs. They do not retain roster, wallet, shop-consumption, or combat-state copies. Distinct roster/draw and shop processing services keep these use-case responsibilities explicit.

Buffers own canonical state, stable owned-ID allocation, indexes/read projections, and their declared lifetimes. Their validation protects storage consistency: identity, expected values, duplicates, initialized values, bounds against the final context, and agreement between canonical and projected state. A Buffer does not decide purchase eligibility, select cards, calculate healing or damage, or execute Effects. Buffer-group operations prepare every affected replacement before the first write, then install the prepared values and return the result. Cleanup remains under the Buffer group.

The current CharacterBuffer verifies the documented soul/effective-stat relationships as a storage invariant. Tasks 5–7 must avoid introducing a second independently maintained gameplay formula in Buffer validation: establish one pure Core rule implementation when migrating those calculations and preserve a narrow, explicit consistency check at the publication boundary. Moving a rule into an internal helper alone does not change its responsibility.
