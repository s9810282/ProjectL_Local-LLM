# 전투 View 구현 계획 — 드래그와 클릭 최단 경로 이동

2026-11-17 · Phase 1~4 코드 반영 · 정적 리뷰 완료 · 사용자 Unity 우선 확인 3건 완료. 사용자 요청으로 [View 설계](../specs/2026-11-17-combat-click-shortest-move-view-design.md)를 구현 기준으로 채택했다. Core 제공 기준은 `f6b6ae1f8`이며 경로·출처·견적 소비 계약은 [전용 인계 §2~3](../handoffs/2026-11-17-combat-click-shortest-move-view-handoff.md)에 있다. Core 실행 검증은 미완료다.

## 진행 순서와 리뷰 지점

| Phase | 선행 | 리뷰할 결과 |
|---|---|---|
| 1. 범위 응답 수명 | Core 제공 코드 | 선택한 유닛의 현재 범위를 같은 사실로 표시하고 경로를 조회할 수 있다. |
| 2. 드래그의 공통 견적 분리 | 1 | 기존 드래그만 연결한 상태에서 견적 승인·거절·늦은 제출·취소를 비교할 수 있다. |
| 3. 클릭 미리보기 연결 | 1·2 | 실제 필드 입력으로 후보 선택·교체·취소와 정지 칸 표시를 확인한다. 이 Phase에서 클릭 Move 제출은 0건이다. |
| 4. 두 번째 클릭으로 제출 | 3 | 미리보기를 본 뒤 시작한 동일 목적지 클릭만 Move 1건을 제출한다. |
| 5. 통합 리뷰와 Unity 인수 | 4 | 정적 근거와 사용자가 실제로 관찰한 결과를 구분해 기록한다. |

각 Phase 끝에서 변경 파일·완료 Task·정적 확인·남은 Unity 항목을 보고하고 멈춘다. 다음 Phase는 사용자 지시에 따라 시작한다. 설계 변경이 필요하면 구현 전에 논의한다. 코드 검토와 Unity 결과는 별도로 기록하며, 실행하지 않은 사례는 미확인으로 둔다.

**현재 브랜치 적용 범위.** `c9b8c4d64`에서 전투 View의 RecordInputOnly와 관련 시험이 제거됐다. 이전 설계의 해당 모드 재생 항목은 현재 브랜치에서 적용 대상 밖이다. 그 항목의 의도인 ‘견적·문맥 없는 Move 0건’은 현재 Live 입력의 대기·거절·오래된 응답 사례로 확인한다.

## Phase 1. 수락한 이동 범위를 출처와 함께 보관

주요 파일은 `MovePath/CombatMovementRangeRequest.cs`, `CombatMovementRangeTracker.cs`, `CombatPathInput.cs`다. 기존 선택 범위와 드래그 범위가 같은 Tracker를 사용한다. [현재 입력 소스 폴더][input]

- [x] **1.1 범위 사실.** `CombatMovementRangeFacts` 생성·비교에 QueryRevision을 추가한다. 선택 범위와 드래그의 두 생산 경로(`RangeFactsOf`, `CurrentRangeFacts`)를 함께 맞춘다. 빈 범위 근거를 FactsReader가 조회할 때 현재 revision은 전투 Buffer에서 읽어 사실 공급자 재호출을 피한다.
- [x] **1.2 응답 수락과 갱신.** `TryConsume`에서 기존 세대·요청/슬롯·전투·행위자·원점·결과 순번과 함께 요청 당시 revision, 현재 revision 및 양수 `SourceRevision`의 일치를 검사한다. 다른 번호의 늦은 응답은 현재 요청을 보존한다. 자기 요청의 사실이 낡은 경우에는 자기 번호만 회수하고 현재 범위를 다시 조회할 수 있게 한다.
- [x] **1.3 조회와 정리.** Tracker에 수락한 결과와 표시 사실을 함께 보관한다. 소비자가 ‘미준비 / 수락했으나 해당 경로 없음 / 현재 경로 있음’을 구별하게 한다. 실패와 성공 빈 범위도 수락 완료다. 목적지는 Core가 검증한 경로의 끝점에서 생성하고, View는 `TryGetRoute`의 불변 참조를 사용한다. 표시용 결과의 해제와 턴 종료 판단용 성공 빈 범위 근거의 기존 수명을 구분한다.

**완료 기준.** 같은 사실의 범위는 슬롯 반납 후에도 사용 가능하고, revision만 바뀌어도 이전 경로는 조회되지 않는다. 사용자 Unity 확인은 유닛 선택 시 범위, 범위 갱신 도중 원점 드래그, 빈 범위 유닛의 기존 턴 종료 판단이다.

## Phase 2. 드래그에서 견적 검증·명령 제출만 분리

주요 파일은 `MovePath/CombatMovementInteraction.cs`, `CombatPathInput.cs`와 같은 폴더의 신규 내부 견적 객체 및 `.meta`다. 이 Phase에서는 기존 드래그가 공통 코드의 첫 소비자다.

- [x] **2.1 견적 소유 이전.** 요청 번호·요청 경로·세대/요청 버전·승인 문맥과 슬롯 소유 검사를 공통 객체로 옮긴다. 현재 연결에 Path가 한 인스턴스를 두고 사용한다. `RequestPreview`의 동일 초안 중복 억제, MoveRange 이후 `ResumePreview` 유예, 번호 기반 `ClearPreview`를 유지한다.
- [x] **2.2 응답 검증.** 기존 `OnPreview`가 확인하는 요청 버전·번호, 현재 슬롯의 Move/행위자/전체 경로, `ValidStepCount`, `PathMovement.RequestedPath`, 기대 사실·전투 ID·행위자·관찰자·의도·경로가 맞는 `MovementContext`를 대조한다. 오래된 응답 무시, 현재 거절 응답, 현재 성공 문맥 불일치를 호출자가 구분해야 한다. 드래그의 점유 거절, 유효 접두 복구와 거절 안내는 기존 편집기에 둔다.
- [x] **2.3 제출과 대기.** 승인 경로·문맥으로 `CombatViewCommandData.Move`를 만들어 기존 sink/계측을 통해 제출하는 코드를 한 곳으로 모은다. 드래그의 `Confirm`과 `_frozen`이 제출 **시점**을 결정한다. 이미 승인됐을 때와 Release 뒤 승인이 올 때 모두 정확히 한 번 제출한다. 취소 시 미처리 제출 번호를 유지하고 기존 `HandledCommandNumber` 경계를 지킨다.

**완료 기준.** 추출 전후 드래그의 ‘입력 → 견적 → 제출 번호’ 흐름을 나란히 리뷰한다. 사용자 Unity 확인은 경로 그리기/되짚기, 도약·자리 교환, 거절 후 다시 그리기, 승인 전 Release, 원점만 누르기, UI 위·필드 밖 Release, 공격 드래그 인계다. 이 단계에서 차이가 관찰되면 클릭 연결과 분리해 원인을 찾을 수 있다.

## Phase 3. 선택 전에 클릭을 분배하고 예상 도착 위치 표시

주요 변경은 [씬 입력 조립][factory], `CombatSceneInputDriver`·`CombatSceneInput`·`CombatInteraction`·`CombatInputRouter`의 포인터 전달 경계, `CombatPathInput` 및 신규 내부 클릭 객체와 `.meta`, [선택][selection], `ICombatMovementFeedback`과 [이동 Presenter][presenter]다. 아래 Task는 하나의 Phase 안에서 조립해 첫 클릭을 실제 입력부터 화면까지 리뷰한다.

- [x] **3.1 누름 판정.** Driver의 `InspectUnit` 전 한 번만 UI 차폐·필드 칸·점유를 판정한다. 점유는 선택이 쓰는 `ICombatInspectionFactsReader.TryPick`를 공유한다. 표시/선택 쪽에서 제공하는 좁은 집기 결과를 Factory가 연결한다. Driver에는 이동 규칙을 넣지 않는다. 같은 결과를 Inspect, Path, 환경 누름에 전달하고 외부 콜백 뒤 기존 연결을 재검사한다.
- [x] **3.2 분배와 Release 귀속.** 설계 §3의 순서대로 기존 전경·UI, 선택 앵커, 다른 점유 칸, 범위 대기, 합법 빈 칸, 범위 밖을 구분한다. 원점은 후보 정리 후 기존 드래그, 다른 점유 칸은 기존 선택과 후속 라우팅이다. 범위/가용성/슬롯 대기의 빈 칸은 해당 누름만 소비하고 목적지를 예약하지 않는다. 소비한 Press가 환경 고정이나 선택 해제로 중복 전달되지 않게 하되 공통 버튼·가용성 동기화는 수행한다. 취소된 누름의 Release가 다른 모드에 전달되지 않도록 한다.
- [x] **3.3 후보와 견적.** 클릭 객체에 누른 칸·누를 때의 용도·후보 세대를 보관한다. 같은 칸 Release 시 현재 사실을 다시 읽어 첫 후보를 만들거나 다른 합법 목적지로 교체하고 Phase 2의 공통 견적을 요청한다. 승인 전 동일 칸 Press는 Release까지 무동작이다. 거절 시 기존 사유를 표시하며 같은 칸의 다음 클릭은 새 견적 요청으로 취급한다. 이전 A 응답이 새 A 후보에 도착해도 세대·번호·전체 경로를 대조한다.
- [x] **3.4 슬롯과 수명.** 후보가 대기/표시 중이면 선택·스킬 가용성, 유닛 호버, 포효·HUD 조회가 전경 Move에 양보하게 한다. 범위 대기 클릭은 배경 쓰기를 허용한다. `IsInputOwnerActive`의 소비자별로 확인해 선택 변경·커서 스냅·Undo에 드래그 상태를 잘못 전파하지 않는다. 슬롯 상실, revision·원점·선택·턴 변경, 결과 재생, 공격/스킬/배치 진입, 우클릭, 캡처/포커스 상실, 설정 Layer 전환, Detach에서 누름·후보·자기 요청만 정리한다. 낡은 revision을 발견한 목적지 누름은 소비하고 최신 범위만 재조회한다.
- [x] **3.5 화면 표시.** 첫 클릭 직후 전체 요청 경로를 중립으로 그린다. 성공하면 원래 목적지에 끝점 강조를 유지하고 고스트는 `FinalStop`의 `CellSurfaceToWorld` 위치에 둔다. 표시 완료 후 같은 세대인지 재검사해 ‘표시됨’을 기록한다. 포인터·카메라 이동은 후보를 편집하지 않는다. 교체·취소·표시 예외·씬 해제에서 경로/끝점/고스트를 정리하고 원본 투명도를 복구한다.

**완료 기준.** 범위 대기 클릭과 첫 클릭, 표시 후 재클릭까지 모두 클릭 Move 0건이다. 첫 클릭은 견적과 표시까지 도달한다. 사용자 Unity 리뷰는 토네이도 칸, 다중 칸 유닛·구조물, 후보에서 다른 유닛 선택 및 원점 드래그, 범위 밖·빈 범위·실패, 카메라 이동, 높이가 다른 칸·강제 이동 견적, 설정 열고 닫기다. 같은 장면에서 기존 드래그는 이동할 수 있어야 한다.

## Phase 4. 표시 이후 시작한 두 번째 클릭으로 Move 1건 제출

주요 파일은 Phase 3 클릭 객체와 `CombatPathInput`이다. Phase 2의 견적·제출 코드와 Phase 3의 누름 소유 결과를 소비한다.

- [x] **4.1 확정할 Press 식별.** 표시가 완료된 현재 후보의 **요청 목적지**를 누른 경우에만 그 세대·견적 번호를 확정용으로 캡처한다. 예상 정지 칸이 다를 수 있다. 견적 대기 중 시작한 Press의 용도는 응답 도착 후에도 바꾸지 않는다.
- [x] **4.2 Release 재검사와 제출.** 동일 필드 칸, UI 차폐, 후보 세대·요청 번호, 전투·턴·행위자·원점·결과 순번·revision, `CanEditPath`(선행 미처리 명령 포함), 현재 슬롯·전체 경로·승인 문맥을 대조한다. 튜토리얼·모달·연출 제한을 기존 정책에서 받는다. 확정 자격을 먼저 소비하고 공통 제출 입구를 한 번 호출한다. 취소나 다른 칸 Release는 정리만 한다.
- [x] **4.3 제출 뒤 처리.** 제출 번호·대기는 기존 이동 수명이 소유한다. 후보 표시를 내려도 미처리 명령은 보존한다. 결과 표시·행동 사용·Undo는 기존 이동 경로를 따른다. 첫 클릭이나 클릭의 응답 처리에는 제출 호출이 없는지 정적으로 대조한다.

**완료 기준.** 늦은 응답, 대기 중 Press/표시 후 Release, 확정 Press 뒤 revision 변경은 각각 0건이다. 표시 뒤 새로 시작한 같은 목적지 클릭만 1건이고 연타·반복 Release는 추가 0건이다. 클릭과 드래그가 동일 경로를 승인받았을 때 사용자 Unity에서 이동 결과와 가능한 Undo를 비교한다.

## Phase 5. 통합 리뷰와 인수 기록

- [x] **5.1 정적 리뷰.** 설계 §7 기준으로 경로 원본(Core), 수락 범위(Tracker), 선택, 후보, 견적/제출 번호, 표시 자원에 소유자가 하나씩 있는지 확인한다. SOLID는 실제 변경 단위로 점검한다. 클릭 확정 규칙은 클릭 객체, 드래그 편집은 기존 편집기, 시각 변경은 Presenter, 의존성 연결은 Factory에 머물고 공통 견적 변경만 두 입력을 함께 검증해야 한다. 기존 sink·입력 Submit·등록/수명·표시 해제의 JMH/FW 계약과 새 C# 파일의 `.meta`를 확인한다.
- [ ] **5.2 사용자 Unity 확인.** 설계 §8의 각 행에 대해 실제 입력 순서, 화면에 표시된 경로/정지 칸, 입력 전후 Move 명령 번호 또는 건수, 선택·고스트 정리 결과를 기록한다. 특히 범위 수락 후/견적 후/확정 Press 후 revision 변경, A→B→A 지연 응답, 슬롯 경쟁, 강제 이동, ESC 설정 복귀를 구분한다. 정상 플레이에서 재현하지 못한 항목은 정적 근거와 함께 미관찰로 남긴다.
- [ ] **5.3 인계.** Phase별 변경·정적 근거, 사용자가 확인한 컴파일/재생 결과, 잔여 사례와 담당을 이 계획에 기록한다. Core 제공 계약의 불일치가 확인되면 요청 번호·출처 revision·기대/관찰값을 갖춰 Core 작업자에게 전달할 내용으로 정리한다.

**작업 규칙.** View Test 코드를 작성하지 않고 전투 View MSBuild를 실행하지 않는다. 기존 시험은 우리 변경으로 컴파일이 깨질 때만 필요한 호출을 최소로 맞춘다. 우리 시험의 실행 실패는 검증 의도를 보존해 호출만 맞추고, 타인 시험의 실행 실패 수정은 먼저 묻는다. 컴파일·재생은 사용자 Unity 확인이다. 커밋·push는 사용자가 한다.

### 드래그 재진입 후속 수정과 7기준 재검토

| 중간 지적 | 수정 후 Unity에서 확인할 동작 |
|---|---|
| 통과 가능한 칸을 범위 이탈로 오인하거나 직전 견적의 도착 시점에 따라 수동 경로를 교체함 | 도약으로 유닛이나 벽을 거쳐 최단 경로와 다른 합법 경로를 그리면 그대로 이동한다. 새 칸까지 연장한 수동 경로 전체가 점유·이동 한도로 거절된 경우, 해당 칸에 서로 다른 최단 경로가 있으면 새 견적으로 승인받는다. 이동 가능 범위 밖에서 기존 경로로 되짚으면 접두 경로를 유지한다. |
| 이미 보인 범위의 원본만 바뀌면 드래그가 계속되면서 보드 재진입이 막힘 | 드래그 중 행위자와 결과 번호가 같아도 QueryRevision이 바뀌면 해당 드래그가 취소된다. 이전 버튼을 놓아도 제출은 0건이며 선택한 유닛의 범위가 갱신된 뒤 새 드래그나 클릭을 시작할 수 있다. |
| 보드 재진입 직후 놓으면 범위 응답을 기다리는 동안 숨은 고스트가 동결됨 | 버튼을 누른 채 보드 밖으로 나가면 고스트는 무효 색으로 커서를 따라간다. 범위 응답 전에 타일 안쪽으로 돌아와 놓으면 고스트가 그 월드 위치에 중립 색으로 남고, 이동 가능한 칸이면 견적 승인 뒤 한 번 이동한다. 보드 밖이나 UI에서 놓으면 취소한다. |

SSOT·SOLID·기능 독립성은 수동 경로 편집과 클릭 확정을 각각 추적했다. 경로 복구는 드래그가 담당하고 두 입력은 같은 견적·전체 경로 대조·제출을 사용한다. JMH/FW·C#/Unity는 기존 Buffer 슬롯과 고스트 표시 수명을 따른다. 위 세 건의 Unity 재생은 확인 대기다.
