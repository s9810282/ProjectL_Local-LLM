# 게임 설명의 수치 대응 — Task와 Phase 계획

- 작성·갱신: 2026-11-02, View 작업.
- 원본 설계: [현황 조사와 설계안](../specs/2026-11-02-description-numeric-values-design.md).
- 상태: **A 환경·D 회복, B 특성 33종·59개 토큰 등록/읽기 연결 코드 반영(§13). SO 본문 이전은 7종. 나머지 문구·목록/문자열 표시와 C·D 잔여·A7은 남음. 전체 완료 아님, 컴파일 미확인.**
- 전체 원칙: 최초 계획은 각 Phase 후 리뷰였으나 사용자가 “Phase 쭉 진행해”라고 지시해 이번 작업의 후속 Phase를 연속 진행한다. 설계와 달라지는 결정은 구현 전에 묻는다. Test 코드 작성·MSBuild·커밋·push 금지. Core 코드는 별도 명시 지시 없이 수정하지 않는다.

## 1. 실행 순서

| Phase | 범위 | 시작 조건 |
|---|---|---|
| 0 | 현재 경로 조사, 설계·계획, Core 요청 작성 | 이번 단계에서 완료 |
| A | 공통 치환 부품과 기존 환경 수치 경로 정리 | 2026-11-02 승인·코드 반영, Unity 확인 대기 |
| B | 특성 설명을 개체/등급별로 통합 | 후속 진행 승인 유지, `78fdc81` 확보. 토큰 정의 → 연결 → 문구 순서 |
| C | 아이템·유물 효과 설명 연결 | C 진행 지시, 각 효과의 공개값 확보 |
| D | 훈련·증강·강화·회복 설명 본문 | D 진행 지시, 각 선택지의 설정값 확보. 회복은 기존 공개값으로 독립 진행 가능 |
| E | 전체 소비 경로 누락 점검·인계 | 대상 Phase 구현 인수 후 |

Phase A는 이미 공개된 환경값만으로 진행할 수 있다. 미공개 고지대/모래폭풍 값은 확보 후 별도 후속 Task로 수행하며 기존 숫자를 임의 변경하지 않는다. 후속 Phase 연속 진행은 승인됐으므로 B/C/D의 공개 계약 대기와 독립적인 Task를 먼저 처리한다. Core 직접 수정은 이 승인에 포함되지 않는다.

## 3. Phase A — 기존 환경 치환과 공통 부품

- [x] A1. 대상 환경 SO와 운영 등록 목록을 대조해 `키/필드/토큰/공개 출처/소비 화면` 목록 확정. 기존 `{n}` 의미도 기능별로 기록([작성 안내](../viewDocs/description-token-guide.md)).
- [x] A2. 설계 D2~D3의 무상태 공통 치환 부품·`.meta` 작성. 문법/필수값 오류, escape, 숫자 형식, Rich Text/줄바꿈 보존 코드 반영. 실행 미확인.
- [x] A3. `CombatEnvironmentText`의 종류별 값 연결을 환경 기능 내부 변환으로 분리하고 기존 공개값을 사용. 수집·공개 여부·중복 문구 처리·호버 범위 정책 유지.
- [x] A4. 현재 연결된 지뢰/깃발/칸 보정/약한 지반/먼지 흔적/화약통/보급품/토네이도/낙석만 필요한 틀 이전. 신규 미공개값이나 장애물 상세창 활성화 제외.
- [ ] A5. 사용자가 Unity에서 서로 다른 수치의 동일 종류 원본, 남은 지반 횟수, 토네이도 주기, 낙석 비율, 줄바꿈·색상 확인. 에셋 변경 시 기존 `DataBaseAssetTests` 포함.
- [x] A6. 실제 변경 범위·수치 출처·잔여·컴파일 미확인을 §9에 기록하고 코드 구현 Phase 종료. A5 사용자 확인은 대기.

Core 값 공개 후 후속 A7: 고지대/모래폭풍, 지뢰 파급 등 남은 규칙 수치만 추가한다. 원래 A 완료와 전체 환경 대응 완료를 구분한다.

## 4. Phase B — 특성의 전투·손패·덱 설명

- [x] B1a. 현재 등록과 신규 정의안을 구분한 토큰 이름·원본 필드·의미/단위·시점 표 작성. [작성 안내 §8](../viewDocs/description-token-guide.md#8-문구-이전에-정할-토큰-정의안-2026-11-02). 기존 5종 이름 유지. 목록/문자열·복수 특성 원본은 미결 표시 설계로 분리.
- [ ] B1. 설계 §2.2의 모든 특성을 운영/퇴역/미사용으로 분류하고 수치별 읽기 계약 확정. 전투와 보유 설명의 설정 의미가 동일한지 확인.
- [ ] B2. 종류별 typed 값 변환과 불변 등록 목록 조립. 공용 부품은 특성 키를 모르게 유지. **33종 단일 수치 59개 등록 완료(§13), 목록/문자열 잔여.**
- [ ] B3. `UnitCardTraitContent`를 공용 내용 조립 역할로 제한. 숫자 문장을 SO 틀로 이전하되 가용성/일부 사용 불가 안내 유지.
- [x] B4. `UnitCardUI`, `DeckEditModelBuilder`/표시 모델, `DeckSlotInfoUI`, `CombatInspectionInfoMapper` 및 손패 경로에 같은 의미의 설정값 전달. `TraitSettingsSet` 사용, 상세창은 같은 전투 표시의 설정 참조 유지(§13). **코드 반영, Unity 확인 대기.**
- [ ] B5. 코드 본문 생성/수치 줄과 고정 SO 본문의 중복 제거. 기본/강화/훈련 등급의 숫자를 각각 보유/전투의 실제 공개값에서 사용.
- [ ] B6. 사용자가 Unity에서 같은 CharacterKey의 다른 등급·강화 두 개체, 덱→손패→배치→복귀, 적 특성, 미지원 특성, 표시 중 갱신 시점 확인.
- [ ] B7. 인수 범위와 아직 부족한 공개값을 기록하고 Phase 종료.

Core가 일부만 공개하면 해당 키만 구현 완료로 기록한다. 나머지 키를 기본 수치로 채워 B 전체 완료로 표시하지 않는다.

## 8. 확인 규칙

정적 확인은 실제 변경 파일의 diff, 참조·등록·토큰 대응을 확인한다. 이를 컴파일이나 실행 성공으로 보고하지 않는다. 사용자 Unity 확인 전 보고에는 **컴파일 미확인**을 적는다. 기존 시험은 컴파일이 깨지는 최소 호출 조정만 허용하고, 실행 실패를 임의로 고치지 않는다. 에셋 변경 시 기존 `DataBaseAssetTests`를 사용자 확인 항목에 넣는다.

## 9. Phase A 실행 기록 (2026-11-02)

사용자가 “오케이 일단 이 방향으로 진행하자”라고 승인했다. 승인 직전 합의는 설명 종류별 토큰/공개값 등록, 동일 등록으로 문법 검사, 미등록 이름의 오류 처리다. 이번 실행은 Phase A까지이며 B~E나 Core 구현으로 확대하지 않았다.

### 구현

| 파일/영역 | 반영 |
|---|---|
| `RuntimeSystem/Common/Descriptions/DescriptionToken.cs` | 토큰 이름·별칭·typed 공개 수치 읽기를 하나로 정의. 종류별 `From<TSource>` 형식 검사 |
| 같은 폴더 `DescriptionTemplate.cs` | 생성 시 이름/문법/중복/미등록 검사, 리터럴·값 읽기로 준비. 문화권 독립 숫자, `{{`/`}}`, 빈 설명, Rich Text/줄바꿈 보존 |
| `Combat/Input/Assist/CombatEnvironmentTokenBindings.cs` | 환경별 토큰 등록 원본. 기존 `{n}`은 해당 숫자의 별칭으로 유지 |
| 같은 폴더 `CombatEnvironmentDescriptions.cs` | 준비된 틀과 현재 환경 사실 연결. 같은 기믹/원본으로 토네이도 주기·낙석 비율 조회. 새 상태 저장 없음 |
| `Factory/Runtime/InGame/View/CombatEnvironmentDescriptionFactory.cs` | 등록된 외형만 한 번 조사하여 틀 검사·조립. 선택적 미등록 외형은 실제 사용 때 기존 조회 경로가 요구 |
| `CombatEnvironmentText.cs`, `CombatSceneInputFactory.cs` | 수집과 치환 분리, 로컬 부품 주입. 기존 공개 여부·호버 셀·문구 중복 처리·표시 순서 유지 |
| View SO 6개 | 지뢰/화약통 `{피해량}`, 깃발 `{우선도증가량}`, 약한 지반 `{붕괴횟수}`, 토네이도 `{이동주기}`, 낙석 `{최대체력손실률}`로 기존 `{n}` 이름만 변경 |

새 C# 5개와 `.meta` 5개, 새 폴더 메타 2개를 함께 추가했다. 보급품·먼지 흔적의 기존 명명 토큰과 빈 PresenceModifier 문구는 에셋 변경 없이 연결했다. 하붑/기존 고정 환경 문구도 수치 토큰이 없는 틀로 검사한다. 원문에 고정된 나머지 규칙값은 A7/Core 요청 대상이며 전체 수치 대응 완료로 보고하지 않는다.

### 정적 확인과 구조 검토

- 기존 소스 diff와 에셋 diff를 대조했다. 에셋 변경은 6개 파일의 토큰 이름 각 1곳뿐이다. 해당 에셋→외형 Table, 관련 6개 Table→ViewGroup 등록을 확인했다.
- 허용 토큰과 실제 SO의 토큰을 대조했다. 현재 출력에 필요한 getter는 이전 구현과 같은 공개 필드다. 지반 잔여값·먼지 흔적별 값·토네이도 멤버별 값은 기존 현재 사실에서 읽는다.
- 기존 생성자 참조는 운영 Factory 한 곳이며 `Assets/Tests`의 관련 직접/문자열 참조가 검색되지 않았다. 기존 시험 수정 없음.

### 13.1 실행 결과와 정적 확인

- 변경은 C# 8개와 View SO 2개다. 신규 C#·메타·서비스·UI·씬/프리팹 연결 없음. 보유/덱은 기존 `DescriptionSource` 전달을 그대로 사용하므로 Deck 모델/Builder/슬롯 코드는 다시 수정하지 않았다.
- `TraitDescriptionBindings`에 33개 키·59개 getter를 등록했다. `TraitDescriptionBinding`은 소유 개체 선택 delegate를 제거하고 `DescriptionToken<TraitSpec>`만 보관한다. Formatter는 키로 `TraitSettingsSet`에서 선택하고 기존 필수값/형식/문법 오류를 유지한다.
- `UnitCardTraitContent`의 숫자 원본은 `TraitSpec`, 사용 불가/일부 사용 불가 안내는 기존 상태/가용성 snapshot이다. 기존 `ConfiguredValues` 코드를 지우고 위압/재생의 같은 수치 줄을 SO로 옮겼다. 이제 보유/덱도 위압/재생 수치를 표시한다.
- `CombatSceneDisplay`가 같은 표시의 설정을 Presenter에 전달하고 Mapper에는 해당 캐릭터의 `TraitSettingsSet`만 넘긴다. 구조물은 특성 설정을 읽지 않는다. UnitCardUI는 기존 캐릭터 읽기 경계에서 해당 전투 설정을 사용한다.
- 정적 대조: 단일 수치 프로퍼티 59개가 등록과 모두 대응, 종류 키/typed spec/문서의 이름·필드 일치, 키 안 중복 토큰 없음. 토큰을 쓰는 특성 SO 7개의 모든 이름과 Table 등록 확인. 옛 설명 속성 5개의 View 참조 검색 결과 0. 호출부는 새 인자와 대조했고 Test 파일 수정 없음.
- 단독 행동의 `ResetEveryControllerTurnEnds`는 현재 규칙이 자기 진영 종료 횟수로 사용한다. 이름은 보존하고 작성 안내의 단위를 실제 규칙에 맞게 정정했다. 게임 규칙은 수정하지 않았다.
- SSOT/SOLID/JMH/FW: 공통 parser 변경 없이 종류별 등록이 허용 목록과 값 읽기를 함께 소유. 기능은 typed Contracts만 받으며 Factory/서비스 Export/루트 Builder/UI 등록/입력 수명 변경 없음. 문장 수정은 SO와 해당 특성에 한정한다.

이번 완료는 **토큰 등록과 읽기 연결**이다. 모든 Description 본문 이전이나 Unity 인수가 아니다. 사용자 확인 항목은 위 BT5와 [작성 안내](../viewDocs/description-token-guide.md)를 따른다. Core/Buffer/Test 수정·MSBuild·Unity 실행·커밋·push·외부 발송 없음. **컴파일 미확인.**

## 14. 웹 제출본의 특성 42개 SO 반영 (2026-11-03)

사용자가 `project-l-descriptions (1).json`에서 완료된 특성 42개만 반영하도록 요청했다. 입력은 `project-l-description-submissions` v1, 내보낸 시각 `2026-11-03T03:11:09.189Z`다. 61건 중 특성 제출 60건에서 `entryId`별 `createdAt`이 가장 최근인 42건을 선택했다. 이전 특성 제출 18건과 랜턴 외형 제출 1건은 반영하지 않았다.

- `ViewGroup/TraitVisual/Item` 아래 해당 SO 42개의 `traitVisualData.description`만 변경했다. 가시밭 `defenseReductionDescription`과 먼지 연막 `trailDescription`은 제출본과 이미 같아 그대로 유지했다. 42개 SO의 총 44개 설명 필드가 최신 제출값과 일치한다.
- 제출 문구의 줄바꿈, 고정 수치, 토큰, 말미의 폐기·보류 표기를 그대로 보존했다. 문구의 표기를 에셋 삭제나 특성 비활성화 지시로 해석하지 않았다. 해당 표기가 있는 항목은 2연발·관통 볼트·도어 브리칭·산탄(폐기 여부 질문)·연쇄 폭발(보류)·이동 후 공격 할인·집중·행운의 탄환이다.
- 정찰 부대에는 제출 메모 `이거 좀 난해해서 다시 수정할 것 같음.`이 있다. 설명에는 최신 제출 본문만 넣고 이 메모는 후속 검토 사항으로 기록한다.
- 적용 전 현재 SO 설명과 내보내기 당시 원문을 대조해 충돌 0건을 확인했다. 경로·에셋 이름·허용 필드를 대조했고 사용한 토큰은 현재 특성 등록 및 먼지 연막 호버 계약에 모두 존재한다.
- 적용 후 YAML을 다시 읽어 44개 설명의 문자열 일치를 확인했다. 설명 필드를 제외한 직렬화 데이터의 해시가 전부 동일하므로 키·이름·아이콘·연출·참조 값 변경은 없다. 대상 diff 공백 검사 통과. 기존 작업 트리의 다른 변경은 유지했다.

SSOT/SOLID/JMH/FW: 문구 값만 View SO에 반영하고 기존 토큰 등록·Formatter·서비스 조립·입력·씬 수명은 그대로 사용한다. Core·Buffer·C#·Test 코드 수정, MSBuild·Unity 실행, 커밋·push는 하지 않았다. **컴파일 미확인.** 사용자는 Unity에서 기존 `DataBaseAssetTests`와 특성 설명의 토큰 치환·줄바꿈 표시를 확인한다.
