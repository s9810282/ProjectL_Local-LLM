# Combat 선택 유닛과 HUD 사전 준비 작업 계획

작성일: 2026-11-02  
작성: Codex  
설계: [선택 유닛과 HUD 사전 준비](../specs/2026-11-02-combat-selected-unit-prewarm-design.md)  
갱신일: 2026-11-03

상태: P1~P4 코드 반영과 정적 검토 완료. Unity 기능·성능 인수 대기.

사용자가 정한 네 단계에 맞춰 선택 대상 확정 → 모델과 HUD 생성 → 첫 활성화와 UI 갱신 대기 → 배치 재사용 순서로 진행한다. **2026-11-03 사용자 지시로 P4까지 연속 구현 후 검토했다.** 아래 체크는 코드 반영 기준이며 Unity 인수를 대신하지 않는다.

## 작업 제한

- Test 코드를 작성하지 않고 MSBuild를 실행하지 않는다. 컴파일·재생 확인은 사용자가 Unity에서 수행한다. 필요 시 사용자의 computer-use 측정 지시에 따라 프로파일링하며 실행한 범위만 기록한다.
- Core·FieldCamera·Architecture는 수정하지 않는다. 필수 계약이 부족하면 설계를 변경하기 전에 사용자에게 알리고, Core 변경 요청은 지정 인계 문서에 기록한다. 그 문서를 수정할 때는 제목과 갱신일도 함께 바꾼다.
- 기존 사용자 변경과 다른 기능의 계획·설계는 유지한다. 커밋·push는 하지 않는다.
- 이번 범위에 포함하는 공용 변경은 설계 P6의 로딩 준비 완료 계약이다. 기존 LodingNode의 동기 실행 순서와 AfterLoad의 카메라 연결을 보존한다.
- 추가 API·파일 이름은 구현 전에 해당 Phase에서 확정하되 책임·공개 의미·소유권이 설계와 달라지면 먼저 확인한다. 새 C# 파일에는 .meta를 함께 둔다.

## Phase와 완료 조건

| Phase | 사용자 단계 | 산출물과 완료 조건 |
|---|---|---|
| P1 | 1 선택 목록과 수량 | 확정 RunDeck 기준의 준비 대상 읽기. 선택하지 않은 보유 유닛 제외, 같은 종류 여러 개체 유지. |
| P2 | 2 모델과 HUD 생성 | 기존 풀·생성 경로를 사용하는 준비 부품. 모델·클립·체력 텍스트·HUD를 확보하고 필요한 데이터 적용. |
| P3 | 3 활성화와 첫 UI 갱신 | 로딩이 준비 완료까지 기다리고, 렌더 가능한 첫 UI 갱신과 정리를 완료한 뒤 Reveal. |
| P4 | 4 배치 재사용 | 실제 첫 배치가 준비 자원을 사용. 최신 상태 적용, 취소·재진입 회귀와 전후 성능 인수. |

## P1 선택 대상과 수량

- [x] `IRunDeckReadSink`와 `ICharacterBufferReadSink`를 기존 Buffer 조회 경로에서 받는 진입 준비용 읽기 부품을 만든다. 예: `Combat/Display/Unit/CombatUnitPreparationReader.cs`.
- [x] OrderedIds → 보유 ID·EntityKey → 가능한 경우 현재 CharacterData의 대응을 고정한다. 수량을 종류별로 집계하면서 서로 다른 보유 개체를 유지한다.
- [x] 메인, 같은 종류의 여러 서브, 선택되지 않은 보유 유닛, 초기 손패 밖의 선택 유닛, 개발용 사전 배치 유닛을 구분한다. 이미 표시 중인 선택 개체는 중복 확보하지 않는다.
- [x] RunId·DeckRevision·BattleInstance·연결 수명에 귀속된 작업 입력을 정의한다. 필수 데이터 불일치는 명확한 예외로 보고한다.
- [x] 드로우 전 유닛의 전투 사실 부재를 정상 상태로 다룬다. 실제 사실 적용과 공통 자원 준비를 구분하고 가짜 CharacterCombatFacts를 만들지 않는다.
- [x] 이 Phase에서는 게임 진입·배치 동작을 변경하지 않는다. 필요한 읽기 연결은 Factory 또는 기존 서비스 바인딩에만 둔다.

검토: 작은 선택 예시로 대상 수량과 제외 목록을 수동 대조한다. 전체 Owned 또는 현재 Characters만 읽는 잘못된 축약이 없는지 확인한다. Test 코드 없음. 컴파일 미확인 상태와 Unity 확인 항목을 보고한 뒤 멈춘다.

## P2 모델과 HUD 준비 부품

- [x] `FieldUnitPresenter`에 기존 Rent/CreateView/EnsureUnitHud를 조합하는 명시적 준비 입구를 둔다. 초기화 구현을 예열용으로 복사하지 않는다.
- [x] 같은 종류의 필요한 수량을 동시에 확보하여 서로 다른 객체를 준비한다. 준비 대여의 소유자·반환 책임을 명시한다. CustomPool 자체는 수정하지 않는다.
- [x] `FieldUnitView`의 모델 외형·UnitClipChannel·체력 텍스트와 최종 UnitHUDLayer 아래 HUD를 준비한다. 정상 배치에서 다시 생성하거나 부모를 옮기지 않아도 되는 상태로 만든다.
- [x] 실제 CharacterData가 있으면 현재 표시 경로를 재사용한다. 없는 유닛은 HUD에 한정된 공통 자원 준비 API를 사용한다. 독립 정보창·툴팁의 UI 등록·이력을 우회하지 않는다.
- [x] 한 Tick에 한 개체를 처리하는 준비 부품을 만든다. Unity 객체 생성은 메인 스레드에서 수행한다. 한 번의 Instantiate 자체를 프레임 중간에 중단할 수 있다고 가정하지 않는다.
- [x] 준비 중 모델·HUD가 정상 필드 대상이나 입력 대상이 되지 않게 한다. 공격 클립 재생·효과·오디오·Core 명령을 발생시키지 않는다.
- [x] 준비 상태는 하나의 작업 객체가 소유한다. 준비 보유 → 반환 완료 → 정상 풀 대여의 상태를 구분하고, 중복 반환·부분 생성 실패를 처리한다.
- [x] 생성·HUD 준비·클립 준비에 동기 구간별 ProfilerMarker를 둔다. 프레임 사이를 가로지르는 Begin/End 샘플은 사용하지 않는다.

검토: 정상 생성과 준비가 같은 경로를 쓰는지, N개가 실제 N개인지, 준비 객체가 EntityViewSet에 들어가지 않는지, 실패 후 남는 대여가 없는지 확인한다. 이 Phase의 부품은 운영 로딩에 아직 연결하지 않는다. 보고 후 멈춘다.

## P3 첫 활성화와 로딩 완료 대기

- [x] LoadingSystem에 씬별 준비 작업 등록 및 Begin/Tick/완료/취소 계약을 추가한다. 기존 LodingNode는 유지하고, 준비 작업이 없는 씬은 기존 경로를 따른다.
- [x] `SceneEnterLoaded → AfterLoad → 준비 작업 → BeginReveal` 순서를 연결한다. 기존 AfterLoad finally 실행과 카메라 연결을 바꾸지 않는다. 표현이 없는 로딩도 준비 완료를 기다린다.
- [x] 준비 객체는 매 진입마다 생성하고, LoadingSystem은 그 진행만 소유한다. Combat의 구현·유닛 수를 Global에 넣지 않는다. 상위 Builder로 서비스를 중복 재등록하지 않는다.
- [x] Combat Install 뒤 준비 Pending을 기존 진입 대기 조건에 연결한다. 입력·호버·배치·버튼·자동 진행이 준비 중 열리지 않게 하며 Shown의 기존 의미는 유지한다.
- [x] 로딩 화면이 완전히 덮인 동안 실제 Canvas의 유효한 위치에서 HUD 데이터를 적용·활성화한다. UnitHUDLayer가 준비 가시성·레이캐스트를 관리하도록 하여 표시 소유자를 중복시키지 않는다.
- [x] 데이터 적용 뒤 Canvas/TMP 갱신을 거친 다음 Tick에서 완료를 판정한다. 비활성 부모, 화면 밖, alpha 0만으로 준비 완료를 처리하지 않는다. 준비용 갱신은 필요 수명 동안만 구독하고 취소 시 해제한다.
- [x] 로딩 표현이 없는 개발 경로에는 시각 노출 없는 명시적 UI 갱신을 적용하고 운영 렌더 예열과 결과를 구분한다.
- [x] 준비 완료 시 표시·입력 차단·임시 데이터와 대여를 정리한 뒤 기존 풀로 반환한다. 그 다음 Reveal과 기존 보드·Nexus·적 연출을 허용한다.
- [x] Clear/Detach/Abort/Shutdown이 동일 준비 객체를 멱등적으로 취소하도록 연결한다. 실패를 Complete로 바꾸거나 오래된 완료로 새 연결을 열지 않는다.
- [x] 공용 로딩 계약과 Factory 연결 변경을 기존 Framework 문서 및 공유 메모에 기록한다. 외부 발송은 하지 않는다.

사용자 Unity 확인: 로딩 중 모델·HUD 노출 없음, 입력 불가, 로딩 애니메이션 진행, 준비 종료 후 기존 진입 연출 유지. 보드 연출 꺼짐·타일 없음·동일 씬 다시 진입·로딩 표현 없음·실패 시에도 상호 대기나 입력 조기 허용이 없어야 한다. Lobby/Stage 전환도 확인한다. 다른 작업자가 작성한 시험의 실행 기대 변경이 필요하면 먼저 확인한다. 보고 후 멈춘다.

## P4 배치 재사용과 성능 인수

- [x] 첫 Acquire가 준비한 모델·HUD·체력 텍스트·클립 채널을 사용하는지 연결을 검토한다. 대여 시 최신 Buffer 값과 위치를 적용하고 이전 유닛의 선택·미리보기·피해 표시를 남기지 않는다.
- [ ] 같은 종류를 선택 수량까지 연속 배치해 신규 생성이 없는지 확인한다. 기존 이동·손패 복귀·재배치에서도 대여·반환이 정상이어야 한다.
- [x] 실제 배치 결과 소비·준비 자원 생성·HUD 적용을 구분해 계측한다. 준비 대상 외 추가 생성은 정상 fallback으로 구분하고, 예상 수량의 준비 실패를 숨기지 않는다.
- [x] 정상 배치에 ForceUpdateCanvases나 전체 예열 호출이 남지 않게 한다. 변경 없는 상태의 반복 활성화 호출은 해당 소유자 안에서 줄이되 UIBase 전체의 수명은 바꾸지 않는다.
- [ ] 아래 기능·성능 표를 Unity에서 확인하고 실제 결과만 기록한다. 남는 큰 JIT·카메라 렌더링·VFX 비용을 이번 예열의 성공/실패와 분리한다.
- [ ] 결과에 따라 후속 병목을 기록한다. 전체 결과 갱신 제거, HUD 상시 활성화, Canvas 분리, Core JIT 대응은 이번 계획에 임의 추가하지 않는다.

보고에는 컴파일·재생의 실제 확인 주체와 범위, 변경 파일, 성능 전후, 남은 제한을 적는다. 미실행 컴파일은 **컴파일 미확인**으로 표기한다. 보고 후 멈춘다.

## 변경 위치와 책임

코드 기준 경로는 `Assets/ProjectL/Script/Systems/`다. 아래 목록은 허용 범위이며 실제 필요한 파일만 변경한다.

| 범위 | 예상 위치 |
|---|---|
| 대상 읽기와 준비 진행 | `RuntimeSystem/InGameSystem/ViewSystem/Combat/Display/Unit/`의 준비 부품과 .meta |
| 기존 자원 생성과 반환 | 같은 폴더의 `FieldUnitPresenter.cs`, `FieldUnitView.cs`, 필요 시 `UnitClipChannel.cs` |
| HUD 갱신과 준비 표시 | `UnitHUDLayer.cs`, `GlobalSystem/UISystem/Screens/Stage/UnitHUD.cs`와 직접 필요한 내부 위젯 |
| 씬 조립과 연결 수명 | `CombatSceneDisplay.cs`, `CombatViewConnection.cs`, `CombatViewSystem.cs`, `Factory/Runtime/InGame/View/`의 관련 Factory |
| 값 읽기 연결 | 기존 BufferReadSink 주입 위치와 진입 전용 읽기 부품. Buffer Store·Core 계산은 수정하지 않음 |
| 준비 완료 대기 | `RuntimeSystem/GlobalSystem/LoadingSystem/`의 계약·등록·로딩 상태 진행 및 .meta |
| 기록 | 이 설계·계획, 필요한 Framework 계약 문서·공유 메모 |

`EntityViewSet`의 필드 대여 의미, `CustomPool`의 공용 큐, `UIBase`의 전체 활성화 정책을 바꾸는 방식으로 해결하지 않는다. 씬·프리팹 변경이 필요한 경우에는 해당 Phase에서 정확한 변경과 필요성을 제시하며, 코드만으로 필요한 연결이 가능한지 먼저 확인한다.

## 성능 비교 절차

1. 기존 캡처는 설계 §2의 참고 자료로 보존한다. 비교용 기준은 가능한 한 같은 프로젝트 상태·유닛 선택·스테이지·Game 해상도·카메라·Profiler 모듈로 다시 확보한다. Deep Profile은 끄고 메모리 부족 상태를 피한다.
2. Editor와 Player 측정을 분리한다. 첫 실행 상태인지 이미 같은 코드를 실행한 상태인지, Domain Reload 설정과 재생 순서를 기록한다. 재생을 다시 눌렀다는 이유만으로 JIT 초기 상태라고 간주하지 않는다.
3. 첫 메인 배치, 종류별 첫 배치, 동일 종류 추가 배치, 기존 이동, 복귀 후 재배치를 비교한다. 입력 프레임과 다음 결과 반영 프레임을 함께 본다. 초기 실행은 가능하면 별도 초기화 세션 3회, 반복 상태는 같은 세션 3회 이상을 기록한다.
4. 준비한 자원의 첫 배치 신규 생성 횟수 0을 구조적 완료 기준으로 삼는다. 전체 CPU 시간, 관련 JIT, 생성·HUD·렌더 CPU 시간과 GC 할당량을 별도로 적는다. 평균만으로 단발 끊김을 가리지 않는다.
5. 로딩 추가 시간·로딩 중 최장 프레임·메모리 증가·대기 HUD의 상시 비용을 기록한다. 최대 합법 선택 수량과 여러 번의 씬 왕복에서 자원 수가 안정적인지 확인한다.
6. 최초 표시 비용이 로딩으로 이동하고 실제 배치 프레임이 감소했는지 판단한다. 60fps의 16.67ms는 비교 기준이며 이번 작업의 무조건적인 성능 보장으로 삼지 않는다. Player 빌드 확인은 사용자가 준비한 환경에서 별도로 수행한다.
