# 뛰어넘기 경유 칸의 드래그 단절 보완 — 설계·Task (2026-11-02)

- 상태: **1차 수정은 사용자 “안되는데요?”로 미해결 확인. Core 정규화의 거절 계약을 빠뜨린 조건을 보완했다. 보완 코드의 컴파일·재생 미확인.** 최신 결과는 §6이다.
- 사용자 현상: 뛰어넘기로 도달할 수 있는 칸은 이동 범위에 보이지만 그 칸까지 경로를 드래그할 수 없다.
- 범위: View 이동 경로 편집과 기존 Core 견적 소비. Core/Buffer/규칙/FieldCamera/Architecture 수정 없음.
- 사용자 승인 방향: 드래그 중 후보 경로는 보존하고 놓았을 때 전체 경로의 Core 승인을 받아야 이동한다. 기존 C3의 거절 즉시 자르기에서 `DestinationOccupied`의 편집은 보존하며, 놓은 뒤 불가이면 취소하는 M3는 유지한다. 1차 구현의 “마지막 한 칸인지 ValidStepCount로 판별”은 실제 Core 계약과 맞지 않아 제거했다.

## 1. 원인과 현재 계약

1. Core `CombatMovementCalculator.Range/Reach`는 중간 통과(`CanTraverse(..., landing: false)`)와 최종 착지(`CanLand`)를 구분한다. 뛰어넘기가 있는 유닛은 벽·절벽·유닛 칸을 중간에 지나갈 수 있지만 그 칸에서 멈출 수는 없다. 구조물 통과는 허용하지 않는다.
2. 드래그는 `MovementPointerSampler`가 지나간 칸을 `MovementDraft`에 직교 한 칸씩 추가한다. 뛰어넘기도 Core 경로에는 모든 중간 칸이 들어가므로 인접 조건을 풀거나 벽 칸을 생략하면 안 된다.
3. 커서가 중간 장애물 칸에 있는 동안 요청하는 경로는 그 칸을 **현재 끝점**으로 한다. Core는 그 경로를 `DestinationOccupied`로 거절한다. 다만 `MovementPathNormalizer.TryNormalize`가 상세 검사보다 먼저 통과/착지를 확인하므로 여기서 거절되면 `ProjectRoute`의 초기값 `validStepCount = 0` 그대로 반환한다. **거절된 끝점의 직전까지가 ValidStepCount라는 최초 설명은 잘못이었다.**
4. `CombatMovementInteraction.OnPreview`는 모든 거절에 `Draft.RetainPrefix(validSteps)`를 실행해 편집 초안을 자르고 `_lastPointer`를 비운다. `CanResumeAt`은 남은 경로의 인접 칸만 받으며, 이미 거절한 칸은 재진입에서도 제외한다. 따라서 장애물을 너머로 이어 갈 초안이 사라진다.
5. 예: A(시작) → B(벽) → C(빈 칸). A→B는 최종 착지가 불가하므로 거절된다. 현재 View는 A로 잘라서 C를 연결하지 못한다. A→B→C 전체는 뛰어넘기 유닛의 Core 견적이 승인할 수 있다. 빠른 커서 이동으로 전체 경로를 한 번에 보내면 통과할 수도 있어 입력 속도/응답 도착 시점에 의존하는 문제다.

이는 범위 계산의 추가 이동거리 누락이나 비인접 점프 입력의 문제가 아니다. 원인은 코드 대조로 확인했으며 이번 조사에서 Unity 실행 재현은 하지 않았다.

## 2. 수정 설계

### LP1 — 편집 후보와 실행 승인을 구분한다

드래그 중이며 Core 거절 이유가 `DestinationOccupied`이면 원본 편집 초안을 유지한다. 정규화 거절의 `ValidStepCount = 0`으로는 끝점과 이전 중간 칸 중 어디가 막혔는지 구분할 수 없으므로 View에서 거절 위치·통과 가능성을 추측하지 않는다. 뛰어넘기 특성/지형/점유 판정을 View에 추가하지 않는다.

- `MovementDraft`는 A→B를 편집 후보로 유지하고, 다음 포인터 이동은 B에서 이어 A→B→C로 기존 Core 견적을 요청한다. 연속 장애물 칸도 끝점이 옮겨질 때마다 같은 방식으로 전체 경로를 묻는다.
- 화면의 `RetainedPath`는 **이전에 성공한 경로와 현재 후보의 공통 접두**만 유지하고, B의 끝점/고스트는 기존 불가 색을 사용한다. 거절 응답의 0을 새로운 유효 접두 정보로 쓰거나 미승인 칸을 유효 착지로 보이지 않는다. 기존 `RequestPreview → TrimRetainedPath`가 공통 부분을 유지한다.
- 드래그 시작·샘플러·인접 규칙·커서 스냅·이동 범위는 바꾸지 않는다.
- 다른 사유의 거절(거리 초과, 잘못된 경로 등) 및 놓은 뒤의 모든 거절은 기존 자르기·재진입/취소 경로를 유지한다.
- 뛰어넘기가 없는 유닛이나 구조물이 막는 경로도 `DestinationOccupied`이면 드래그 중 초안만 남는다. 그 초안은 계속 불가 표시되며, 되짚어 장애물을 제외하거나 취소할 수 있다. 전체 경로 성공 응답 없이 이동하지 않는다. 1차 구현과 달리 “이전 중간 칸이 막혔으면 즉시 자르기”를 보장할 수 없으며, 이를 보장하려고 View에서 규칙을 복제하거나 Core를 수정하지 않는다.

### LP2 — 제출·요청 수명은 기존 계약을 유지한다

- 버튼을 놓은 뒤(`_frozen`)의 거절은 항상 기존 M3 처리로 취소하며, 편집 보존 분기로 들어가지 않는다. `MovementPreviewContext`가 있는 최신 성공 응답만 기존 `SubmitFrozen`으로 제출한다.
- 편집용 거절에는 실행 context를 보관하지 않는다. 같은 후보/같은 거절 응답을 포인터 이동마다 반복 게시·소비하지 않도록 기존 요청 번호·Revision·슬롯 소유권을 재사용한다. 새로운 Tick 검사/타이머/전역 상태를 추가하지 않는다.
- 이전 응답은 기존 전투/수명/요청/Revision/경로 대조를 통과한 때만 소비한다. 커서가 먼저 C에 도달했으면 늦은 A→B 거절이 현재 초안을 잘라서는 안 된다.
- 취소·UI/필드 밖 이탈·원점/이전 경로 재진입·다른 입력의 슬롯 선점은 기존 정리/재요청 계약을 따른다. 미승인 꼬리를 다른 경로로 복제 보관하지 않는다.

## 5. LP1 1차 구현 기록 — 조건 오류로 §6에서 보완 (2026-11-02)

아래는 최초 구현 당시 기록이다. `MovementPathNormalizer`의 조기 거절을 빠뜨려 ValidStepCount가 0으로 오는 경우를 반영하지 못했다. 당시 정적 흐름 대조는 그 잘못된 가정에 기반했으며, 실제 동작 통과의 근거가 아니다. 현재 계약과 코드는 §2·§6을 따른다.

사용자 “그 방향으로 가자”에 따라 위 LP1을 구현했다. 변경은 실행 코드 1개(`CombatMovementInteraction.cs`), 기존 입력 안내, 이 설계·Task 문서다. Core/Buffer/규칙/Factory/MovementDraft/샘플러/표시 구현·에셋·기존 시험은 변경하지 않았다.

- `OnPreview`의 기존 요청/수명/Revision/슬롯 대조를 통과한 거절 중, 드래그 중의 `DestinationOccupied`이며 `ValidStepCount == StepCount - 1`인 응답만 편집 후보를 보존한다. `RetainedPath`에는 해당 응답이 확인한 접두만 복사하고, 실행 context는 null로 두며 끝점은 기존 불가 표시를 사용한다.
- 같은 거절 응답 객체는 다시 소비하지 않는다. 기존 요청 번호·Revision·슬롯을 유지하므로 같은 칸의 포인터 이동은 `RequestPreview`의 기존 중복 차단으로 게시하지 않는다. 다음 칸/되짚기로 Draft Revision이 바뀌면 기존 입구로 전체 초안의 새 견적을 게시한다.
- `_frozen`이면 이 분기로 들어가지 않는다. 놓은 끝점이 이미 거절된 경우 기존 `OwnerAdapter.Poll`이 최신 응답을 다시 넘기면 기존 확정 거절로 빠지고, `CombatPathInput.OnPreview`가 `_released`와 대기 해제를 보고 지정을 취소한다. 성공 context가 없는 후보를 `SubmitFrozen`으로 보내지 않는다.
- 성공 응답을 받으면 이전 거절 칸 표지를 비워 이후 잘못된 거절 안내가 남지 않게 했다. 일반 성공의 context·전체 경로/걸음 수 대조와 제출은 그대로다.

정적 흐름 대조(실행 시험 아님):

| 경계 | 대조한 동작 |
|---|---|
| A→벽 B 거절 후 C로 진행 | 초안 A→B 유지, 불가 B 표시, 다음 이동은 A→B→C 전체를 Core에 요청 |
| 여러 장애물 경유 | 각 응답이 마지막 칸만 거절하면 초안을 유지. 이전 중간 칸도 거절하면 기존 접두 자르기 |
| 같은 포인터/응답 반복 | 같은 요청/Revision은 재게시하지 않고 같은 응답은 접두 목록을 다시 만들지 않음 |
| B에서 놓기 | frozen에서는 보존 분기 없음. 기존 거절·확정 해제·지정 취소, 이동 제출 없음 |
| 더 먼 경로 뒤 늦은 B 응답 | 요청 번호/Revision 일치 검사에서 제외 |
| 이전 경로로 되짚기 | 기존 Draft.Accept가 자르고 Revision 변경, 표시 공통 접두 및 새 전체 경로 견적 사용 |
| UI/필드 밖·포커스 상실 | 기존 Suspend/재진입·Cancel 수명 사용. 보존 초안이 있어도 포인터 무효·UI 위에서는 제출 안 함 |
| 일반 이동·PositionSwap | Core 성공 응답은 기존 흐름, 중간 장애물/다른 실패와 거절 확정은 기존 분기 |

SSOT/SOLID/FW 대조: 특성·지형 계산 없이 공개 Core 응답만 사용한다. 편집 후보·표시 접두·실행 context는 기존 소유자를 유지하고, 새 상태 필드·서비스·별도 실행기·Tick/코루틴·공용 API 변경은 없다. 기능 보완은 응답 소비자 한 파일에 한정했다. LF/UTF-8(BOM 없음)/대체 문자·후행 공백·diff 검사와 직접 소비자 계약을 정적으로 대조했다.

**컴파일 미확인.** 새 View 시험 작성·기존 시험 수정/실행·MSBuild·Unity 재생은 하지 않았다. LP1 리뷰 지점에서 멈추며 LP2 실제 입력 확인은 위 체크리스트가 남았다. 스테이징·커밋·push 없음.

## 6. 사용자 미해결 보고 후 보완 — 2026-11-02

사용자 “안되는데요?”를 받아 Core의 **Preview → ProjectRoute → MovementPathNormalizer → MovementRouteValidator** 전체 순서를 다시 대조했다. 1차 수정은 상세 검사에서 유효 접두가 반환된다고 가정했지만, 정규화 자체가 `CanTraverse`를 호출해 같은 장애물 착지를 먼저 거절한다. ProjectRoute는 이때 validStepCount 초기값 0으로 끝나므로 경로에 이미 일반 걸음이 있거나 연속 장애물을 넘는 경우 1차 보존 조건에 들어가지 않았다. 이는 오래된 DLL이라고 추정할 사안이 아니다. 조사 시 DLL 시각(UTC 04:52:28)은 1차 소스 시각(04:48:54)보다 뒤였고, 이 시각 정보는 이번 보완 컴파일 확인으로 쓰지 않는다.

승인받은 “편집 후보 유지·놓았을 때 전체 Core 승인” 방향에 맞게 View 한 파일을 보완했다.

- 드래그 중 `DestinationOccupied`의 보존 조건에서 ValidStepCount 비교를 제거했다. 거절 위치를 추측하지 않고 전체 Draft와 포인터 샘플링을 남긴다.
- 거절 응답으로 접두를 새로 만드는 코드도 제거했다. 강조는 기존 성공 경로와 현재 초안의 공통 접두만 사용하며, 추가 칸은 다음 전체 성공 응답 전까지 유효 표시하지 않는다.
- 같은 응답 1회 소비·동일 Revision 재게시 차단·context null·frozen 뒤 기존 거절 취소·새 성공에서 이전 거절 표지 제거는 유지했다. Core/Buffer/특성·지형 판정/샘플러/이동 실행은 수정하지 않았다.

재대조한 실제 계약(정적 확인): `A→빈 칸 B→벽 C`는 정규화 거절/ValidStepCount 0이어도 초안을 유지한다. 다음 빈 칸 D에서 `A→B→C→D`를 다시 견적내며, 중간 통과가 가능한 뛰어넘기 유닛의 성공 응답만 기존 전체 경로/context 검사 뒤 사용할 수 있다. 연속 장애물 C/D에서 계속 0 거절이 와도 초안은 유지된다. 뛰어넘기 미보유/구조물 통과는 계속 거절·불가 표시되고, 버튼을 놓으면 frozen 분기가 기존 취소로 끝낸다. 어떤 거절도 실행 승인으로 전환하지 않는다.
