# 로컬 LLM 실행 검증과 공통 비교 입력 초안

작성일: 2026-10-22

7주차 차주 계획 3번(M3)의 기록이다. §1은 기존 S01~S06 상황의 실제 응답·형식 오류·지연이고, §2는 룰 정책과 LLM이 **같은 후보**를 판단하도록 만드는 입력 초안이다. §2는 같은 날 `tools/llm_projection.py`·`tools/run_llm_compare.py`로 구현했고, 첫 비교 결과는 §3에 있다.

### 1.1 형식

6건 모두 형식 검증을 통과했다(오류 0, `done_reason` 모두 `stop`). 고른 후보가 6건 모두 자기 점수의 최고점이었다. 스키마 강제가 있는 조건에서 4B 모델의 형식 오류는 관찰되지 않았다. 스키마 없이 보내는 경우는 시험하지 않았다.

### 1.2 지연

| 항목 | 1차(`localhost`) | 2차(`127.0.0.1`) |
|---|---:|---:|
| 클라이언트 측정 중앙값 | 3,057ms | 919ms |
| 클라이언트 측정 최대 | 3,169ms | 989ms |
| Ollama 내부 합계 | 0.77~1.15초 | 같은 수준 |
| 입력 처리 | 0.10~0.38초 (입력 417~487 토큰) | |
| 출력 생성 | 0.54~0.76초 (출력 42~54 토큰, 61~78 토큰/초) | |

- 1차의 약 2초 차이는 모델이 아니라 이름 해석이었다. `/api/version` 호출이 `localhost`로 약 2,050ms, `127.0.0.1`로 1~15ms 걸렸다. Windows에서 `localhost`가 IPv6를 먼저 시도하는 것으로 보인다. 실행기는 `127.0.0.1`을 쓰도록 고쳤다. **Unity 연결에서도 같은 문제가 생길 수 있으므로 주소를 IPv4로 지정한다.**
- 모델이 메모리에 없을 때의 첫 요청은 별도 확인 실행에서 로딩 23.5초 + 입력 처리 30.5초였다. 일괄 실행의 warmup이 이 비용을 통계에서 빼지만, 실제 게임에서는 전투 진입 전에 모델을 미리 올려야 한다.
- 출력 토큰 대부분이 `reason` 문장이다. 이유 문장을 빼거나 줄이면 출력 시간이 줄어든다.

### 1.3 반복 일관성

1차·2차 실행의 선택·점수·이유 문장이 6건 모두 완전히 같았다. S02는 그 전 확인 실행까지 3회 같았다. temperature 0과 고정 seed 조건에서 재현된다.

### 1.4 선택 읽기

| 상황 | LLM 선택 | `ruleChoice` | 읽은 점 |
|---|---|---|---|
| S01 | 1 메인 1 피해 | 1 | HP 1 Akimbo 처치(0)보다 메인 1 피해를 골랐다. 이유는 "위협을 줄인다"(위협 수 2→1) |
| S02 | 0 메인 처치(**즉시 승리**) | 1 ShotGun 처치 | 기획 의도(R01: 즉시 승리 우선)와 맞는 선택. 단 이유는 승리를 말하지 않는다 |
| S03 | 2 Sniper·메인 관통(Sniper 처치) | 0 Akimbo·ShotGun 17 피해 | 피해 합계보다 메인 포함 사선을 선호 |
| S04 | 1 멀어지는 이동(위협 0, 거리 4) | 0 추적 | Demon이 추적을 포기하고 물러남 |
| S05 | 2 멀어지는 이동(위협 0) | 0 HP 1 Sniper 처치 | 빈사 Demon이 처치 대신 도망. R23의 기획 의도(교환)와 반대 |
| S06 | 1 이동 후 메인 공격 | 1 | Sniper 처치(0)보다 메인 10 피해 |

- 6건 중 3건(S01·S04·S05)에서 **위협 수가 낮은 후보를 강하게 선호**한다. S06에서는 위협 0인 이동·대기를 0점으로 매겨 이 경향이 보이지 않았다. 지시문의 "살아남으면서"와 필드 설명 "낮을수록 안전"을 그대로 따른 것으로 보인다. S 형식에는 위협이 실제 몇 피해인지 없어서, 위협 1과 위협 3의 차이를 과장해서 읽을 수 있다. §2 공통 입력이 위협 수 대신 예상 피해를 주려는 이유다.
- 이유 문장은 짧고 일반적이며, "거리 최소화"와 "거리 유지"처럼 후보와 맞지 않는 표현이 섞인다. 판단 근거의 시각화에는 이유 문장보다 점수를 쓰는 것이 낫다.
- `ruleChoice` 일치는 2/6이지만, `ruleChoice`는 현행 Core 룰을 가정한 값이라 성능 점수로 쓰지 않는다(설계 §8). 6건은 경향을 말하기에 적은 표본이다.

## 2 공통 비교 입력 초안

### 2.1 지금 두 입력이 다른 점

| 항목 | LLM용 `fixtures/S*.json` | 룰용 `rule_fixtures/R*.json` |
|---|---|---|
| 후보 ID | 배열 번호 0~3 | 문자열(`a_main_hit`), 배열 순서와 무관 |
| 피해 | 대상 이름을 쉼표로 이은 `expectedDamage` 합계, `killsTarget`은 하나라도 처치 | 모든 캐릭터·본진의 시작·종료 HP |
| 위험 | `threatAfter`: 위협하는 유닛 수 | 다음 내 턴 전 상대별 AP·비용·피해 일정 |
| 위치 | `distToTargetAfter`: 추적 대상까지 거리 | 메인 공격 위치까지 이동 AP(전·후), 넉백 전·후 비용 |
| 정답 비교 | `ruleChoice`: 현행 Core 룰을 **가정**한 선택 | `expected`: 기획 의도, 평가기가 두 정책 선택을 계산 |

S 형식은 설계 §3에서 이미 "새 공식을 적용할 정보가 부족하다"고 판단했다. 같은 후보를 비교하려면 반대 방향, 즉 **R 형식을 원본으로 두고 LLM이 읽을 화면을 코드로 뽑는 것**이 맞다. 한 사실은 R 파일 한 곳에만 둔다(SSOT).

### 2.2 구조

```text
rule_fixtures/R*.json  ──►  rule_policy.evaluate_case  ──► 승리·역할 선택, 항목별 점수
   (원본, 하나)        └─►  LLM 투영(새 코드)  ──► LLM 요청 ──► 선택 ID, 점수, 이유
                                                         │
                         같은 후보 ID로 비교 ◄────────────┘
```

- 실제 연결에서는 원본이 R 파일 대신 Core의 `EnemyDecisionRequest`(입력 대응 문서 §4)가 된다. 투영 코드는 그대로 쓴다.
- 미평가 상황(R12·R15)은 룰과 같이 LLM에도 보내지 않는다. 두 정책이 같은 상황 집합을 판단해야 비교가 공정하다.

### 2.3 LLM에 보낼 것과 보내지 않을 것

원칙은 설계 가이드의 "계산은 코드가, 판단은 LLM이"다. 산술로 확정되는 사실은 코드가 미리 계산해 넣고, 가중치나 정책 점수처럼 **판단 자체**는 넣지 않는다.

| 넣는 것(사실) | 출처 | 비고 |
|---|---|---|
| 후보 ID | R 후보 `id` → 중립 별칭 `c1, c2…` | **구현 중 변경.** 원래 ID 자체가 `b_pointless_self_death`, `b_safe_move`처럼 평가 단어를 담아 답을 흘린다. 화면 순서대로 별칭을 붙이고, 응답의 별칭을 원래 ID로 되돌려 비교한다 |
| 행동 요약 | `actions` | `"move 1 → attack"`처럼 코드가 만든 중립 문구 |
| 종료 결과 | HP 변화 | 평가기와 같은 규칙: 메인 0이면 적 승리, 본진 0이면 적 패배 |
| 대상별 피해 | `players`·`playerHpAfter` | `{id, role, hpBefore, hpAfter, killed}` 목록. 합계로 뭉치지 않는다 |
| 아군·본진 손실 | `allies`·`allyHpAfter`, `headquarters` | 손실이 있을 때만 |
| 자기 HP | `selfHpAfter` | 이번 행동으로 사망하면 `diesNow: true` |
| 다음 내 턴 전 예상 피해 | `responseWindow` → 평가기의 일정 산술 | 적용 피해와 `diesBeforeNextTurn`. **할인하지 않은 원값** |
| 메인 접근 비용 | `approachCostBefore/After` | 원값. null은 "도달 불가" |
| 역할 사실 | `roleFacts` | 다음 턴 위협 가능, 가장 가까운 플레이어 거리, 넉백 전·후 비용 |

| 넣지 않는 것 | 이유 |
|---|---|
| `label` | "안전한", "무익하게" 같은 평가 단어가 들어 있어 답을 흘린다 |
| `expected`, `assumptions` | 기대 정답과 작성 메모 |
| 가중치·W·Role·Q·위험 할인 | 룰 정책의 판단이다. LLM이 따로 판단해야 비교가 된다 |
| `legal=false` 후보, AP 부족 후보 | 룰 평가기가 제외한 후보는 LLM에도 보내지 않는다. 합법성은 코드가 판단한다 |

### 2.4 정책별 지시문

룰에 두 정책이 있으므로 LLM도 지시문 두 개로 같은 상황을 두 번 판단한다. 지시문에는 숫자 가중치를 넣지 않고 목표만 말로 적는다.

- **승리 지향**: "적 진영이 이기도록 하라. 즉시 승리가 있으면 먼저 하고, 플레이어 유닛 제거와 메인 압박을 자기 유닛 손실과 비교하라."
- **역할 지향**: 승리 지향 지시 + 유닛별 역할(설계 §7.1)을 말로 설명. 예: Gravekeeper는 "넉백으로 플레이어를 본진에서 밀어내는 교란", Ballista는 "여러 대상을 한 사선으로 관통하고 거리를 유지하는 포격". "전술적으로 크게 손해 보는 역할 행동은 하지 마라"를 함께 적는다.

지시문 파일은 `prompts/`에 정책별로 두고, 실행 기록에 해시를 남긴다(현재 `run.json`과 같은 방식).

### 2.5 응답 형식

```json
{"scores": [0, 0, 0], "choice": "a_main_hit", "reason": "한국어 한 문장"}
```

- `scores`는 화면에 나온 후보 순서대로 0~10 정수. 히트맵 시각화와 "고른 후보가 최고점인가" 확인용이다.
- `choice`는 후보 ID 문자열이다. Ollama `format` 스키마의 `enum`에 그 상황의 ID 목록을 넣어 강제하고, 코드에서 다시 검증한다(현재 `validate`와 같은 원칙).

### 2.6 투영 예시: R20의 관통 후보

R20 `a_lane_shot`을 위 규칙으로 투영하면 다음과 같다(손으로 계산한 초안 예시).

```json
{
  "id": "a_lane_shot",
  "action": "attack",
  "outcome": "ongoing",
  "hits": [
    {"id": "main", "role": "main", "hpBefore": 50, "hpAfter": 40, "killed": false},
    {"id": "regular_b", "role": "regular", "hpBefore": 10, "hpAfter": 3, "killed": false}
  ],
  "self": {"hpBefore": 10, "hpAfter": 10, "maxHp": 10, "diesNow": false},
  "beforeMyNextTurn": {"expectedDamage": 2, "hpAfter": 8, "dies": false},
  "approachCost": {"before": 0, "after": 0},
  "role": {"canThreatenNext": true, "nearestPlayerDistance": 4, "knockback": []}
}
```

같은 후보를 R19(Focus 3스택)로 투영하면 `beforeMyNextTurn`이 `{"expectedDamage": 10, "hpAfter": 0, "dies": true}`로 바뀐다(가장 가까운 플레이어 거리도 3이다). 룰 정책은 이 차이를 할인 0.5로 반영해 둘 다 관통을 골랐다. LLM이 R19에서 후퇴를 고르는지가 비교 지점이 된다.

### 2.7 비교 지표

| 지표 | 의미 |
|---|---|
| 기대 일치 | LLM 선택이 R의 `expected`(기획 의도)에 드는 비율. 룰과 같은 기준 |
| 룰 일치 | LLM 승리 지향 선택 = 룰 승리 선택, LLM 역할 지향 선택 = 룰 역할 선택 |
| 형식 오류율 | §1과 같은 분류 |
| 지연 | 전체·입력·출력 시간. 후보 수와 입력 토큰 수에 따른 변화 |
| 순서 불변 | 후보 순서를 섞어도 같은 ID를 고르는가. 룰 평가기는 순서 불변이다 |
| 반복 일관성 | temperature 0, 같은 seed로 반복했을 때 같은 답인가 |

`ruleChoice` 일치율은 새 정책의 성능 점수로 쓰지 않는다(설계 §8). 기존 S 상황은 형식·지연 기준선으로만 남긴다.

### 2.8 구현

- `tools/llm_projection.py`의 `project(case, settings)`가 `rule_policy.evaluate_case`를 한 번 호출해 합법성·종료 결과·반격 일정 산술을 그대로 쓰고, LLM 화면과 별칭 표를 만든다. 같은 산술을 두 번 구현하지 않는다.
- `tools/run_llm_compare.py`가 R 상황마다 승리·역할 지시문(`prompts/compare.victory.txt`, `compare.role.txt`)으로 요청하고, 룰 선택·기대와 비교한다. 요청·응답·형식 검증·시간 통계는 `run_ollama_test.py`의 함수(`schema`, `validate`, `send`, `timing`)를 공유한다.
- 응답 실패는 오프라인 비교에서 오류로 기록만 한다. 실제 연결의 룰 복귀는 입력 대응 문서 §5를 따른다.
- `tests/test_llm_projection.py` 7건: label·기대 이유·원래 ID 비노출, 제외 후보 미전송, 반격 피해가 룰 일정과 같음, 사망·종료 후 일정 없음, 대상별 피해, 미평가 상황 거절, 문자열 ID 검증. 전체 25건 통과.
- 순서 섞기·반복 실행 옵션은 아직 없다(§3.5).

## 3 R 상황 첫 비교

결과: [20261022T082833.618685Z](../results/llm_compare/20261022T082833.618685Z/run.json). 모델·옵션은 §1과 같다. 룰 설정은 `rule-v2.1-2026-10-22`(역할 허용 차이 6)이다. R12·R15는 룰 미평가라 보내지 않았다. 22개 상황 × 지시문 2개 = 요청 44건이다.

### 3.1 요약

| 항목 | 룰 정책 | LLM 승리 지시문 | LLM 역할 지시문 |
|---|---:|---:|---:|
| 형식 검증 통과 | — | 22/22 | 22/22 |
| 기대 일치(R11 제외 21개) | 19 | 11 | 12 |
| 룰 선택과 일치(R11 제외) | — | 13 | 14 |
| 고른 후보가 자기 최고점 | — | 22/22 | 22/22 |
| 지연 중앙값 / 최대 | — | 1,169ms / 9,636ms | 1,221ms / 1,452ms |

R11은 합법 후보가 대기 하나뿐이라 판단 비교에서 뺐다. 룰이 틀린 R19·R23에서 LLM도 같은 선택을 했다. **LLM이 룰보다 기대에 가까운 상황은 없었다.**

### 3.2 상황별 선택

| 상황 | 기대(승리/역할) | LLM 승리 | LLM 역할 | 읽은 점 |
|---|---|---|---|---|
