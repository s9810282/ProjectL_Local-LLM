### 1.2 사용자와 일하는 방식

- **커밋·push는 사용자가 직접 한다.** Claude는 커밋하지 않는다.
- 사용자는 과정을 이해하고 직접 발표해야 한다. 단계마다 무엇을·왜 했는지 설명하고, 실행은 사용자가 직접 해 보도록 명령을 준다. 결과는 함께 읽는다.
- 큰 작업은 계획 → 단계별 구현 → 단계마다 멈추고 보고. 계획과 다른 결정이 필요하면 먼저 묻는다.
- 기대 선택은 **계산 전에** 적고, 결과를 본 뒤 고치지 않는다.
- 저장소 루트의 `CLAUDE.md`는 ProjectL View 작업용 지침이다. Core·View 파일을 건드리지 않는다는 원칙은 이 연구에도 그대로 적용한다.

## 2 다른 PC에서 환경 준비

| 항목 | 기준 | 비고 |
|---|---|---|
| OS·셸 | Windows, PowerShell | 명령은 프로젝트 루트(`...\Local LLM`)에서 실행 |
| Python | 3.10 이상(작업 PC 3.13.3) | **추가 패키지 없음.** 표준 라이브러리만 쓴다 |
| Ollama | 작업 PC 0.40.6, 두 번째 PC(RTX 4070) 0.40.12 | `http://127.0.0.1:11434` |
| 모델 | `hf.co/unsloth/Qwen3.5-4B-GGUF:Q4_K_M` (4.21B, Q4_K_M) | 처음 한 번 받는다 |

```powershell
ollama pull hf.co/unsloth/Qwen3.5-4B-GGUF:Q4_K_M
```

- **주소는 `127.0.0.1`을 쓴다.** Windows에서 `localhost`로 접속하면 IPv6를 먼저 시도해 요청마다 약 2초가 늘어난다. 도구는 이미 `127.0.0.1`을 쓴다(`tools/run_ollama_test.py`의 `SERVER`). 예외로 학습용 `tools/ask_once.py`는 아직 `localhost`를 쓴다(시간 통계는 Ollama 내부 값이라 영향 없음).
- 모델이 메모리에 없을 때 첫 요청은 약 54초(로딩 23.5초 + 입력 처리 30.5초)다. 실험·시연 전에 한 번 요청해 둔다.

```powershell
python LLMTest/tools/run_ollama_test.py S01
```

- 실험 조건: `temperature 0 · seed 42 · num_predict 200`, `think false`, Ollama `format` 스키마로 응답 형식 강제. 바꾸면 결과를 이전과 비교할 수 없으므로 기록한다(`OPTIONS`가 `run.json`에 남는다).
- **줄바꿈:** Git 전역 설정이 `core.autocrlf=true`인 PC는 체크아웃할 때 파일을 CRLF로 바꾼다. 그러면 지시문이 `\r\n`째 모델에 들어가고 §4.3 해시도 달라진다. `LLMTest/.gitattributes`가 LF로 고정한다. 새 PC에서는 지시문 해시가 §4.3과 같은지 먼저 확인한다(§10).
- **PC가 바뀌면 LLM 답도 일부 바뀐다.** 모델 파일과 요청이 같아도 Ollama 버전이나 GPU가 다르면 판단 약 5%가 달라졌다. 새 PC에서는 기준선 8회(R·V × 기본판·가이드판 × 파일·뒤집기)를 먼저 다시 잰다. 근거는 LLM 문서 §7.
- 터미널 패널 탭으로 긴 명령을 보낼 때 탭 시작이 늦어 명령이 중간에 끊긴 적이 있다. 끊기면 다시 실행한다.

## 4 지켜야 할 설계 규칙

### 4.1 공통 비교의 원칙

- **원본은 R 상황 파일 하나다.** 룰은 그대로 평가하고, LLM 입력은 `llm_projection.py`가 같은 파일에서 뽑는다. 실제 연결 때는 원본이 Core의 결정 요청으로 바뀌고 투영 코드는 그대로 쓴다.
- **계산은 코드, 판단은 LLM.** 합법성·종료 결과·반격 피해 산술은 룰 평가기 결과를 쓴다. LLM에는 할인하지 않은 원값만 준다.
- **답을 흘리지 않는다.** `label`, `expected`, `assumptions`, 가중치·점수는 보내지 않는다. 후보 ID에도 평가 단어가 있어 `c1, c2…` 별칭으로 바꾸고 결과에서 되돌린다.
- **같은 상황 집합만 비교한다.** 룰이 미평가로 둔 R12·R15는 LLM에도 보내지 않는다. 룰이 제외한 후보(불법·AP 부족)도 보내지 않는다.
- 이 원칙은 `tests/test_llm_projection.py`가 검사한다.

### 4.2 측정 규칙

- **LLM 비교는 최소 파일 순서와 뒤집기 두 가지로 돌린다.** 같은 입력이면 답이 재현되지만, 후보 순서만 바꿔도 판단 약 4분의 1이 바뀐다. 두 순서에서 같은 선택만 LLM의 판단으로 집계한다.
- **"고른 후보가 자기 최고점인가"(`choice_is_max`)를 함께 본다.** 가이드판에서 점수와 선택이 어긋난 응답이 나왔다.
- **같은 PC·같은 Ollama 버전에서 잰 실행끼리만 비교한다.** 다른 PC의 수치와 섞지 않는다(LLM 문서 §7.5).
- R11은 합법 후보가 하나뿐이라 판단 비교에서 뺀다. 집계 기준은 R 세트 21상황 × 2지시문 = 42판단, V 세트 8 × 2 = 16판단.
- `ruleChoice`(S 상황)나 룰 선택과의 일치율을 LLM 성능 점수로 쓰지 않는다. 기준은 `expected`(기획 의도)다.

### 4.4 보류 검증 세트

- `validation_fixtures/V01~V08`은 가이드판 고정 뒤 만들었고 룰 가중치·지시문 조정에 쓰지 않았다.
- **V 세트의 결과를 이미 보았다.** 앞으로 V 결과를 보고 지시문을 고치면 V는 더 이상 보류 세트가 아니다. 지시문을 개선할 때마다 새 보류 세트(V09 이후 또는 새 폴더)를 개선 **전에** 만들어 둔다.
- 기대 판단과 가이드판을 같은 작성자(Claude)가 같은 기획 의도로 썼다. 독립 검증은 아니다. 사용자나 다른 사람이 기대를 정한 세트가 있으면 더 강한 근거가 된다.

### 4.5 기타

- 실행 결과 폴더는 덮어쓰지 않는다. `expected`는 결과에 맞춰 고치지 않는다.
- 새 상황을 만들 때는 기존 R 파일을 복사해 실제 DB 값(입력 대응 문서 §3.1)을 쓰고, `assumptions`에 가정과 "확인 필요"를 적는다. 상황 생성에 쓴 임시 스크립트는 저장소에 없다. JSON 파일 자체가 원본이다.

사용자는 **LLM 성능을 룰 수준으로 끌어올리는 방향**으로 진행하기로 했다(10-22). 7주차 문의 사항도 이 방향으로 바뀐다. 차주 계획 ①은 룰 개선이므로 LLM 개선 실험으로 바꿀지 사용자에게 확인한다.

LLM 개선 후보와 공정하게 재는 방법:

| 후보 | 기대 효과 | 측정 |
|---|---|---|
| 여러 순서 질의·다수결 | 위치가 선택을 정하는 판단 제거 | 순서 2~3개로 묻고 다수 또는 만장일치만 채택. 채택률과 채택된 판단의 기대 일치를 함께 본다 |
| 판단 예시(few-shot)를 포함한 지시문 | R08·R09·V03 같은 남은 경향 교정 | 예시는 평가 세트 밖 상황으로 만든다. 평가 세트 상황을 예시로 쓰지 않는다 |
| 우선순위 순서 조정 | R09(아군 손실이 처치보다 뒤) | 새 지시문 파일 + 새 보류 세트 |
| 이유 문장 제거 또는 짧게 | 출력 시간 감소, 점수·선택 일관성 | 선택이 바뀌는지 같은 순서 조건으로 비교 |
| 더 큰 모델 | 판단 품질 | 같은 지시문·두 순서·같은 세트. 지연과 메모리를 함께 기록 |
| 채택 조건(두 순서 일치 + 최고점 확인 + 룰 복귀) | 실제 적용 안전성 | 채택률, 채택 판단의 기대 일치, 룰 복귀 비율 |

모든 개선 실험에서 지킬 것: 새 지시문은 새 파일, 시작 전에 새 보류 상황과 기대 판단을 먼저 만든다, 두 순서 이상으로 잰다, `choice_is_max`를 확인한다, 같은 PC의 기준선과 비교한다.

그 밖의 후속 과제:

- 룰 쪽: 유닛별 전력 가치·확실성별 위험 할인 프로필(R19·R23·V08), R07 재작성.
- Unity 연동(M3): Core 요청 Q1~Q5의 전달 여부 결정, Unity에서 Ollama 요청(IPv4) 확인, 의사결정 시각화(M2의 남은 부분, 점수 히트맵 기반).
- 독립 기대 판단: 사용자나 다른 사람이 기대를 정한 상황 세트.
