# 계획 AI 예상 피해 기억해 두기 설계 (초안, 2026-11-18)

> **상태: 결정 완료(2026-11-18 사용자 "권장안대로, DM-0" = Q-DM1~Q-DM4 모두 권장안). DM-0 측정 완료(§11) — 결과로 DM3 대신 DM5(§11.3)를 제안, Q-DM5 결정 대기. 계획 AI 코드 변경 없음.**
> 사용자 요청 "응, 설계해 줘"(2026-11-18). 앞 측정: [병렬 설계](2026-11-18-planner-background-parallel-design.md) §16(우리 코드 몫)·§17(예상 피해 되풀이).
> 범위: 연구 저장소(Local LLM)의 계획 AI(`Assets/ResearchEnemyPlanner/`)만. 팀 저장소·develop에는 올리지 않는다. 사용자 지시(2026-11-18 "Enemy AI 관련으로는 우리가 수정해도 문제 없어")의 범위 안이다. 게임 규칙 함수(Core 피해 식)는 바꾸지 않는다.

## 1 지금 문제

- 계획 한 번의 시간 약 22%, 할당 약 31%가 예상 피해(`PlannerEvaluator.Estimate` → Core `CombatDamageCalculator.Attack`)다(§16.2, Release·l0).
- 계획 한 번에 5만~50만 번 부르는데, 판이 달라도 같은 공격자·대상 사실 객체로 묻는 것이 약 64%, 값까지 같은 것이 약 88%다(§17.2). 같은 판 안에서는 되풀이가 없다.
- 벤치마크 판에서 같은 질문의 답이 달랐던 적은 없다. 그러나 Core 피해 식은 두 유닛 사실 말고도 판을 읽기 때문에(§3), 두 유닛만 보고 기억하면 그 입력이 다른 판에서 틀린 답을 쓸 수 있다.

## 2 목표와 범위

- **목표:** 같은 답이 나올 것이 확실한 질문만 기억해 다시 쓴다. 결정은 바뀌지 않아야 한다(기억 전후 `dump`가 같음).
- **범위 안:** `PlannerEvaluator`의 예상 피해 입구 하나, 빠른 이동 점수의 `MoveTo` 사본, 측정 도구의 확인 모드.
- **범위 밖:** Core 피해 식 자체를 빠르게 하는 일, 정산(시간 약 57%), 공격 범위 조회(약 15%), 병렬(BG-b).

## 3 확인한 사실 (코드 대조)

### 3.1 지금 부르는 꼴

- `Estimate(board, attacker, damage, target, percent)`가 `CombatDamageCalculator.Attack(board, _engine, _pipeline, attacker, victim, damage, role, percent, attacker.Anchor, null, board.State.Environment[, targetHealth])`를 부른다. `role`은 `percent >= 100`이면 Primary, 아니면 Additional.
- `damage`는 공격자의 공통 피해(`BaseDamage` = Core `CommonAttackDamage`)다. 영혼·유물·디버프가 이 값에 들어가므로, 이 값을 열쇠에 넣으면 그쪽 판 의존은 저절로 따라온다.
- 부르는 곳: `BestStrike`(위험·기회·빠른 이동 점수의 기회), `QuickMoveScore`의 위험 합. `QuickMoveScore`는 `CombatMovementCalculator.MoveTo(unit, destination)`로 매번 새 사실 객체를 만들어 묻는다. §17의 L3(객체 같음 64%)과 L5(값 같음 88%)의 차이는 주로 이 사본으로 본다(추정). **→ 틀림(DM-0, §11.2): 이 사본은 +4%p뿐이고, 차이의 대부분은 전투 기록(`StageRecord`)만 바뀐 새 사실 객체다.**
- `_engine`(`CombatEffectEngine`)·`_pipeline`(`TargetDamagePipeline`)은 평가기가 갖는 상태 없는 계산기다.

### 3.2 `Attack`이 두 유닛 사실 말고 읽는 것

| 읽는 것 | 어디서 | 언제 |
|---|---|---|
| 공격 프로필 목록 `board.Profiles` | `RequiredProfile`(공격자·대상·참호 보유자) | 늘 |
| 다른 유닛들 `board.Characters` — 결속 방어 보너스 | `CombatEffectiveStatsCalculator.CohesionDefenseBonus` | 대상이 결속(Cohesion) 특성을 가질 때 |
| 다른 유닛들 — 참호 오라 | `CombatCommandEffects.CaptureIncoming` → `EntrenchmentEffectRule` | 판에 참호(Entrenchment) 보유자가 있을 때 |
| 판 위의 공격자 사실(아이디로 찾음) | `TauntEffectRule.EvaluateIncomingDamage` | 대상이 도발(Taunt) 특성을 가질 때 |
| 환경의 먼지 연막 흔적 | `DustScreenTraitRule.DefenseSourcesAt` | 대상 칸에 흔적이 있을 때 |
| 환경·환경 분류의 지형(모래폭풍·고지대) | `EnvironmentTerrainRules.RemainingDamagePercent`(대상 칸·공격 출발 칸) | 늘 |

- 받는 피해를 바꾸는 규칙(`EvaluateIncomingDamage`)은 지금 셋뿐이다: 도발·참호·먼지 연막. 주는 피해를 바꾸는 규칙(`EvaluateTargetDamage`: 집중 포격·제자리 사격·추적 사격 등)의 입력은 공격력·거리·대상 체력 등 두 유닛 사실에서 나오는 값뿐이다.
- 환경 객체는 판마다 새로 만들어진다(§17.2 L2 0%). 그래서 "환경 객체가 같은가"로는 거를 수 없고, 위 표의 읽는 몫만 따로 봐야 한다.
- 사실 객체(`CharacterCombatFacts`)는 바뀌지 않는 객체이고 `Equals`를 다시 정의하지 않았다. 같은 객체면 같은 사실이다. 다음 판 만들기(`Project`)는 바뀌지 않은 유닛의 사실 객체를 그대로 넘긴다.

## 4 설계

### DM1 기억 열쇠 = 두 유닛 객체 + 판에서 읽는 몫

`Estimate`가 `Attack`을 부르기 전에 열쇠를 만들고, 있으면 기억한 답을 쓴다.

```
열쇠 = (공격자 객체, 대상 객체(유닛 또는 구조물), 구조물이면 그 체력, damage, role, percent,
        판 맥락)
판 맥락 = (프로필 목록 객체,
           대상이 결속이면 Core CohesionDefenseBonus 값, 아니면 없음,
           판의 참호 보유자 객체 목록(없으면 빈 것),
           대상이 도발이면 판 위 공격자 객체, 아니면 없음,
           대상 칸의 먼지 연막 흔적 목록,
           Core RemainingDamagePercent(대상 칸, 공격 출발 칸) 값)
```

- 결속 보너스와 지형 비율은 **Core 함수를 그대로 불러 그 값**을 열쇠에 넣는다. 규칙을 베끼지 않는다.
- 참호·도발·먼지 연막은 Core에 "이 판의 이 몫" 함수가 없어서, 읽는 대상을 넉넉하게(보유자 전부, 판 위 공격자 객체, 그 칸 흔적 전부) 넣는다. 넉넉하면 덜 맞히지만 틀리지는 않는다.
- 판마다 같은 것(참호 보유자 목록, 칸별 먼지 연막 흔적)은 판 객체마다 한 번만 만든다(판 객체 → 맥락 조각, 계획 하나 동안만).
- 기억 표는 평가기(계획 하나)가 갖고 계획이 끝나면 버린다. 계획 사이에 남기지 않는다.

### DM2 모르는 규칙이면 기억하지 않기 (안전 기본값)

- 대상의 받는 피해 규칙 묶음(`CaptureIncoming`이 고르는 규칙 종류)이 **확인한 목록(도발·참호·먼지 연막)에 없는 것을 하나라도 가지면 그 질문은 기억하지 않고 매번 계산**한다.
- 결속처럼 방어력을 판에서 읽는 다른 특성이 생겨도 잡히도록, 대상이 확인한 목록에 없는 특성(특성 키)을 가지면 기억하지 않는 안(Q-DM3 B)도 있다. 더 엄하지만 거의 모든 유닛이 특성을 가지므로 기억이 거의 안 될 수 있어, 확인 대상 특성 키 목록을 지금 것 전부로 두고 새 키만 막는 꼴을 권장한다(Q-DM3 A).
- 막힌 질문 수는 진단 칸으로 센다(§7).

### DM3 이동 사본도 같은 객체로

- `QuickMoveScore`가 `MoveTo(unit, destination)`를 부르는 자리를 평가기의 표 `(유닛 객체, 칸) → 옮긴 사실 객체`로 바꾼다. 같은 유닛을 같은 칸으로 옮긴 사본은 같은 객체가 되어 DM1 열쇠가 맞는다.
- `MoveTo`는 위치만 바꾼 새 객체를 만드는 순수 함수라 다시 써도 결과가 같다.

### DM4 확인 모드

- 측정 도구에 `memocheck` 모드를 둔다: 기억이 있어도 늘 다시 계산해 기억한 답과 비교하고, 다르면 판·유닛·열쇠를 적고 실패한다. 벤치마크 판 11개 × 씨앗 1·7, l0·l1.
- develop 갱신 뒤(규칙이 바뀌었을 수 있음) 이 모드를 다시 돌린다(README §3 절차에 한 줄).
- 결정 대조: 기억 넣기 전에 `dump`로 기준 결정 기록을 새로 만들고, 넣은 뒤 같은지 본다(BG-0 기록은 그 뒤 변경이 있어 쓰지 않는다).

## 5 예상 효과 (추정)

- 열쇠가 지금 판들에서 §17의 L3~L5 사이를 맞힌다면 예상 피해 호출의 약 64~88%를 건너뛴다. DM3를 넣으면 L5 쪽에 가까울 것으로 본다.
- 예상 피해 몫(시간 약 22%·할당 약 31%)에서 열쇠 만들기·찾기 비용을 빼면 계획 시간 약 12~18%, 할당 약 20~27%가 줄 것으로 본다. 재지 않았다(DM-0에서 잰다).
- 정산(약 57%)은 그대로라 이것만으로 첫 행동까지의 기다림이 크게 짧아지지는 않는다. GC 멈춤은 할당이 준 만큼 덜 잦아질 것으로 본다.
- 기억 표 크기: G16 계획 하나에 예상 피해 약 50만 번, 서로 다른 열쇠 수만~15만 개, 수십 MB 안쪽으로 본다(추정). 계획이 끝나면 버린다.

1. 측정 도구 빌드 오류 0.

## 8 위험

- **Core 규칙이 바뀌어 판에서 새로 읽는 것이 생기면 기억이 틀릴 수 있다.** DM2가 새 받는 피해 규칙·새 특성 키는 막지만, 이미 있는 규칙이 읽는 것을 바꾸면 못 잡는다. DM4를 develop 갱신마다 돌리는 것으로 줄인다.
- 열쇠가 너무 넉넉하면 적중이 줄어 효과가 작다. DM-0에서 먼저 잰다.
- BG-b(여러 코어)로 가면 기억 표를 여러 일꾼이 같이 쓰게 된다. 그때는 병렬 설계 BP6처럼 동시 사용 표로 바꾼다(지금은 일 스레드 하나).

## 11 DM-0 결과 (2026-11-18)

- 측정 사본(`LLMTest/core_port/probe`, Release, 씨앗 1)에서 `damage` 모드로 벤치마크 판 11개 × l0·l1을 쟀다. 계획 AI 코드는 바꾸지 않았다. 결과 원본: `LLMTest/results/core_port/20261118_dm0_memo_key.txt`.
- L6 = DM1 열쇠(프로필 목록 객체) + DM2 막기, L7 = 같은 열쇠에 프로필 목록 대신 고른 프로필 객체, L8 = L7 + 대표 객체(§11.3). 측정 코드는 `probe/DamageLog.cs`의 `TryMemoKeys`·`Canon`.

### 11.1 숫자

| 열쇠 | 되풀이(건너뛸 수 있는 몫) l0 / l1 | 어긋남 |
|---|---|---|
| L3 공격자·대상 객체만 (판 무시, 안전하지 않음) | 63.8% / 63.7% | 0 |
| L5 값 같음 (판 무시, 안전하지 않음) | 88.1% / 88.0% | 0 |
| **L6 DM1 + DM2** | 63.8% / 63.7% | 0 |
| L6 + DM3(이동 사본 같은 객체) | 67.9% / 67.8% | 0 |
| **L8 DM1 + DM2 + 대표 객체** | **97.4% / 97.3%** | 0 |

- 예상 피해 호출 1,208,813번(l0) 중 DM2로 막힌 질문 0번(확인 밖 규칙 0, 새 특성 키 0). 판에서 읽는 몫(결속 값·도발 공격자·먼지 연막·참호 보유자)이 열쇠에 실제로 들어간 질문은 20,388번(1.7%)이고 모두 T8 판이다.
- 판마다의 계획 결과 지문(평가 수·결정 해시) 22개가 DM3 사본과 원래 사본에서 모두 같다. DM3는 결정을 바꾸지 않는다.
- 판 하나(계획 하나)의 서로 다른 열쇠: L6 약 2만~15만 개, L8 1,944~6,088개(l0).

### 11.2 알게 된 것

1. **판에서 읽는 몫은 적중을 줄이지 않는다.** L6 = L3. 프로필 목록 객체는 판이 바뀌어도 같은 객체다(L6 = L7).
2. **DM3의 효과는 작다.** 63.8% → 67.9%. §3.1·§5의 짐작(L3와 L5의 차이는 주로 이동 사본)은 틀렸다.
3. **차이의 원인은 전투 기록이다.** L5로는 되풀이인데 L7로는 처음인 질문 144,416번(N8·G16·T8)에서 처음 물은 객체와 지금 객체를 속성마다 비교하니, 다른 것은 `StageRecord`와 `OccupiedCells`(위치에서 다시 만든 목록, 내용은 같음)뿐이었다. 공격자 쪽 54%, 대상 쪽 46%.
   - `StageRecord`는 보유 아군의 이번 전투 기록(받은 피해·준 피해·이동 칸·처치 수)이다. 명령 정산이 기록하고(`CombatCommandCalculator.cs:244` `CombatStageRecordSettlement.Record`), 읽는 곳은 경험치 정산·이동 되돌리기뿐이다. 피해 식은 읽지 않는다(2026-11-18 Core 검색).
   - 언제 기록만 바뀌는지는 확인하지 않았다. 계획 안의 플레이어 응수 시뮬레이션에서 플레이어 유닛이 공격하거나 움직인 뒤로 본다(추정).
4. **대표 객체로 묶으면 97%가 되풀이다(L8).** L5보다 높은 것은 L5가 능력치·상태 묶음을 같은 객체인지로 봤고, 대표 판정은 Core `SameValues`로 값을 비교하기 때문이다.
5. **대표 찾기 비용:** 찾기는 호출마다 두 번(공격자·대상)이다. `With(stageRecord:)` + `SameValues` 비교는 계획 하나에 4만~12만 번(G16 122,699번)이다. 시간은 재지 않았다.

### 11.3 제안 DM5: 대표 객체 (DM3 대신)

- 기억 열쇠의 두 유닛 자리에 사실 객체 대신 **대표 객체**를 넣는다. 대표 = 같은 아이디의 앞선 객체 중 `앞선.With(stageRecord: 이것.StageRecord).SameValues(이것)`인 것, 없으면 자기 자신. 표는 계획 하나 동안만 둔다.
- "같은 값"은 Core `CharacterCombatFacts.SameValues`가 정한다. 사실 형식에 필드가 더해지면 Core가 여기에 비교를 더하게 되어 있다(그 함수 주석, `ContractShapeGuardTests`). 우리가 필드 목록을 베끼지 않는다.
- 우리가 지키는 사실은 하나다: **"피해 식은 전투 기록을 읽지 않는다."** DM2의 확인한 사실 목록에 더하고, `memocheck`(DM4)가 develop 갱신마다 확인한다.
- `Attack`에는 지금처럼 진짜 객체를 넘긴다. 대표는 열쇠에만 쓴다.
- DM3(`MoveTo` 표)는 필요 없다. 이동 사본도 값이 같으면 같은 대표가 된다.
- DM-a에서 함께 줄일 것: 대표 찾기 비교 수(같은 아이디 안에서 위치·체력이 다르면 비교하지 않기), 열쇠 만들기 비용(판마다 같은 조각은 판 객체마다 한 번, DM2 판정·도발·결속 여부는 대표 객체마다 한 번, `object[]` 대신 구조체 열쇠). 적중이 97%이면 계산이 줄어든 만큼 열쇠 만들기가 차지하는 몫이 커지기 때문이다.

### 11.4 고친 예상 효과 (추정, 재지 않음)

- DM5면 예상 피해 호출의 약 97%를 건너뛴다. §16의 몫(시간 약 22%, 할당 약 31%)에 곱하면 계획 시간 최대 약 21%, 할당 최대 약 30%다. 여기서 열쇠·대표 찾기 비용을 뺀 만큼이 실제로 준다. DM-b에서 잰다.
- DM3로만 가면(68%) 시간 약 15%, 할당 약 21%에서 열쇠 비용을 뺀 값이다.
- 정산(약 57%)은 그대로다.
